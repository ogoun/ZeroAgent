# ТЗ zero-agent. Часть 04. Контракт с ZeroAIMemory

Контракт построен по коду и документации ZAM на срезе `m6-token-economy`, HEAD `13b0bac` плюс незакоммиченная рабочая копия, 2026-11-06 (R01, R10). Контракт прошёл независимую сверку с кодом, исправлено 27 расхождений. ZAM не менялся и не запускался: поведение установлено чтением кода и тестов и подтверждается контрактными тестами на живом сервере (MEM-130).

**Статусы возможностей:**
- **[вып.]** — выпущено в `v0.0.10-m5.7`.
- **[ветка]** — есть на ветке M6, не выпущено. Ветка тоже называет себя `0.0.10-m5.7`, поэтому версии недостаточно.
- **[план]** — запланировано в M6 или M7, маршрута ещё нет.
- **[CR]** — требуется изменение ZAM (раздел 18); не согласовано с владельцем.

## 1. Принципы

| ID | Принцип |
|---|---|
| MEM-001 | ZAM — отдельный проект на постоянно работающем отдельном сервере, одна память на множество агентов, доступная откуда угодно. zero-agent только использует её по HTTP: не запускает, не обслуживает, в её код не вмешивается |
| MEM-002 | Если память недоступна, агент выдаёт предупреждение и продолжает работу: чтение возвращает явный отказ, записи копятся в outbox в своём SQLite и досылаются после восстановления (раздел 14) |
| MEM-003 | ZAM хранит и ищет, вся генерация, решение что записать и исполнение — на агенте. На сервере нет LLM |
| MEM-004 | Шина, очереди и живые статусы — в zero-agent; push в ZAM нет |
| MEM-005 | Запись всегда явная и через шлюз `za-memory`, ни один компонент не пишет в обход него |
| MEM-006 | Контент памяти — данные, а не инструкции, в том числе `axiom` и Rules. Модель угроз в документах ZAM отсутствует, эта обязанность на агенте (R10 §4) |
| MEM-007 | Контракт привязан к обнаруженным возможностям, а не к номеру этапа |
| MEM-008 | Числовые умолчания ZAM не вписываются в zero-agent. M6 подбирает их сетками; агент передаёт свои `budget_tokens` явно |
| MEM-009 | Приоритет владельца ZAM «качество важнее токенов» сохраняется: выдача не урезается ради экономии вслепую |

## 2. Подключение

| Параметр | Значение |
|---|---|
| Адрес | `memory.url`, обязательная настройка: адрес сервера памяти |
| Токен | `Authorization: Bearer zam_…`. Хранится в секретах агента, не в файлах проекта и не в окружении дочерних процессов. Выпускается только в WebUI или администратором |
| Версия API | `/api/v1`, MCP на `POST {base_path}/mcp` |

**Заголовки.** На `/mcp` сервер пробрасывает во внутренние вызовы только перечисленные ниже контекстные заголовки. `If-Match` и `Idempotency-Key` туда не доходят, для MCP это аргументы.

| Назначение | REST | MCP | Ограничения |
|---|---|---|---|
| Сессия run | `X-Zam-Session` | Тот же заголовок | Всегда, иначе нет `seen` и учёта. До 128 символов |
| Решение | `X-Zam-Solution` | Тот же | GUID; некорректный игнорируется |
| Машина | `X-Zam-Machine` | Тот же | До 128 символов |
| Область | `X-Zam-Area` | Тот же | До 128 символов. Читает сам агент (MEM-012) |
| Ревизия | `If-Match` или `base_rev` в теле | Аргументы `rev`, `base_rev` | `PATCH /nodes` берёт `base_rev` в теле, без него 400 |
| Идемпотентность | `Idempotency-Key` | Аргумент `idempotency_key`, только `memory_log` | До 200 символов, ключ привязан к пользователю. Только записи журнала и REST `/supersede` |

| ID | Требование | Приор. |
|---|---|---|
| MEM-012 | `.zeroaimemory/area.toml` (`area = "…"`) разбирает zero-agent: ни клиент `zam`, ни сервер его не читают | P1 |

## 4. Каналы

Используются два канала.

| Канал | Назначение | Почему |
|---|---|---|
| MCP `POST /mcp` (тонкий JSON-RPC) | Операции, которые инициирует модель: `memory_search`, `memory_read`, `memory_cache_put`, `memory_tree`, `memory_write`, `memory_log`, `memory_update_entry`, `memory_link`, `memory_code` | Оптимизированный для агента Markdown, строки `~N tok` |
| REST `/api/v1` (типизированный) | Жизненный цикл и управление харнессом | Полнее MCP: `parent_id`, `solution`, `record`, `code_map`, `no_cache`, `session_id`, `brief_min_rel` |

| ID | Требование | Приор. |
|---|---|---|
| MEM-020 | `MemoryClient` скрывает выбор канала. Прочий код не знает о транспорте | P0 |
| MEM-021 | `zam mcp`, хуки и файлы привязки по pid не используются для нативного агента | P0 |
| MEM-022 | Подпроцессы `zam` используются только для `zam code sync`, `zam refs check|verify`, `zam report` (большие файлы). Выставляется `ZAM_AGENT=1`, флаги `--by`, `--origin` | P1 |
| MEM-023 | Большие тела (больше `note_body_max`, ≈10 МБ) на `POST /spaces/{s}/entries` и `/mcp`: одновременно не более двух, ожидание 500 мс, иначе 503 `busy` с `Retry-After: 2`. Шлюз выстраивает их в очередь. Обычные запросы этому лимиту не подвержены | P0 |
| MEM-024 | Таймауты: connect 2 с, recall до 1 с, поиск 5 с, запись 30 с; отмена запроса при отмене run. Требования транспорта `/mcp` (Accept, версия протокола) подтверждаются в MEM-130 | P0 |

**Правило `skip_seen`.**

| Вызов | `skip_seen` | Результат |
|---|---|---|
| MCP на L2+ | **Не передаётся** | Фрагмент остаётся с пометкой `(выдавалось)`; при источнике действующей выжимки того же ответа `(выдавалось, в выжимке)` без фрагмента (рабочая копия ZAM, не закоммичено) |
| MCP, `true` | Скрывает как REST |
| MCP, `false` | Нет ни скрытия, ни пометки |
| MCP на L1 | Скрывает как REST, пометки нет |
| REST | Передаётся явно; по умолчанию `true` |

Все варианты работают только с явной сессией в заголовке. Рантайм передаёт `true`, только когда точно знает, что нужный текст лежит в контексте этого run.

## 5. Соответствие сущностей

| zero-agent | ZAM | Как |
|---|---|---|
| Проект | Решение (solution) | GUID в `.zeroaimemory/solution.toml`. Нет файла: `POST /solutions {name, …}` и запись файла с подтверждением. 202 `pending` — работа без памяти решения до одобрения |
| Подкаталог | Область | MEM-012 |
| Узел | Машина | `X-Zam-Machine` |
| Run | Сессия | `POST /sessions {id, agent:"zero-agent", solution, area, parent_id, agent_type}`. Id всегда задаёт агент; без него сервер выдаст UUID |
| Роль run | `agent_type` | `top`, `orchestrator`, `worker:<skill>`, до 128 символов |
| Пользователь | Пользователь ZAM | Токен. Сущности «агент» в доступе нет |
| Токен | Один на агента | Все run одного узла идут с одним токеном и различаются сессией |

**Идентификатор сессии:** `za-<project>-<run_id>`, до 128 символов; значение `unattributed` зарезервировано. Срок хранения 30 дней от `last_seen_at`; для долгих проектов важные связи дублируются в записях.

**Ограничения, которые обеспечивает харнесс.** Токен открывает всю память пользователя, кроме Human, включая Vault и другие решения.

| ID | Требование | Приор. |
|---|---|---|
| MEM-013 | Правило «строго внутри проекта» распространяется на память: шлюз разрешает только текущее решение и Knowledge. `all_solutions`, чужой `X-Zam-Solution`, `scope.spaces` вне этого набора требуют гранта. Реестр утилит живёт в Knowledge и поэтому доступен | P0 |
| MEM-014 | Vault ограничен рантаймом (раздел 13). Токенов с областью нет до CR-2 | P0 |

## 6. Жизненный цикл

Нативная реализация моментов, которые у чужих агентов закрывают хуки. Клиент `zam` выполняет часть шагов параллельно ради бюджета 300 мс; нативный агент может идти последовательно, у него такого бюджета нет. Жёсткий инвариант порядка один (MEM-040).

| Момент | Действия | Статус ZAM |
|---|---|---|
| **Старт run** | `GET /health` (раз в N минут); `POST /sessions`; догоняющий снимок оборванной сессии [план]; `POST /files/changed` → `GET /file-refs`; `POST /recall {event: session_start, source, solution, area, code_map, agent_block_version, session_id, budget_tokens}`; `GET /triggers` с `If-None-Match`; фоновый `zam code sync` | [вып.] |
| **Запрос пользователя** | Параллельно: отправка очереди файлов и `POST /recall {event: prompt, prompt, session_id}`. Пусто — тишина | [вып.] |
| **Перед работой** | Поиск → карточки или `[cache]` → чтение пачкой → `memory_cache_put`. Перед исследованием поиск с `insight_kinds=[experiment,failure]` | [вып.] |
| **Взятие задачи** | `claim` (нужен `X-Zam-Session`, иначе 400), затем статус `in_progress` и `next_step` по шагам. Захват продлевается той же сессией до истечения | [вып.] |
| **Незнакомый код** | `memory_code map`, перед правкой с неясными последствиями `impact` | [вып.] |
| **Перед правкой или командой** | Локально, без сети: `file_glob`, `command_regex`, знание о файле из кэша. Одна запись показывается один раз; показанное сбрасывается при `compact` и `clear` | [вып.] в клиенте `zam`; у нас MEM-041 |
| **После инструмента, успех** | Без сети: событие, очередь изменённых файлов | [вып.] |
| **Ошибка инструмента** | Локальный `error_regex`, затем `POST /recall {event: post_tool, error, tool, session_id}`. Подсказка при каждой ошибке; третий раз тот же `err_fp` — подсказка проверить память | [вып.] |
| **После исправления** | Запись `insight` `gotcha`/`failure` с `error_regex` | [вып.] |
| **Субагент** | Родитель: `POST /sessions {id, parent_id, agent_type, agent, solution}`, затем `POST /recall {event: brief, task, parent_id, session_id: <id потомка>}`. Без `session_id` показ отметится у родителя и погасит его подсказки. Пакет вкладывается в `<task>` | [вып.] |
| **Перед компакцией** | Обновить `next_step`; параллельно отправка очереди и снимок [план] | См. метки |
| **После компакции, resume** | `POST /recall {event: recovery, session_id, budget_tokens}`. Сам начинает новую эпоху, отдельный `new_epoch` не нужен, а двойной сдвиг безвреден. Если `recovery` откладывается, перед компакцией `POST /sessions {id, new_epoch: true}` | [вып.], эпохи [ветка] |
| **Очистка контекста** | `event: session_start, source: clear`: новая эпоха без пакета восстановления | [ветка] |
| **Остановка** | Отправка очереди, синхронизация карты, снимок. Проверка итогов по журналу агента, а не по `memory_writes` (MEM-043) | [вып.] как хук |
| **Конец сессии** | `PATCH /sessions/{id} {ended: true}`, снимок. Хуки этого не шлют, это расширение нативного агента | Маршрут [вып.], снимок [план] |

**Особенности `/recall`.** `source` действует только с `event: session_start`. `session_start` подчиняется настройкам `hooks.*`, `recovery` и `brief` нет. Значения бюджетов (2000, 1500, 800) — лишь умолчания.

| ID | Требование | Приор. |
|---|---|---|
| MEM-030 | Инъекция памяти имеет бюджет на ход и потолок на сессию. Пустой результат не даёт текста. Снимок в первом сообщении: на 8k ≤ 200 токенов, 16k ≤ 400, 32k ≤ 800, 64k+ ≤ 1500 | P0 |
| MEM-031 | Дайджест старта замораживается в первом user-сообщении run и не обновляется. В system он не входит: так префикс остаётся общим между run (CTX-001, ZAM закладывает то же) | P0 |
| MEM-032 | Для самодостаточных запросов поиск в памяти пропускается; модель получает условное правило, а не обязательный вызов | P0 |
| MEM-033 | Подсказки `prompt`, `post_tool`, триггеры приходят append-сообщением с меткой источника | P0 |
| MEM-034 | Различаются «пусто» и «не успели»: `warnings: ["recall timeout"]` ведёт к одному отложенному повтору вне горячего пути | P1 |
| MEM-035 | Rules и ловушки повторно вставляются при длинных сессиях, потому что правила размываются к концу (R10) | P1 |
| MEM-040 | Инвариант: `files/changed` → `file-refs` строго последовательно, иначе индекс придёт без свежей устарелости | P0 |
| MEM-041 | Сопоставление триггеров реализовано в `za-memory` своим кодом по описанию из CR-5, включая сброс показанного. Тип `keyword` хранится сервером, но ни сервер, ни хуки его не сопоставляют: сопоставляет только `za-memory`, сверять с `zam` нечего | P1 |
| MEM-042 | `err_fp`: нормализация ошибки совместима с `zam` (blake3); детектор пары ошибка→исправление работает по семантике своего шага и плана | P1 |
| MEM-043 | «Итоги записаны» определяется по журналу агента: `memory_writes` растёт и от `claim`, `release`, `POST /cache`, смены статуса | P1 |

## 8. Чтение

### 8.1. Протокол поиска (четыре шага)

1. `memory_search`: `[cache]` или карточки. Оценки ZAM: 100–400 токенов и 30–50 на карточку.
2. Карточки → решение, что читать.
3. `memory_read` пачкой до 20 целей с явным `budget_tokens`, изменения через `since_rev`.
4. `memory_cache_put` с честными `sources`, выжимка до 600 токенов.

| ID | Требование | Приор. |
|---|---|---|
| MEM-060 | `budget_tokens` передаётся всегда: `memory_read` с умолчанием 1500 обрежет длинную заметку | P0 |
| MEM-061 | Бюджет считает сервер своим счётчиком. На L2+ планировщик учитывает `/health.tokenizer_id`, закладывает запас 10 % либо пересчитывает своим токенизатором; на L1 только своим | P0 |
| MEM-062 | Автополитика `focus` при L3: включается, когда запись длинная (`~T` > ~600), модель дорогая или контекст узкий и нужен один факт. Решение рантайма, не дисциплина модели | P1 |
| MEM-063 | `skip_seen` выбирается по правилу раздела 4. После компакции эпоха сброшена | P1 |
| MEM-064 | Фильтры применяются явно: задачи и идеи ищутся только через `kinds`; документы через `kinds=["attachment"]` (по документам ZAM полнота 0,73 против 0,98) | P0 |
| MEM-065 | «Только что записанное» читается по id, а не поиском. FTS видит запись сразу, вектор отстаёт (цели ZAM: ≤ 5 с CPU, ≤ 1 с GPU); `pending_count` показывает отставание | P0 |
| MEM-066 | `degraded: true` и `degraded_reason` видны в журнале; агент не считает отсутствие результата доказательством отсутствия | P0 |
| MEM-067 | Префетч: асинхронная подготовка релевантной памяти до хода модели, без блокировки | P2 |

Ссылки: `n:`, `i:`, `c:`, `r:`, `t:`, `k:`, `q:`, `w:`, `e:`, `a:`, `b:`, `d:`, путь `<space>:/<path>`. Ссылка `p:` токену недоступна.

### 8.2. Формат для модели

Ответы MCP идут в контекст как есть. На L2+ дата в тексте — UTC `yyyy-MM-dd HH:mm:ss`. Результаты памяти оборачиваются:

```text
<memory source="zam" kind="search" tainted="{bool}">
…ответ…
</memory>
```

## 9. Запись

### 9.1. Таксономия записи

Правила выбора вида обеспечивает шлюз: он проверяет обязательные поля и атрибуты. У каждого `insight` обязателен `data.kind`.

| Событие | Куда | Обязательно |
|---|---|---|
| Ловушка, сбой | `insight` `gotcha`/`failure` | Триггеры `error_regex`, `file_glob` |
| Эксперимент | `insight` `experiment` | `data.experiment.result`: `confirmed`, `refuted`, `inconclusive` |
| Изменение проекта | `changelog` | `data.kind` |
| Решение | `insight` `decision` | `data.decision` с `decided_by`, `revisit_if` |
| Отвергнутый подход | `insight` `decision`/`failure` | Причина |
| Знание вне проекта | `scope: global` (Knowledge) | |

## 11. Общий раздел утилит (N-11)

Такого раздела в ZAM нет и он не запланирован. Вводится двухэтапная схема.

**Этап 1, без изменений ZAM.**

| Элемент | Реализация |
|---|---|
| Запись | `insight` `pattern`, `scope: global` (Knowledge), теги `tool`, `tool:<name>` |
| Описание | `title`, `body`: назначение, вход, выход, эффекты, примеры |
| Контракт | `data.tool`: схема из части 08, раздел 6.2 (единственный источник). У `insight` `data` свободный; проверяет шлюз |
| Исходник | В `body` до 5 МБ или вложением к заметке `knowledge:/tools/<name>/<version>` |
| Находимость | Поиск `insight_kinds=[pattern]`, фильтр по `data` в поиске отсутствует, теги в поиске не фильтруются: отбор на стороне `za-memory`. Лента `GET /spaces/{s}/entries?tag=` |
| Проактивность | Триггеры `keyword`, сопоставляет `za-memory` (MEM-041) |
| Версия | Новая — только через `supersede` (иначе 409 `possible-duplicate`); поиск показывает только действующие |
| Устаревание | `revisit` + `task` на переписывание |

**Важно:** заметки Knowledge не попадают в подсказки, поэтому первичная сущность именно `insight`. Вложения Knowledge и индексируемость `.py`, `.rs` проверяются в MEM-130.

**Этап 2.** Вид записи `artifact` со строгой схемой (CR-1), подсказки и `verified_at` из Knowledge (CR-18), общий раздел между пользователями (CR-13). Жизненный цикл и контракт утилит — в части 08, раздел 6.

## 14. Деградация и ошибки

| Ситуация | Сигнал | Поведение |
|---|---|---|
| Сервер недоступен | Ошибка соединения | L0: предупреждение в UI и журнале, локальные триггеры по кэшу, запись в outbox |
| Старт сервера, нет модели, ORT или Qdrant | `degraded: true`, `degraded_reason` | Работа, поиск только FTS; повтор семантического запроса позже |
| Нет реранкера | `warnings: ["reranker not installed"]` | Лог, работа |
| Индекс отстаёт | `pending_count > 0`, `warnings: ["index rebuilding"]` | Чтение по id |
| Занято | 503 `busy`, `Retry-After` | MEM-023 |
| Медленное большое тело | 408 | Повтор с меньшим телом |
| Конфликт | 409 | MEM-073 |
| Нет ревизии | 428 | Подставить, повторить |
| Неверный или отозванный токен | 401; при превышении лимита неудачных попыток 429 с `Retry-After` | Тревога в UI, L0. На обычные запросы лимита нет |
| Доступ к решению | 202 `pending`, 403 | Показать пользователю |
| Большое тело | 413 | Разбить, вложение |
| Vault заблокирован | 503 `vault-locked` | Показать пользователю |
| Несовместимость | 400 с именем поля, 422 | MEM-010 |

## 17. Контрактные тесты

**MEM-130 (P0).** Набор на живом `zam-server`, запускается при обновлении ZAM:

- все строки таблиц: форма ответа, коды ошибок, требования транспорта `/mcp`;
- заголовок `X-Zam-Session` учитывается во всех каналах (подтвердить вывод R01 про `unattributed`);
- таблица `skip_seen`, эпохи, `recovery`;
- `claim` при гонке двух писателей, продление, снятие;
- нагрузка: целевое число параллельных писателей на SSD и HDD, задержка;
- индексируемость исходников в Knowledge, регистр путей Windows;
- восстановление outbox без задвоений.

Отдельной схемы OpenAPI у ZAM нет, поэтому форма ответа фиксируется снимками в репозитории zero-agent (CR-9).

## 19. Правила развития контракта

- Изменение ZAM отражается здесь и в контрактных тестах в той же итерации.
- zero-agent поддерживает текущую и предыдущую минорную версии ZAM.
- Изменения разрабатываются вместе: если задача требует правки ZAM, она ведётся в его репозитории с его процессом и спецификациями.
- Журнал несовместимостей ведётся в `docs/journal.md`.
- Расхождения кода ZAM и его документации перечислены в R01 §13 (15 пунктов) и R10 §12; при конфликте верить коду, затем M6, затем ТЗ ZAM.
