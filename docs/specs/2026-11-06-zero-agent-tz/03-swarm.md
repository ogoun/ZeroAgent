
## 2. Решатель: рой или один поток

Модель оркестратора предлагает декомпозицию через `set_plan`: подзадачи, зависимости, файлы, оценку объёма. Рантайм считает выгоду детерминированно и может отказать в рое; прогноз пишет он, а не модель. По умолчанию выбирается **один поток** (N-02).

### 2.1. Алгоритм

| Шаг | Проверка | Результат |
|---|---|---|
| 1 | Класс работы: только чтение (поиск, чтение, ревью, независимые гипотезы) или запись | Чтение идёт на шаг 2; запись по умолчанию в один поток |
| 2 | Граф зависимостей: критический путь близок к сумме задач | Один поток (случай −70 % у Google) |
| 3 | Множество записи: файлы и символы по git-графу, импорт-графу, tree-sitter, карте кода ZAM. Гранулярность — регион, а не файл | Пересечение ведёт к сериализации |
| 4 | Оценка выгоды | Формула ниже |
| 5 | Сила модели: при сильной одиночной модели запас роя меньше; при слабой локальной запись в рое опаснее | Корректировка порога |
| 6 | Ресурсы: слоты инференса, VRAM | На одной GPU ускорения может не быть; рой оправдан изоляцией контекста или удалёнными слотами |

```text
выигрыш = T_serial − (критический_путь + T_coord + p_conflict · T_merge)
цена    ≈ N · (токены_контекста + токены_задачи)
```

Стартовые априорные значения: `p_conflict` 20–40 % на пару при пересечении области, множитель токенов до 15×, fan-out по шкале: факты 1 агент; сравнения 2–4; сложный обзор 10+, для воркеров записи 3–5.

| ID | Требование | Приор. |
|---|---|---|
| SWM-010 | Решатель работает до запуска по декомпозиции из `set_plan` и пишет прогноз в `swarm_forecasts` с входными данными. Отказ в рое может отменить только пользователь (SWM-015) | P0 |
| SWM-011 | Запрет параллельной записи в пересекающуюся область | P0 |
| SWM-012 | Объявленная область записи — гипотеза. Механизм поправки на ходу обязателен; иначе повторяется провал динамического допуска (46 из 90 запусков заблокировались) | P1 |
| SWM-013 | Факт сравнивается с прогнозом во время работы: при отставании рой отменяется и работа продолжается в один поток | P0 |
| SWM-014 | После завершения: факт записывается, априорные значения уточняются по журналу | P1 |
| SWM-015 | Пользователь может принудительно задать `single` или `swarm`, расчёт всё равно записывается | P1 |
| SWM-016 | Показ оценки стоимости до запуска крупного роя, порог подтверждения настраивается | P1 |

### 2.2. Типовые шаблоны

| Шаблон | Когда | Механика |
|---|---|---|

| Состязательные гипотезы | Сложный баг | Параллельные проверки только на чтение |

## 5. Управление: pause, resume, cancel, correct

Control plane отделён от шины. Команда — обращение к рантайму, срабатывает мгновенно и работает при зависшей модели.

```text
UI / родитель (control_child) / пир с правом control
        │  POST /runs/{id}/control {command_id, action, mode, note, expected_generation}
        ▼
Control Router: авторизация (пользователь или предок по дереву; пир — право control проекта)
        ▼
SQLite: control_commands (pending) → журнал → уведомление
        ▼
Реестр run → AgentHandle { cancel: CancellationToken, state: watch, inbox: mpsc }
        ▼
Цикл: select! { llm_stream, tool_future, state.changed(), cancel.cancelled() }
        ├─ control.ack → журнал → SSE → UI, родитель
        └─ на границе шага → <control> user-сообщение (correct, resume)
```

| Команда | Модель стримит | Работает инструмент | Простой | Что видит модель |
|---|---|---|---|---|
| `pause` | Дочитать до границы; при `mode=now` прервать стрим | Завершить с таймаутом, новые шаги не начинать | `paused` | Ничего |
| `resume` | — | — | `<state>` из журнала, цикл продолжается | `<state>` |
| `cancel` | Обрыв стрима | Снятие дерева процессов | `cancelled` | Ничего; родитель получает событие с частичными артефактами |
| `correct mode=queue` | Дочитать | Дождаться | Следующий ход | `<control>` на границе шага |
| `correct mode=interrupt` | Обрыв | Отмена или ожидание безопасной точки | Немедленно | `<control>` сразу |

| ID | Требование | Приор. |
|---|---|---|
| SWM-060 | `pause` и `cancel` выполняет рантайм без модели; зависшая локальная модель не мешает | P0 |
| SWM-061 | Каскад: пауза и отмена распространяются на потомков, отмена через `child_token()` | P0 |
| SWM-062 | То же для верхнего агента; источник — только пользователь. Команды принимаются, даже когда ввод запрещён политикой | P0 |
| SWM-063 | Команда записывается до применения. После рестарта `pending` применяются заново, а `running` без аренды переходят в `paused`; автопродолжение настраивается | P0 |
| SWM-064 | `command_id` уникален, `generation` растёт; устаревшая команда отклоняется. Приоритет `cancel > pause > correct > resume`; `cancelled` терминален | P0 |
| SWM-065 | `control.ack` со статусом `applied`, `rejected`, `pending_safe_point`. UI показывает реальное состояние | P0 |
| SWM-066 | Управлять могут только предки по дереву и пользователь; воркеры не управляют соседями | P0 |
| SWM-067 | Текст из инструментов, шины, веба и пиров не повышается до управляющей роли | P0 |
| SWM-068 | Отмена с компенсацией: освобождение аренды, снятие захвата ZAM, сохранение или откат worktree по настройке | P0 |
| SWM-069 | Пауза на локальной модели: перед освобождением слота `action=save`, при resume `restore`; решение по замеру | P1 |
| SWM-070 | Отменённый стрим не записывается в историю; при `resume` история пересобирается байт в байт (проверка `/apply-template`) | P0 |
| SWM-071 | Вне процесса и через relay: команда в потоке `control`, проверка права `control` и `command_id` на цели; при потере связи с родителем дольше срока воркер завершает шаг и становится на паузу (dead-man) | P1 |
| SWM-072 | Заморозка работающего инструмента (cgroup freezer, Job Object) исследуется отдельно; по умолчанию пауза мягкая | P3 |

**Обязательные тесты:** команды на каждой фазе (стрим, инструмент, простой); `kill -9` между записью и применением; зависшая модель; команда через relay при разрыве; строка-имитация `<control>` в выводе инструмента.

## 7. Очередь к моделям и ресурсы узла

Покрывает N-17…N-21. Модель и железо — общий ресурс всех уровней: верхний агент, оркестраторы, рой, задания, арена и служебные вызовы (компактор, роутер) не обращаются к модели напрямую, а ставят запрос в очередь и ждут ответа.

```text
top ─┐                         ┌─► пул «локальные»: llama.cpp, vLLM на этом узле
orch ┼─► очередь запросов ─────┤      параллелизм = слоты, ограничены ресурсами
work ┤   приоритет, ожидание   ├─► пул «облако»: OpenRouter, Anthropic, OpenAI
jobs ┤                         │      параллелизм = лимит провайдера и бюджет
arena┘                         └─► пул «пиры»: модели и слоты других узлов (relay)
                 ▲
       монитор ресурсов: CPU, GPU, RAM, VRAM, диски → допуск или пауза
```
