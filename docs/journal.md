## 2026-11-09. R0, задача 11: бинарник `zero-agent` и приёмка R0

Крейт `zero-agent`: команды `doctor [--json]`, `demo-run --project <dir> [--steps N] [--resume <run>] [--crash-at intent:N|execute:N]` (по умолчанию 20 шагов) и `replay --project <dir> --run <id>`, разбор аргументов `clap 4.6.7` (derive, без цветного вывода). Коды выхода: 0 — готово, 1 — ошибка (неверные аргументы тоже 1, а не 2 по умолчанию clap; справка и версия — 0), 3 — нужно решение пользователя. `demo-run` печатает id run первой строкой stdout до шагов (по нему продолжают после аварийного завершения), затем `done` или `needs_decision` и id открытых прерываний по строке; `--resume` неизвестного run — ошибка. `replay` печатает хэш `replay_hash`; нет журнала проекта или run — ошибка 1, пустой журнал не создаётся.

Каталог данных (`home.rs`): `ZA_HOME`, иначе `%LOCALAPPDATA%\zero-agent` на Windows, `$XDG_DATA_HOME/zero-agent` (если путь абсолютный) или `~/.local/share/zero-agent` на прочих ОС; пустые переменные считаются незаданными, ничего не найдено — ошибка `NoHome`. Журнал — `ZA_HOME/projects/<project_id>/journal.db` (ARC-020), `log.txt` демонстрации — в каталоге проекта. `project_id` — первые 16 hex BLAKE3 от байтов канонического пути (`canonicalize`, на Windows вид `\\?\H:\...` с регистром из файловой системы), поэтому `a/sub/..` и `a` дают один id. Отклонения от брифа: `za_home()` и `project_id()` возвращают `Result` (каталог может не определиться, `canonicalize` требует существующий каталог).

`doctor` (`doctor.rs`): SQLite — версия встроенной библиотеки (`za_store::sqlite_library_version`, новая константа `za_store::MIN_SQLITE` = `3.51.3`) сравнивается по `x.y.z`, ниже минимума или неразборчиво — `Fail`; llama.cpp — `probe_llama(LLAMA_URL)`, не задан или недоступен — `Warn`, никогда не `Fail`; Rust — фактический `rustc --version` компилятора сборки (из `build.rs`, переменная `ZA_RUSTC_VERSION`) и MSRV из `CARGO_PKG_RUST_VERSION`: одна MSRV не говорит, чем собран бинарник. Код 1 только при `Fail`. `--json`: `{"sqlite": {"status", "detail"}, "llama": {...}, "rust": "..."}`. Проверка памяти (`ZAM_URL`, `ZAM_TOKEN`, уровни L0–L2) и тесты на неё перенесены в задачу 9: клиент памяти отложен до завершения ZeroAIMemory (решение заказчика).

Приёмочные тесты `crates/zero-agent/tests/r0_acceptance.rs` запускают бинарник отдельным процессом с `ZA_HOME` в `CARGO_TARGET_TMPDIR`: аварийное завершение после выполнения шага 3 — продолжение даёт код 3, открытое прерывание `unk-{run}:3:1`, единственное незавершённое намерение `tool` шага 3, по одному намерению на эффект шагов 1–3, файл не изменился, повтор даёт то же; аварийное завершение после намерения шага 2 — `NonIdempotent` не выполняется повторно; `replay` дважды и после повторного `demo-run` завершённого run даёт тот же хэш, тот же сценарий в другом проекте — тот же хэш; кириллический путь с пробелами (`Рабочий стол/проект 1`, `ZA_HOME` «домашний каталог»); журнал вне каталога проекта; `doctor` с недоступным и с незаданным `LLAMA_URL` — `Warn` и код 0. `std::process::abort()` на Windows даёт код 0xC0000409, тест проверяет только ненулевой код.

**Ручная приёмка R0** (Windows, диск H:, `ZA_HOME=.tmp/r0-home`, проект `.tmp/r0`, отладочная сборка): `doctor` — `sqlite ok 3.54.1 (минимум 3.51.3)`, `llama warn LLAMA_URL не задан`, `rustc 1.99.1 (58cf8f9c3 2026-10-13) (MSRV 1.92)`, код 0; с `LLAMA_URL=http://127.0.0.1:8080` (сервер не запущен) — `warn`, код 0. `demo-run --steps 20` — `done`, код 0, 20 строк в `log.txt`; два `replay` подряд — один хэш `5095e4f4953a4d10424fa2b755c78be6e0aff419c91b700d7b2a534352ab4ad9`. Время `demo-run` на 20 шагов 1,7…2,2 с, около 90 мс на шаг: в шаге намерение `NonIdempotent` с `synchronous=FULL` (замер задачи 3: `append_durable` 33,4…33,8 мс, `append` при NORMAL 0,17 мс) и `sync_data` файла `log.txt`. Live-проверка llama.cpp не выполнялась: сервер не был запущен.

## 2026-11-09. R0, задача 10: демонстрационный run

`za-core`: `run_demo(store, run, cfg)` — детерминированный run без сети для сквозной проверки журнала. Шаги нумеруются с 1: перед шагом `n` вызывается `next_step()`, поэтому шаг `n` — эффекты `{run}:n:0` (`model`, `Idempotent`, аргументы `{step, prefix_hash}` с хэшем стабильного префикса фиксированного демонстрационного промпта, ответ `{text}` по номеру шага) и `{run}:n:1` (`tool`, `NonIdempotent`, аргументы `{file: "log.txt", line: "step n"}`, дописывает строку в `workdir/log.txt` с `sync_data`, других файлов не трогает). Нет run — создаётся (`Top`, `project_id` `demo`) и переводится в `running`; перед шагами run проходит `recover`, при неизвестном исходе (и при `EffectError::Unknown` во время шагов) run переводится `running → paused` с причиной `needs_decision` (`NEEDS_DECISION`) и возвращается `DemoOutcome::NeedsDecision(ids)` без шагов; run в `paused` снова проходит `recover`: прерывания открыты — те же id без новых событий, открытых нет — `paused → running` и продолжение; run в `done` возвращает `Done`, ничего не записывая; прочие статусы — `InvalidTransition`. `CrashPoint::AfterIntent(n)` / `AfterExecute(n)` вызывают `std::process::abort()` внутри замыкания `tool` до и после записи файла (проверяются в задаче 11 через CLI, не в тестах процесса). `replay_hash` — BLAKE3 hex от тега `za-replay-v1` и канонического JSON `{actor, kind, payload}` каждого события run по `seq`, с префиксом длины; без `seq`, `id`, `ts`, `run_id`, `parent_seq`, `schema_v`, `blob_ref`, `tainted`; в payload id run заменяется на `{run}` (ключи эффектов, `root_id`, id прерываний), у `interrupt.opened` удаляется `payload.intent_seq` (глобальный `seq`). Времени хранилище в payload не пишет. `za-core` теперь зависит от `za-llm` (ради `prefix_hash`, с `default-features = false`) и `blake3`.

Решения контроллера (раунд исправлений 1): `za-protocol` разрешает прямой переход `running → paused` — немедленная пауза в безопасной точке, выбранной самим рантаймом (ожидание решения, отказ провайдера), без `pausing`. `za-store`: `set_status_with_reason(id, to, expected_generation, reason)` добавляет `reason` в payload `run.status`, `set_status` делегирует с `None` (payload без поля). `za-llm`: функция `probe` (по умолчанию) включает зонд и зависимости `reqwest`, `thiserror`, `tracing`; без неё крейт — только префикс и хэш; `cargo tree -p za-core` не содержит `reqwest`, `hyper`, `rustls`.

## 2026-11-09. R0, задача 8: зонд llama.cpp

`za-llm`: `probe_llama(base_url)` делает `GET {base}/props` (завершающий `/` в базе допустим), таймаут соединения 2 с, общий 5 с. `n_ctx` берётся из корня ответа, иначе из `default_generation_settings.n_ctx`; должен быть положительным u32. `model` — `model_alias`, иначе `model`, иначе имя файла из `model_path` без каталога (разделители `/` и `\`), иначе пустая строка. `total_slots` — из одноимённого поля, если есть. Ошибки: `ProbeError::Unreachable` (нет соединения, таймаут, обрыв, некорректный URL), `ProbeError::BadResponse` (не 2xx, тело не JSON, нет `n_ctx`). Положение полей на живом `llama-server` не проверено: тест `live_probe` под `#[ignore]`, запуск с `LLAMA_TEST_URL`. HTTP-клиент `reqwest 0.12.28` без default features, с `json` и `rustls-tls` (rustls на ring, без OpenSSL), корни сертификатов встроенные (`webpki-roots`), а не из хранилища ОС, чтобы поведение на Windows и Linux совпадало (решение заказчика); лицензия `webpki-roots` CDLA-Permissive-2.0 добавлена в `deny.toml`. Клиент строится с `no_proxy()`: локальный сервер не должен достигаться через `HTTP_PROXY`/`ALL_PROXY`. Поддельный сервер в тестах — `axum 0.8.9` (только dev). На Windows отказ в соединении приходит примерно за 2 с (ОС повторяет SYN), укладывается в таймаут соединения.

## 2026-11-09. R0, задача 7: стабильный префикс и его хэш

`za-llm`: `render_tools` — инструменты, отсортированные по `name`, массивом объектов `{description, name, parameters}` в каноническом JSON (CTX-001); `render_system` — единственное system-сообщение из блоков core, adapter, overlay, agents_md через пустую строку, блоки из одних пробельных символов пропускаются (CTX-004). Во всех строках, включая строки внутри `parameters`, CRLF заменяется на LF, иначе хэш расходился бы между Windows и Linux. `prefix_hash` — BLAKE3 hex от тега формата `za-prefix-v1`, затем tools и system, каждая часть с префиксом длины (u64 LE), чтобы перенос текста между частями менял хэш. Золотой хэш фикстуры (три инструмента, короткие блоки) в `crates/za-llm/tests/golden/prefix.hash`, файл помечен `-text` в `.gitattributes`; при расхождении тест печатает новый хэш. `za-llm` зависит только от `za-protocol`, `serde_json`, `blake3`.

## 2026-11-09. R0, задача 6: протокол эффектов и восстановление

`za-store`: `record_intent` пишет строку `effects` и событие `effect.intent {key, class, name, args}` в одной транзакции; намерение `NonIdempotent` фиксируется с `synchronous=FULL` (CORE-005), прочие классы — с надёжностью по умолчанию. `record_receipt` пишет `effect.receipt {key, result}`; результат длиннее `BLOB_THRESHOLD` уходит в blob, в событии `{key, result_blob}`, хеш в `effects.blob_ref`. `effect` отдаёт строку вместе с результатом, `pending_effects` — намерения без квитанции по `intent_seq`. `open_interrupt` идемпотентен (`ON CONFLICT DO NOTHING`, событие `interrupt.opened {id, kind, payload}` только при первом открытии), статус `open`. Новые ошибки: `UnknownEffect` (квитанция без намерения), `EffectConflict` (повторное намерение или квитанция). Намерение и прерывание для неизвестного run дают `UnknownRun`.

`za-core`: `RunCtx::effect` с ключом `(run, step, effect_seq)`: квитанция есть — результат из журнала без выполнения; намерение без квитанции — для `NonIdempotent` (по журналу или по вызову, решает более строгий) прерывание `unknown_outcome` с id `unk-{effect_key}` и `EffectError::Unknown`, для прочих классов повтор без нового намерения; квитанция хранит конверт с явным исходом `{"outcome":"ok","value":…}` или `{"outcome":"error","message":…}` (решение контроллера; большой конверт целиком уходит в blob по обычному пути хранилища), отказ при повторе возвращается из журнала как `EffectError::Failed` с тем же сообщением, успешное значение любой формы — как успех, квитанция без конверта — `EffectError::Store` (повреждение). После любой `EffectError::Store` контекст отравлен: дальнейшие `effect` дают `EffectError::Poisoned` без обращения к журналу, `next_step` это не снимает, продолжение — только новым `RunCtx` (иначе повтор на том же контексте занял бы следующий ключ, и после перезапуска `NonIdempotent`-действие выполнилось бы второй раз). `EffectRow` несёт `name` и `args` из намерения; при повторе расхождение класса, имени или аргументов с журналом пишется в `warn`. `recover` открывает прерывания для всех незавершённых `NonIdempotent` и возвращает `Recovery::NeedsDecision` с их id, иначе `Clean`.

## 2026-11-09. R0, задача 5: blobs, runs, снимки

`za-store`: blobs по BLAKE3 (`put_blob` идемпотентен; до 1 МиБ в строке `blobs`, больше — файл `blobs/<hash>` рядом с `journal.db`, запись через временный файл, `fsync` и переименование; при чтении хеш и размер сверяются). Payload события длиннее `BLOB_THRESHOLD` = 64 КиБ канонического JSON сохраняется blob в той же транзакции, в строке события `null` и `blob_ref`; `read_after` и `read_run` подставляют payload обратно (ARC-032). Runs: `create_run` (статус `queued`, `generation` 0, `root_id` от родителя, у корня свой `id`) и `set_status` (сверка `expected_generation`, затем таблица переходов, `generation + 1`) пишут `run.created` и `run.status {from, to, generation}` в той же транзакции. Снимки: `save_snapshot` (тот же `seq` заменяется), `latest_snapshot` по наибольшему `seq`. Новые ошибки: `UnknownRun`, `InvalidTransition`, `StaleGeneration`. Миграция схемы не понадобилась. Тест `disk_full` переведён на payload 512 КиБ: 1 МиБ теперь уходит в файл и БД не переполняет.

## 2026-11-08. R0, задача 4: устойчивость к `kill -9`

Тестовый бинарник `za-store/src/bin/crash_writer.rs` пишет события из четырёх потоков (убийство попадает и в середину group commit) и печатает `seq` каждого подтверждённого с немедленным flush. `tests/crash.rs` убивает его через `Child::kill` (TerminateProcess на Windows, SIGKILL на Linux) через 50…753 мс после первого подтверждения, открывает журнал заново и проверяет, что все напечатанные `seq` на месте: 20 раундов с `Durability::Normal` и 5 раундов с `append_durable`. На Windows прошло без потерь; `journal.lock` после убийства свободен. За окно 50 мс подтверждается около 430 событий в режиме Normal и около 3 в режиме durable. Тест ловит потерю: при подмене печатаемого `seq` падает в первом раунде. Время теста около 21 с.

## 2026-11-08. R0, задача 3: журнал на SQLite

Крейт `za-store`: `journal.db` в каталоге проекта, блокировка `journal.lock` (`File::try_lock`, второй `open` даёт `StoreError::Locked`), миграции по `PRAGMA user_version` (схема 0001: `runs`, `events`, `effects`, `interrupts`, `snapshots`, `blobs`, таблицы STRICT, `seq` с AUTOINCREMENT). Один поток-писатель: group commit до 256 команд в `BEGIN IMMEDIATE`, у каждой команды своя точка сохранения, ответ после COMMIT; SQLITE_FULL даёт `StoreError::Full`, писатель продолжает работу. Четыре читателя `query_only=ON` в своих потоках. `rusqlite 0.41.1` bundled, SQLite 3.54.1.

**Замер `synchronous`** (Windows, диск H:, 200 последовательных `append` и 2000 параллельных): FULL — 31…33 мс на последовательный `append`, 2000 параллельных за 0,47…0,48 с; NORMAL — 0,17 мс и 0,41 с. Group commit выравнивает пропускную способность, но задержка одиночной записи при FULL на два порядка выше.

**Решение (контроллер, раунд 1):** по умолчанию `Durability::Normal` (`synchronous=NORMAL`). WAL с NORMAL переживает `kill -9` (NFR-08), а FULL с 31…33 мс на запись ломает NFR-02 (≤ 50 мс на ход). Для записей, которые обязаны пережить отключение питания (намерения `NonIdempotent`-эффектов, задача 6), есть `append_durable`: пачка с такой командой целиком фиксируется с FULL, затем значение восстанавливается. `StoreOptions::durability = Full` включает FULL для всего. Повторный замер: `append` 0,17 мс, `append_durable` 33,4…33,8 мс, `append` сразу после серии durable 1,0…1,1 мс (вероятно, авточекпоинт WAL), 2000 параллельных `append` за 66…69 мс.
