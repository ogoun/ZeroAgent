## Rule of Two без вопросов и отклонения от SEC-052, SEC-053

**Контекст.** SEC-052 (Rule of Two) требует, чтобы в одном run не сходились три свойства — недоверенное содержимое, приватные данные и внешняя связь, а третье добавлялось только через человека. SEC-053 требует подтверждения действий в tainted-контексте. R1-C1 (D82) уже снял причину `tainted`: чтение из сети не влияет на запуск команд.

**Решение заказчика 2026-11-11 — «Не спрашивать».** Сочетание приватных данных, недоверенного ввода и внешней связи прерывания не вызывает: вызов идёт по режиму. Экспозиция вычисляется и записывается: `LoopState.exposure` в снимке v4, событие `exposure.changed`, запись аудита `rule_of_two` на каждый вызов с внешней связью, исполняемый при всех трёх свойствах, строка CLI один раз на run. Вызов с внешней связью — это `risk = Network`, инструмент `web_*` и `bash`, классифицированный как сетевой или неопределённый (неразобранный сегмент, метка `unparsed`). Вызовы без внешней связи — `finish`, `ask_user`, `request_grant`, чтение и правка в проекте, `bash`, который разбор считает локальным, — записи не получают и при трёх свойствах (Ruling сомнения 1 прохода fix-5). Для `bash` это не гарантия: «локальная» команда вроде `python x.py` может сама передать данные наружу, а записи у неё нет. Run, где наружу выходит только `bash` без нативного сетевого вызова, трёх свойств не набирает: `bash` в свойства не входит (принятый риск ниже; Ruling I1 повторного ревью fix-5 и fix-6). Свойства вызова — это снимок начала пакета плюс вклад самого вызова. Сколько свойств добавил сам вызов, неважно: переход может быть и сразу на два. Формулировка плана «третье свойство при двух уже установленных» зависела от порядка вызовов: «чтение по гранту, затем сеть» записи не давало. Её заменил Ruling I1 ревью задачи 5. Причины `rule_of_two` в порядке причин одобрения нет. Буква SEC-052 «третье только через человека» и требование SEC-053 этим решением отменены (ссылки: `preflight-rulings.md`, `task-13-notes.md` п. 8 R1-C1, D82, D101, D106).

**Как считается.** Свойства независимы: `untrusted` — любое происхождение метки, кроме `outside_project`; `private` — исполненный нативный вызов с путём вне проекта (в том числе по гранту); `external` — исполненный нативный сетевой вызов. Все три берутся со снимка на начало пакета: аргументы вызовов одного пакета модель выбрала до их результатов, обмен данными внутри пакета невозможен, реплей детерминирован. `bash` и правки внутри проекта в свойства не входят.

**Принятые риски.** Эксфильтрация (командой `bash` или сочетанием нативных вызовов) не предотвращается; граница — режимы, гранты, доверие к проекту и правила по домену. Записывается она только у вызова с внешней связью. Граница shell — best effort (SEC-002): разбор команды узнаёт сетевые утилиты, но не программу, которая сама открывает соединение (`python x.py`, собранный бинарник, скрипт сборки). Такая команда считается локальной: записи `rule_of_two` у неё нет, а run, где наружу выходит только она, без нативного сетевого вызова, трёх свойств не набирает. Аудит позволяет найти такие run после факта. Пересмотр — вместе с ОС-изоляцией и прокси шлюза для `bash` (R2).

**Где в коде** (R1-C2, задача 5):

- тип `za_agent::Exposure` и `Exposure::untrusted_from` — `crates/za-agent/src/exposure.rs`; `decide`, `PolicyCx` (`crates/za-agent/src/policy.rs`) и `REASON_ORDER` (`tools.rs`) экспозиции не получают и не менялись;
- тип `Exposure`, `Exposure::all`, отметка `rule_of_two_marked` и `RuleOfTwoNotice` — модуль `crates/za-agent/src/exposure.rs` (ревью задачи 5, m8);
- флаги вызова — в квитанции эффекта (`private`, `external`; `untrusted` — по происхождениям квитанции): реплей квитанции даёт те же флаги без инструмента и без диска (D92). Флаги ставит только вызов, дошедший до инструмента: отказ разбора, гейта, политики или пользователя и вызов со сменой класса пути их не ставят. Ошибка самого инструмента флаги ставит (например, `web_fetch` с ответом `blocked: local or private address`): запрос, хотя бы DNS, мог уйти (m3 ревью задачи 5);
- снимок начала пакета — `ToolEnv.exposure` (`LoopState::exposure_now`); итог пакета — `ToolsOutcome.exposure`, `ToolsOutcome.rule_of_two` (вызовы пакета с записью аудита `rule_of_two`; признак — в квитанции, `Receipt.rule_of_two`), `ToolsOutcome.exposure_calls` (вызовы, поставившие флаг, которого в снимке не было);
- запись аудита `audit_action::RULE_OF_TWO` (`{call_id, tool, exposure, effect_key}`, объект — run) пишет слот вызова при живом исполнении, как запись гранта (SEC-090), — до вызова, вместе с `tool.started` (Ruling m2 ревью задачи 5). Свойства до вызова: `private` и `external` — по путям решения и спецификации, `untrusted` — по происхождениям без метки самого результата (`ToolJob::exposure_before`). Поэтому отмена посреди вызова запись не теряет, а реплей квитанции после паузы её не повторяет. Повтор замыкания после сбоя процесса (намерение без квитанции) защищён ключом эффекта: `ProjectStore::append_audit_once` пишет одну запись на `effect_key`. Отметка `"rule_of_two": true` ставится в `tool.started`. Если третье свойство дала только метка результата, запись пишется после вызова, а отметка ставится в `tool.finished`. Условие внешней связи — `ToolJob::external_link` (`crates/za-agent/src/tools.rs`); свойства экспозиции оно не меняет: `bash` в них по-прежнему не входит;
- сбой записи аудита обрабатывается как аудит гранта (D72, D91), без молчаливой потери (Ruling m1). До вызова: вызов не исполняется, квитанция — отказ `internal error: journal write failed`, run встаёт на паузу `store`. После вызова: результат не выдаётся (недоверенного содержимого в контексте нет, свойств два), флаги `private` и `external` остаются;
- событие `exposure.changed {untrusted, private, external, calls, rule_of_two}` пишет драйвер после пакета, если флаги run изменились. После пакета, остановленного на прерывании, его нет: шаг доигрывается при resume и пишет событие один раз. Затем `st.exposure` — объединение со снимком; снимает флаги только новый run. Вызовы при трёх свойствах в следующих пакетах флагов не меняют: их видно по аудиту и отметке в `tool.started`;
- строка CLI «в этом запуске сошлись недоверенное содержимое, ваши файлы вне проекта и обращение в сеть (SEC-052); вызов выполнен, запись в аудите» — `crates/zero-agent/src/run.rs`. Она печатается один раз на run, по первой отметке `rule_of_two` (`RuleOfTwoNotice`), и модели не уходит. Resume run, у которого запись `rule_of_two` уже есть, строку не повторяет. Если событие потеряно при отставании шины, строку даёт проверка аудита в конце процесса (m4);
- снимок v4 (D130): `Snapshot.exposure`, `Snapshot.skills` (оба `#[serde(default)]`, `skills` пуст до задачи 13); снимки v1–v3 читаются, фикстура v3 — `crates/za-agent/tests/golden/r1c1_v3.json`;
- тесты: `crates/za-agent/tests/policy.rs` (`rule_of_two_never_asks`, `tainted_never_asks_still_holds`, `untrusted_ignores_outside_project_origin`), `crates/za-agent/tests/tools_native.rs` (`exposure_*`, `third_property_*`, `only_external_link_calls_recorded_under_three_properties`, `grant_read_then_two_fetches_two_records_one_line`, `rule_of_two_survives_cancel_mid_call`, `rule_of_two_audit_failure_blocks_call`, `rule_of_two_not_duplicated_on_retry_after_crash`), `crates/za-agent/tests/resume.rs` (`snapshot_v3_reads_with_default_exposure`, `snapshot_v3_untrusted_label_resumes_untrusted`; `broken_snapshot_fails_other_version_does_not` — `{"v": 5}` не читается), `crates/za-store/tests/conformance.rs` (`audit_once_per_effect_key`), модульные `exposure::tests`, `tools::tests::reason_order_has_no_rule_of_two`, `tools::tests::external_link_cases`, `run::tests::rule_of_two_line_once_per_run`.

## Сетевой шлюз

**Контекст.** SEC-047 требует один компонент сетевого чтения: только чтение, без учётных данных и cookie пользователя, запрет локальных адресов, лимит размера и частоты, журнал. Обход фильтра «нашли — закрыли» (литералы `0x7f.1`, `2130706433`, NAT64, 6to4, DNS rebinding, редирект на `127.0.0.1`, `localhost.`) закрывается архитектурой, а не списком исключений (D107, D108, D124).

**Решение.** Крейт `za-web` (задача 6), объект `WebGateway` — один на процесс, его держат оба веб-инструмента.

- **Разрешающий список (D108).** `check_ip` пропускает только глобально маршрутизируемые адреса: IPv4 вне всех строк реестра IANA IPv4 Special-Purpose (целиком, в том числе строки с «Globally Reachable = True», например `192.88.99.0/24`, `192.31.196.0/24`) и вне `224.0.0.0/4`; IPv6 — только `2000::/3` вне всех строк реестра IANA IPv6 Special-Purpose (целиком весь `2001::/23`, `2620:4f:8000::/48`, `3fff::/20`, `5f00::/16`). Всё прочее — отказ `local or private address`: новый блок реестра правки кода не требует. Вложенный IPv4 проверяется правилом IPv4 только там, где его положение однозначно и трансляция стандартна: `::ffff:0:0/96`, `64:ff9b::/96`, `2002::/16`. Локальный NAT64 `64:ff9b:1::/48` (RFC 8215) отвергается целиком, в любой форме, в том числе `/96`: длину префикса и саму трансляцию выбирает оператор сети, и вердикт по вложенному адресу был бы догадкой (Ruling I1 ревью задачи 6). IPv4-compatible `::/96` (устарел по RFC 4291, 2.5.5.1, глобально не маршрутизируется) тоже отвергается целиком (M6 ревью задачи 6, строже буквы D108). Таблицы — константы `crates/za-web/src/addr.rs`, снимок реестров от 2025-10-09 (сверено 2026-11-16); тест сверяет их со своей копией реестров и проверяет первый и последний адрес каждой строки.
- **Где проверяется.** В резолвере клиента (`FilteredResolver`, трейт `reqwest::dns::Resolve`) поверх системного: соединение идёт только по адресам, которые фильтр пропустил, поэтому проверка и подключение не разделены во времени. Хоть один запрещённый адрес в ответе — отказ всего имени (признак rebinding). IP-литерал резолвер не видит — его проверяет `parse_url` сразу. Хост нормализует только `za_core::net::normalize_host` (D124), после неё — лексический запрет `localhost` и `*.localhost`; запрос уходит на нормализованный хост.
- **Предел портов.** Только порты `[web] ports` (по умолчанию `80, 443, 8080, 8443`), иначе `blocked: port <n> is not allowed` до соединения: GET к SMTP, Redis и подобным сервисам на публичном адресе (межпротокольная атака) невозможен.
- **Клиент.** `no_proxy()` (переменные `HTTP_PROXY` и прокси системы разрешали бы имена мимо фильтра), без cookie, без `Accept-Encoding` (ответ с `Content-Encoding` не `identity` — ошибка без распаковки), `User-Agent: zero-agent/<версия>`, `connect_timeout`, TLS — rustls с webpki-roots.
- **Редиректы** исполняет сам шлюз (`Policy::none` у клиента): каждый переход — своя запись журнала, проверка URL и порта, `robots.txt` и место в лимитере. До пяти переходов на тот же нормализованный хост (`http` → `https` можно, обратно — нет); иначе вызов возвращает `redirected to <url>; …`, и следующий вызов модели снова проходит политику и правила по домену.
- **Лимиты и дедлайн.** Тело до `max_bytes` (5 МиБ), скользящее окно `requests_per_minute` (60) на процесс и не чаще запроса в 500 мс к хосту; запросы к одному хосту идут по одному (замок хоста: `robots.txt` запрашивается один раз). Дедлайн вызова соблюдается на каждом шаге: шлюз сам возвращает `Timeout` вместе с журналом обращений, включая прерванный запрос (`reason = "timeout"`).
- **`robots.txt`** — свой разбор RFC 9309: группа `zero-agent`, иначе `*`; самое длинное совпадение, при равенстве `Allow`; 4xx — всё разрешено, 5xx и сбой — всё запрещено; кэш на источник 24 часа. Редирект `robots.txt` на тот же хост исполняется (до пяти, `http` → `https` тоже), на другой хост — не исполняется и считается 4xx (RFC 9309, 2.3.1.2 «недоступен»), соединения с чужим хостом нет; цель, которую отверг фильтр (порт, userinfo), — запись `blocked` и тоже «недоступен»; 3xx без `Location` — как 5xx.
- **Пределы разбора `robots.txt`** (M4 ревью задачи 6). Текст — до 500 КиБ (RFC 9309, 2.5; столько же читают Google, Bing и Яндекс), дальше не разбирается, обрезка по последней целой строке. Правил группы агента — до 2000 (`ROBOTS_MAX_RULES`), дальше не действуют. Сопоставление жадное по буквальным частям между `*` с линейным поиском подстроки: O(путь + шаблон) на правило вместо прежней динамики O(шаблон × путь). Шлюз разбирает текст один раз на источник и держит в кэше разобранные правила. Худший случай у пределов текста и длины URL (замер в release): разбор около 1 мс один раз на источник, сопоставление до 3,6 мс на запрос; прежде — около 0,5 с на каждый запрос.
- **Журнал.** На каждый HTTP-запрос вызова, отказ фильтра, отказ `robots.txt` и прерванный дедлайном запрос — запись `za_core::NetRequest` (D112). Userinfo и фрагмент в журнал и модели не попадают: ни из URL вызова, ни из `Location` (`final_url`, текст `redirected to <url>`; M2 ревью задачи 6). Строка отладочного лога (`ZA_LOG=debug`) несёт только хост и исход: строку запроса с секретом маскирует только запись журнала (M5).

**Второй держатель HTTP-клиента.** `za-web` — второй после `za-llm` крейт с `reqwest` (те же функции `json`, `rustls-tls`). `za-llm` приходит в `za-web` только транзитивно через `za-core` без функций: клиент шлюза — свой. `cargo xtask policy` проверяет: `za-web` зависит только от `za-protocol` и `za-core`, от `za-web` — только `zero-agent` и `xtask`; прямая зависимость от `reqwest` любого вида (обычная, dev, build) — только у `za-llm` и `za-web` (Ruling I2 ревью задачи 6: иначе второй клиент строится и без `Client::builder` в исходнике, например `Client::default()`); внутри них `reqwest::Client::builder`, `ClientBuilder`, `Client::new`, `Client::default`, упоминание типа `reqwest::Client`, `reqwest::get` и `reqwest::blocking` — только в `crates/za-web/src/gateway.rs` и `crates/za-llm`; у `reqwest` в сборке workspace вместе с тестами нет функций `gzip`, `brotli`, `deflate`, `zstd`, `cookies`, `socks`, `http2`, `http3`, корней ОС и системного TLS (D129).

**Тестовые подмены** (`with_test_resolve`, `with_inner_resolver`) существуют только с признаком сборки `test-hooks` (D128), не под `debug_assertions`: отладочная и release-сборка обхода фильтра не содержат. Тесты с ними — `crates/za-web/tests/gateway.rs` (`required-features`), в CI — отдельный шаг `cargo test -p za-web --features test-hooks`.

**Принятые риски.**

- **Hairpin NAT.** Публичный адрес, который ведёт обратно в сеть пользователя (внешний IP своего роутера с hairpin NAT, публичный адрес собственного сервера), фильтр не отличает от прочих публичных адресов. Предел портов снимает межпротокольные атаки, но HTTP-сервис на разрешённом порту такого адреса достижим.
- **Порты 8080 и 8443** открыты и на публичных адресах внутренних служб, выставленных наружу.
- **NAT64 с общеизвестным префиксом** `64:ff9b::/96` пропускает публичный IPv4 по вердикту вложенного адреса: трансляцию делает сеть пользователя. Локальный NAT64 `64:ff9b:1::/48` риском не является — он отвергается целиком.
- **Пределы `robots.txt`.** Правила дальше 500 КиБ текста или 2000-го правила группы не действуют: для такого сайта шлюз разрешает больше, чем хотел владелец.
- **Прокси для `bash`** нет: команды оболочки ходят в сеть мимо шлюза (D104, R2).

## Инструмент `web_fetch`

**Решение (D110, D112, D113, задача 8).** `za_web::web_fetch_tool(gateway, extractor)` — чтение страницы только через шлюз и только с извлекателем: HTML разбирает `Extractor` (трейт `za_core::extract`, реализация — подпроцесс, задача 10), без извлекателя инструмента нет. В продукте `web_fetch` регистрирует бинарник (задача 14).

- **Дедлайн.** Слот пакета ставит `ToolCx::deadline` = старт вызова + тайм-аут инструмента − 1 с (`za_core::call_deadline`; у пределов до 1 с — половина предела). `web_fetch` передаёт его шлюзу и ограничивает им же извлечение HTML. Тайм-аут шлюза или извлечения — результат `timeout after N s` с журналом обращений; внешний тайм-аут слота (при нём future брошен и журнала нет) остаётся страховкой.
- **Журнал обращений** — `ToolOutput::requests` с `#[serde(skip)]`: в квитанцию эффекта поле не попадает, там URL с секретом в параметре был бы без маски. Слот пишет по событию `web.request {call_id, tool, ...NetRequest}` после вызова и до `tool.finished`, тем же путём, что `boundary.outside`; все строки события (`url`, `final_url`, `reason` — в причине бывает адрес редиректа) проходят маску секретов. Реплей квитанции замыкание слота не запускает: событий повторно нет.
- **Метка.** У любого результата `web_fetch`, в том числе ошибки, происхождение `web`. Своё происхождение инструмента заменяет общие `tool` (от `spec.tainted`) и `network` (от `risk = Network`): первая строка — `[untrusted content: web]`, аудит получает точное происхождение. Происхождения по предметам вызова остаются: `outside_project` — по путям, `network` — у сетевой команды (метка `bash` — `network` или `outside_project`, и сетевая команда с путём вне проекта иначе потеряла бы `network`).
- **Результат.** Строки `url`, `status`, `type` (значение из таблиц D109, а не заголовок сервера), `title` (пробелы и управляющие символы схлопнуты в пробел — заголовок не подделает строку `status:`; не длиннее 200 символов с `...`), при упрощённом разборе — строка `[simplified extraction: …]` (признак `Markdown.simplified`, D127), пустая строка, текст; оборванное тело — `[truncated at N bytes]`. Код не 2xx — ошибка `HTTP <код> <фраза>` и до 2 КиБ текста тела. Редирект на другой хост — не ошибка: ответ называет адрес. PDF до задачи 10 — `unsupported content type application/pdf`.
- **Нечитаемый текст.** Текст без непробельных символов, с долей символов замены U+FFFD и управляющих больше 10 % от непробельных или с долей «двоичных» управляющих символов WHATWG MIME Sniffing (0x00–0x08, 0x0B, 0x0E–0x1A, 0x1C–0x1F) больше 1 % всех символов — `no readable text on the page`. Вторая доля ловит двоичные данные в однобайтовой кодировке (`charset=windows-1251`): байты ≥ 0x80 там становятся буквами, а управляющие остаются управляющими; мерится текст после декодирования, поэтому нулевые байты UTF-16 сюда не попадают (M2 ревью задачи 8). Проверка идёт до извлекателя (двоичные данные под `text/html` в подпроцесс не уходят) и после него (пустой Markdown). Пометка обрыва `[truncated at N bytes]` остаётся и у этого ответа.
- **`digest`** при `prompt` — строки заголовка и отрывки `rank_passages`: пакет показывает его вместо выгрузки длинной страницы (D44). Бюджет — фактический предел слота на этом окне `ToolCx::output_budget` (I2 ревью задачи 8): слот заполняет его из того же расчёта, по которому потом режет результат (`spill_limit_bytes(n_ctx, spill_share, output_limit)` с выгрузкой, `output_limit` без неё; вне пакета — 128 КиБ). Из него вычитаются шапка, пометка обрыва и запас `za_core::DIGEST_RESERVE` = 256 байт под строки слота (первая строка происхождений и указатель выгрузки; худший случай — около 220 байт). Длина меряется после `escape_untrusted` (`za_core::text::escaped_len`; функция экранирования перенесена из `za-agent` в `za_core::text`, имена в `za_agent` прежние). Доли 60/40 — совпадения и голова страницы — делит сам `rank_passages`, один раз. Так `digest` приходит в контекст целиком и на окнах 16k–64k, где прежние 60 % `output_limit` (78 КиБ) в 2–8 раз превышали предел слота (9,8–39 КиБ), и слот резал `digest` головой и хвостом, теряя лучшие совпадения из середины страницы.
- **Метка у `digest`** (I1 ревью задачи 8). Слот ставит строку `[untrusted content: …]` первой строкой и `content`, и `digest`: длинный результат модель видит через `digest`, а метка — в первой строке видимого. То же для всех строк слота: `[no checkpoint for this file: …]` и нарушенные постусловия дописываются и к `digest` (у `bash` с длинным выводом теста он есть).

## Поставщик поиска и `web_search`

**Контекст.** CAP-001 требует один настроенный поставщик поиска. Решение заказчика 2026-11-11: поиск только бесплатный. Brave и другие платные поставщики в R1-C2 не входят, вопрос изучается позже (D101, D125). Экземпляр SearXNG пользователь держит сам, обычно на `127.0.0.1` или в локальной сети, и разрешающий список D108 его бы запретил.

**Решение (D111, D125, D126, задача 9).**

- **Трейт** `za_web::search::SearchProvider` (`name`, `endpoint`, `request`, `parse`). Инструмент знает только, как построить запрос и разобрать ответ; HTTP-клиента трейт не получает. Запрос — всегда `GET` на происхождение `endpoint()` через шлюз. Будущий поставщик с ключом добавит метод трейта со значением по умолчанию (заголовок с `SecretString` из `SecretStore`, `ZA_SECRET_*`), не меняя `web_search`.
- **Единственная реализация** — `za_web::search::Searxng`: `GET {base}/search?q=…&format=json` (запрос и фрагмент базового адреса не переносятся, экземпляр под путём допустим), поля `results[].{title, url, content}`. Ключа нет, `za-secrets` не нужен. Формат `json` должен быть включён в настройках экземпляра (`search.formats`), иначе SearXNG отвечает 403 — инструмент вернёт `search provider returned HTTP 403 Forbidden`.
- **Адрес** — только `[web.search] url` глобальной конфигурации (`WebConfig::search_endpoint`). Проект его задать не может (D122): иначе чужой репозиторий открыл бы исключение на свой адрес. Шлюз проверяет адрес при сборке: только `http`/`https` с хостом, без учётных данных, иначе `WebError::Config`. Без адреса поставщика нет: `WebGateway::search_endpoint()` — `None`, бинарник `web_search` не регистрирует, `doctor` об этом сообщает (задача 14).
- **Исключение фильтра адресов (D126)** привязано к методу, а не к адресу. Его даёт только `WebGateway::get_provider`, и зовёт его только `web_search`:
  - **сверка происхождения.** Схема, хост после `normalize_host` и порт `url` должны совпасть с настроенными. Иначе отказ `blocked: not the configured search provider` до соединения, с записью `blocked`. Тот же хост с другим портом или схемой, `localhost` вместо `127.0.0.1` — отказ. Порт вне `[web] ports` допустим: экземпляр обычно слушает 8888;
  - **второй клиент.** Он строится в `gateway.rs` той же функцией, что клиент страниц (`build_client`): `no_proxy()`, `Policy::none`, без `Referer`, без cookie и сжатия. Его резолвер `ProviderResolver` разрешает только настроенный хост — системным резолвером, в любые адреса, в том числе частные. Любому другому имени он отказывает до обращения к DNS. IP-литерал из конфигурации резолвер не видит, `reqwest` подключается к нему как есть. Это второй слой: сверка происхождения уже не пускает другие хосты к клиенту поставщика;
  - **без перехода.** Любой ответ 3xx — ошибка `search provider redirected; not followed`, второго запроса нет;
  - **`robots.txt`** не запрашивается: это API своего экземпляра;
  - **пределы.** Лимитер частоты общий с `web_fetch`. Ответ — до 1 МиБ (`PROVIDER_MAX_BYTES`), больше — ошибка без разбора. Запрос — не дольше 20 с (`PROVIDER_TIMEOUT`) и не дольше дедлайна вызова;
  - **журнал.** Каждый запрос и отказ — запись `NetRequest`, затем событие `web.request` из слота. Текст запроса виден в `url` и проходит маску секретов.
- **`get` (`web_fetch`)** на тот же адрес идёт через полный фильтр и получает `blocked: local or private address`, подключения нет. Ссылки из выдачи открываются только `web_fetch`.
- **Инструмент** `web_search(query, count?)` (D111, D123):
  - контракт: `Read`, `ReadOnly`, `Network`, `standard`, 30 с, 32 КиБ, `tainted`;
  - `query` — непустой, до 400 символов. `count` — целое от 1, по умолчанию 8. У схемы нет `maximum`: значение больше 20 инструмент обрезает до 20 сам;
  - выдача — строки `N. <title>`, `   <url>`, `   <snippet>`; пусто — `no results`;
  - у описаний и заголовков сняты HTML-теги (линейно: `<` без `>` дальше остаётся текстом) и раскрыты основные сущности;
  - каждое поле сведено в одну строку (`one_line`, общий с `title:` у `web_fetch`): чужой текст не подделает строки выдачи. Описание — до 300 символов, заголовок — до 200;
  - адрес результата — только абсолютный `http`/`https` не длиннее 2048, в записи `url`; иначе результат пропускается;
  - ошибки: `search provider unavailable: <причина>` (сеть, тайм-аут), `search provider returned HTTP <код> <фраза>`, `search provider returned an unreadable response: <причина>`;
  - метка `web` у любого результата, в том числе ошибки. Первая строка — `[untrusted content: web]`, её ставит слот (D110).
- **Правила по домену** к поиску не применяются (D105): `Subjects::hosts` пуст, `hosts_unknown = false`. `deny domain="*"` поиск не останавливает, выключить его можно только `[web] enabled = false`.
- **Тестовый крюк** `WebGateway::provider_client_get_for_tests` — запрос клиентом поставщика без сверки происхождения. Он проверяет второй слой (резолвер отказывает другому имени) и существует только с признаком `test-hooks` (D128). `with_test_resolve` подменяет у резолвера поставщика только поиск адреса настроенного имени: другим именам отказ остаётся и при подмене. Тесты — `crates/za-web/tests/search.rs` (`required-features`): поддельный SearXNG на `127.0.0.1:0`, настоящего интернета нет.

**Принятые риски.**

- **Доверие экземпляру.** Агент доверяет экземпляру SearXNG ровно как адресу, который пользователь вписал в свою конфигурацию. Экземпляр сам ходит в интернет и может быть настроен как угодно. Его выдача — недоверенное содержимое с меткой `web`.
- **Частный адрес по имени.** Если имя из конфигурации указывает на частный адрес или DNS ответит частным адресом, клиент поставщика подключится. Исключение действует только для этого имени и только для `GET` запроса поиска.
- **Текст запроса** уходит экземпляру и в журнал (через маску секретов). Что экземпляр делает с запросом дальше (передаёт движкам), агент не контролирует.

## Извлекатель

**Контекст.** Разборщики HTML и PDF получают враждебные данные, и в процессе агента у них три вида отказа, которые изнутри не перехватываются:

- **Переполнение стека.** `htmd` 0.5.6 обходит DOM рекурсивно. Около 2 МиБ вложенных `<span>` (≈ 350 000 уровней) переполняют стек потока. Переполнение стека в Rust не паника: `catch_unwind` его не ловит, процесс завершается целиком.
- **Квадратичное время.** Проверка «элемент в области видимости» у `html5ever` при вложенных `<div>` растёт с глубиной: в release 64 КиБ разбираются за 0,43 с, 256 КиБ — за 9 с, 2 МиБ — минуты. Реконструкция активных элементов форматирования (`<p><b id=N>x</p>`) разрастает дерево: 32 КиБ входа дают 1,6 млн узлов. Слияние соседних одинаковых строчных элементов у `htmd` (`Vec::remove` в цикле) квадратично по числу детей: серии по 5000 `<b>x</b>` на 2 МиБ — 11 с. Замеры — журнал, 2026-11-16, задача 7 и её ревью.
- **Паники и вечные циклы** у разборщика PDF на битых данных (D113).

Поток зависшего разбора нельзя убить извне. Отдельный процесс снимает все три вида отказа архитектурно; тайм-аут 10 с остаётся жёсткой границей. Чтобы страница, которая иначе упёрлась бы в этот тайм-аут, всё же дала текст, разбор HTML идёт под онлайн-стражем (ниже).

**Решение (D113, D127).** Все разборщики враждебного содержимого собраны в крейте `za-extract`. Его функции вызываются только в подпроцессе `zero-agent extract <html|pdf>` через `za_jail::Runner`: `EnvMode::Clear`, `tmp_dir` — `work_dir("tmp")/<run>`, тайм-аут и предел вывода. Падение, переполнение стека и зависание убивают только подпроцесс, инструмент получает ошибку (`is_error`), процесс агента продолжает работу.

- **HTML** (задачи 7, 10): UTF-8 до 2 МиБ на stdin, в stdout — JSON `Markdown {title, text}` той же формы, что `za_core::extract::Markdown`; тайм-аут 10 с, вывод до 4 МиБ; сбой — `html: extractor failed: <причина>`.
- **PDF** (задача 10): `extract pdf <path> <first> <count> <max_chars>`, тайм-аут 30 с, вывод до 16 МиБ.
- **Направления** (`cargo xtask policy`): `za-extract` не зависит от крейтов workspace ни в каком виде, от него зависит только `zero-agent`. Прямая зависимость от `htmd`, `html5ever`, `markup5ever_rcdom` есть только у `za-extract`. `za-web` HTML не разбирает: он определяет тип и кодировку и передаёт HTML извлекателю (трейт `Extractor`, задача 8).
- **Тип и кодировка** (`za_web::convert`, D109) определяются строго:
  - тип — по `Content-Type`; без заголовка — по сигнатуре в начале тела после BOM и пробелов (`%PDF-`, `<!doctype html`, `<html` целым именем тега), иначе `text/plain`;
  - кодировка — BOM, затем `charset` заголовка, затем `<meta>` (только у HTML, в первых 1024 байтах, без закомментированных), иначе UTF-8; декодирование с заменой;
  - `Content-Encoding`, отличный от `identity`, — ошибка без распаковки. Правило имени кодирования у шлюза и `convert` общее.
- **Преобразование** (`za_extract::html_to_markdown`, D109):
  - вход длиннее 2 МиБ обрезается по границе символа до разбора;
  - в текст не попадают служебные и встраиваемые элементы `head`, `title`, `script`, `style`, `noscript`, `template`, `svg`, `canvas`, `iframe`, `object`, `embed` и элементы управления формы `input`, `select`, `option`, `button`, `textarea` (I1 ревью задачи 7). `form` в списке нет: страница ASP.NET WebForms целиком обёрнута в один `<form>`, и её пропуск стёр бы весь текст — пропускаются только сами элементы управления;
  - заголовок — текст первого `<title>` пространства имён HTML в порядке документа, пробелы схлопнуты, без экранирования Markdown; `<title>` внутри SVG заголовком не считается;
  - картинки с адресом `data:` отбрасывает обработчик элемента `img`, а не замена по тексту;
  - серии пустых строк сжимаются в одну;
  - собственный обход дерева (поиск `<title>`) — без рекурсии.
- **Страж разбора** (D127, ревью задачи 7; проход fix-9) ограничивает сам алгоритм, а не только тайм-аут. Вход подаётся `html5ever` кусками по 16 КиБ; обёртка над `RcDom` (`TreeSink` делегированием) считает события самого разборщика и при превышении порога прекращает разбор на первых килобайтах, до квадратичного разрастания:
  - созданные элементы — не больше 600 000;
  - глубина вставленного элемента — не больше 256, сумма глубин — не больше 2·10^7. Глубина — настоящая, на момент вставки: подъём по указателям `parent` самого `RcDom`, поэтому учтены и перенос из таблицы (foster parenting), и пересадка детей алгоритмом усыновления; содержимое `template` считается от самого шаблона (m1 повторного ревью fix-7). Модели построителя у стража нет;
  - длина поисков узла среди детей родителя — не больше 2·10^8 (проход fix-9). `RcDom` ищет место вставки линейным проходом при каждом переносе из таблицы и при `remove_from_parent`: поток элементов, перенесённых из одной таблицы (`<table><i></i>…`), стоил квадратично — 2 МиБ ≈ 11 с в release. Найдено в проходе fix-9 при работе над m1; на семи реальных страницах счётчик — 0.

  Перед `htmd` — один проход по готовому DOM: точная проверка максимальной глубины (рекурсия `htmd` переполняет стек) и слияние соседних одинаковых строчных элементов (`za_extract::merge`, I1 повторного ревью fix-7). `htmd` 0.5.6 сливает их сам квадратично: на каждом слиянии `Vec::remove` и копия всего накопленного текста (`push_tendril` → `make_owned`), серия из r элементов с текстом длины L — ≈ L·r²/2 байт (L = 40 на 2 МиБ — 13,3 с). Порогом это не лечилось — цена зависит от длины текста. Слияние теперь делаем мы, за линейное время: правило — копия `can_combine` (с `template_contents` и признаком MathML), сравнение с головой серии, как у `htmd`; дети `ol` не трогаются, потому что `htmd` обходит их напрямую, без слияния. После прохода `htmd` сливаемых пар не находит, итог преобразования тот же (модульные тесты на парах «с предварительным слиянием» и «без», байт в байт на семи реальных страницах). Порог цены слияния удалён.

  Пороги — по замеру рецензента (`.tmp/review7-bench.log`; на обычных страницах максимум — глубина 37, сумма 1,5·10^5, элементов 34 тыс.). При превышении текст извлекается линейно, токенизатором без построителя дерева (сущности и raw-text разбираются верно, ссылки и разметка опускаются), результат несёт признак `simplified`, а `web_fetch` ставит в шапку строку `[simplified extraction: …]`. Линейное извлечение ведёт стек открытых пропускаемых элементов (I2 повторного ревью fix-7): пустые элементы (`input`, `embed`) и самозакрытые теги в стек не попадают, закрывающий тег снимает стек до своего имени, `head` закрывается первым элементом тела или текстом, `option` — следующим `option` и закрытием `select`, глубина стека — не больше 64. Прежний счётчик застревал на `<input>`, и от Википедии оставалось 15 байт; теперь линейный путь сохраняет 89–99 % слов полного пути на семи реальных страницах. Худший случай в release — около 0,5 с (2 МиБ тегов ровно по 1024 атрибута — полный разбор; «Noah's Ark» — 0,42 с), остальные классы — 0,03–0,32 с (замеры прохода fix-9, журнал).
- **Предел атрибутов тега** (`za_extract::attrs`, Ruling прохода fix-7, проход fix-8). Проверка повтора имени атрибута в токенизаторе `html5ever` квадратична по их числу в одном теге (один тег `<div a0 a1 …>` на 2 МиБ — ≈ 75 с), а событие `create_element` приходит уже после токенизации всего тега, поэтому страж по событиям её не видит. До токенизатора — линейный байтовый проход: модель состояний тега WHATWG (§13.2.5: имя, до и после имени атрибута, значения в кавычках и без, после значения, `/`) считает начала атрибутов, включая повторы. Переключений построителя дерева (raw text у `script`, `style`, `textarea`; CDATA в SVG; комментарии) байтовый проход сам не знает, поэтому ведёт множество возможных состояний: гипотеза «вне тега» есть всегда, каждый `<` с буквой открывает ветку тега, ветки в одном состоянии сливаются с наибольшим счётом. Настоящее состояние токенизатора всегда среди веток — счёт верхняя граница при любом поведении построителя: кавычка в `<script>` не прячет следующий тег, `>` в значении в кавычках счёт не обнуляет. Рядом идёт детерминированная модель токенизатора (данные, теги, комментарии по WHATWG, DOCTYPE, raw text; проход fix-9, Ruling прохода fix-8). Где она точно знает, что токенизатор в raw text — содержимое `script`, `style`, `textarea`, `title`, `xmp`, `iframe`, `noembed`, `noframes`, `noscript` (при `scripting_enabled`) и `plaintext` в HTML, — ветки по нему не идут и новых не открывают. На `>` открывающего тега ветки сбрасываются, с `<` подходящего закрывающего тега (`</script` и пробел, `/` или `>`) идут снова: атрибуты закрывающего тега токенизатор тоже собирает. Где построитель raw text не включает или модель не может проследить токенизатор, она до конца входа уступает веткам: `<svg>` и `<math>` (иностранное содержимое: `script`, `style`, `title` там не raw text), `<frameset>` (построитель пропускает `<script>`), `<col>` после `<template>` (режим «in column group» в шаблоне пропускает `<script>`), `<!--` внутри скрипта (после `<!--<script>` первый `</script>` скрипт не закрывает). Больше 1024 атрибутов в теге — линейное извлечение и `simplified`. Вход линейного извлечения проходит `sanitize`: перед символом, который начал бы атрибут сверх 64, вставляется `>` — он закрывает тег во всех состояниях начала атрибута, а в raw text, комментарии и значении в кавычках остаётся обычным символом (удаление символов съело бы `</script>` и весь текст после скрипта). Замеры в release (2 МиБ): тег с ≈ 2,8·10^5 атрибутов — `simplified` за 31 мс (было ≈ 75 с); тысяча разных атрибутов и поток повторов — 33 мс; атрибуты с `">"` после кавычки в `<script>` — 35 мс; 2 МиБ тегов ровно по 1024 атрибута — полный разбор за 0,5 с; сам проход — около 30 мс на 2 МиБ. Суммарного предела по всем тегам нет: при `k ≤ 1024` худший случай — 0,5 с, а сумма по модели ложно срабатывала бы на тег-подобном тексте больших скриптов (страница со 100 атрибутами на тег, разбор 124 мс, уже превышала бы порог 2·10^7).

**Цена.** Запуск процесса — около 20–50 мс на страницу, для `web_fetch` несущественно. Страж и слияние на обычных страницах накладных расходов не добавляют (разбор 11–110 мс на синтетических фикстурах до 1,5 МиБ, 2–55 мс на семи реальных страницах).

**Принятые риски.**

- **Память подпроцесса не ограничена**: бомба декомпрессии в PDF или огромное дерево DOM может занять RAM машины. Предел — Job Object с `JOB_OBJECT_LIMIT_PROCESS_MEMORY` и `RLIMIT_AS` через `za-jail`, R2.
- **Тег с сотнями тысяч атрибутов больше не принятый риск** (Ruling прохода fix-7): его ловит предел атрибутов тега до токенизатора (раздел «Решение», проход fix-8). Тайм-аут подпроцесса 10 с остаётся жёсткой границей для квадратичных классов, которые ещё не найдены.
- **Ложное упрощение из-за тег-подобного текста в скриптах — только там, где модель raw text уступает веткам** (проход fix-9). В HTML содержимое raw-text элементов подсчёт пропускает так же, как токенизатор: скрипт с `i<n` и тысячами «слов» без `>` или массивом данных графика страницу больше не упрощает. После первого `<svg>` или `<math>`, `<frameset>`, `<col>` в шаблоне или `<!--` внутри скрипта модель до конца входа уступает веткам, и прежняя цена верхней границы остаётся: скрипт после `i<n` с больше чем 1024 «словами» без `>` уводит страницу в упрощённое извлечение (текст без ссылок, с пометкой `[simplified extraction: …]`). Выход из иностранного содержимого модель не отслеживает: `</svg>` построитель может пропустить (например, внутри `foreignObject`), и тогда `<script>` после него — снова SVG; ошибка в эту сторону прятала бы настоящий тег. В обычном коде `>` встречается через строку-другую (`=>`, сравнения, строки HTML), минифицированный код без пробелов атрибутов почти не даёт; корпус страниц задачи не упрощается.
- **Двоичные данные под `text/html` или текстовым типом** декодируются с заменой: тип берётся из заголовка без угадывания (D109). Ответ «нет читаемого текста» даёт `web_fetch` (D110, задача 8; раздел «Инструмент `web_fetch`»): это проверка доли символов замены, а не эвристика типа.
