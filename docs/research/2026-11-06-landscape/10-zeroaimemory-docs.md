## 1. Моменты жизненного цикла и порядок действий агента

### Takeaway
Память ждёт девять моментов: старт, запрос, перед действием, после действия, ошибка, запуск субагента, остановка, сжатие, конец сессии. Каждый момент есть и как хук, и как явный вызов: «всё, что делают хуки, доступно вызовами MCP». Значит zero-agent может реализовать их нативно, но часть логики хуков живёт в клиенте `zam`, а не на сервере, и её придётся перенять или вызывать.

### Cited Findings

**Принцип.**
- Ядро (REST, MCP, CLI) одно для всех, события агента — тонкие адаптеры; где события нет, та же функция идёт через MCP и инструкцию «с меньшей гарантией срабатывания» — gaps §4 «Принцип агентонезависимости»; ТЗ §10.4.
- Зачем нужна проактивность: «Агент не знает, чего он не помнит»; напоминание работает «в момент действия», а не в начале — ТЗ §10.1; gaps §5.
- Основные моменты: старт сессии, каждый запрос, перед действием над файлом или командой, после ошибки — ТЗ §10.1.
- Анти-цель: хук больше 300 мс на событие или мусор в контексте — провал — ТЗ §2.3.

**Порядок по моментам.** Бюджеты взяты из ТЗ §10.3 (L1062+) и относятся к хукам.

**Логика, которая живёт в клиенте, а не на сервере.** Это важно для нативного клиента.
- Кэши `triggers.json`, `file-refs.json`, `shown-<сессия>.json`; журнал `events-<сессия>.jsonl`; очередь `changed-<сессия>.jsonl`; учёт локальных токенов `tokens-<сессия>.jsonl` — ТЗ §10.3, §10.7, §10.8.
- `err_fp` (blake3 нормализованной ошибки), детектор пары ошибка → исправление и петель — ТЗ §10.7.
- Экстрактор карты кода (tree-sitter) работает **только в клиенте `zam`**; символы и `body_hash` считает он — ТЗ §7.12, §10.7.
- Снимок разбирается в адаптерах `zam`, сервер знает только нейтральный формат — M6 §8а.
- Срабатывание хуков воспроизводимо извне: «хуки — бинарником `zam hook <событие>`: JSON события на stdin, stdout как `additionalContext`». Так работает eval — M6 §3.1.

### Inferences
- У zero-agent три пути: (а) звать `zam hook …` как подпроцесс, подавая JSON в формате Claude Code; (б) переписать клиентскую логику; (в) смешанно: нативно REST для сервера, `zam code sync` и `zam refs check` как подпроцессы. Путь (в) выглядит самым дешёвым: совпадение `body_hash` и `err_fp` с `zam` не придётся поддерживать вручную. Решение за автором спецификации.
- Порядок «очередь файлов → file-refs → recall» значим: иначе индекс придёт без свежей устарелости. В нативном старте это стоит закрепить как инвариант.
- `next_step` — главный артефакт передачи. Автоматическое обновление `next_step` харнессом при каждом завершённом шаге плана дало бы то, что хук только напоминает сделать.

### Gaps
- Полный порядок разделов дайджеста собран из нескольких мест ТЗ: строка L1090, где он описан, была усечена при чтении. Сверить с `arrange()` в `api/recall.rs` (зона `01-zeroaimemory-contract.md`).

## 2. Правила хорошего использования: что писать, куда и когда искать

### Takeaway
Запись всегда явная и делается агентом; сервер не содержит LLM. Каждому виду знания отведён свой журнал со своими правами. Главные правила: искать до работы, писать сразу после вывода, не удалять, а замещать, различать слова человека и выводы агента.

### Cited Findings

**Запись или поиск.**
- Автоматическое извлечение памяти из диалогов — не-цель v1; запись всегда явная, через инструменты — ТЗ §2.2. LLM-наблюдатель сознательно отвергнут как источник шума — review §5.
- Сервер ищет и хранит, выжимку делает агент (G9) — ТЗ §2.1, §9.5.
- Поиск идёт четырьмя шагами, каждый следующий — только если не хватило предыдущего: кэш (~100–400 токенов), карточки (~30–50 на штуку), точечное чтение, сохранение выжимки до 600 токенов — ТЗ §9.3.
- Перед новым поиском по той же теме — сначала кэш — ТЗ §9.3.
- `sources` выжимки — только то, на чём она реально основана; инвалидация автоматическая — guide стр. 19. Кэш работает между сессиями и общий на решение; чужая выжимка помечена автором — ТЗ §9.3, §9.4, §21 п. 6.
- Семантическое попадание в кэш — косинус ≥ 0,92 — ТЗ §9.4.

**Карта видов записи.**

| Что произошло | Куда | Правило | Источник |
|---|---|---|---|
| Ловушка, сбой | `insight` `gotcha`/`failure` с триггерами | Триггеры дают проактивный показ; без них запись находится только поиском | ТЗ §7.5, §14.2 |
| Эксперимент | `insight` `experiment` с `result`, `revisit_if` | Проверяется перед исследованием | ТЗ §7.5 |
| Изменение проекта | `changelog` (feat, fix, refactor…) | Только дописывается; это не ревизии заметок | ТЗ §7.3 |
| Решение | `insight` `decision` с `data.decision` (ADR) | `decided_by: human\|agent`, `revisit_if` | guide стр. 90–93 |
| Отвергнутый подход | `insight` `decision` или `failure` | «Сжатие контекста эти подробности теряет первыми» [план: правило войдёт в guide] | M6 §13 |
| Знание не о проекте | `scope: global` → Knowledge | Сценарий CRLF | ТЗ §1.1, §7.1 |
| Понятие проекта | `term` | Пиши каноническим именем; псевдоним даёт `warnings` | ТЗ §7.7 |
| Работа | `task` | `claim`, `status`, `next_step`; в поиске только явным `kinds: [task]` | ТЗ §7.8 |
| Вопрос человеку | `question` | Копить, не дёргать; дубль даёт 409 с ответом в `candidates` | ТЗ §7.9 |
| Ответ человека в чате | `answer` с `by: human`, `channel: chat` | Даёт `decision` с `axiom`. `by: agent` — `hypothesis`. Не приписывать человеку свой выбор | guide стр. 62–66 |
| Замысел человека | `idea` `origin: human` | Только по диктовке | §2 «Идеи» ниже |
| Своя мысль на будущее | `idea` `origin: agent` | Не предлагается, пока человек не примет | ТЗ §7.13 |
| Итог для человека | `report` | Агент отчёты не читает; выводы для себя — отдельно в `insight` | ТЗ §7.11; guide стр. 46 |
| Проверенная команда | Заметка с `verified_at`, `verified_at_commit` | Дайджест покажет до 3 | ТЗ §7.10 |
| Хост, стенд, секрет | Vault | В заметки не копировать | guide стр. 127–131 |
| Устарело | `supersede` или `retract` с причиной | Не удалять и не править молча | ТЗ §7.5 |

**Жизненный цикл и доверие к записи.**
- `status` (`active`, `revisit`, `superseded`, `retracted`) — жизненный цикл; `certainty` — степень доверия. Это разные поля — ТЗ §3, §7.5.
- `hypothesis` — умолчание у агента; `theorem` требует `evidence {checked, method, result}`; смена `certainty` агентом — с `reason` — ТЗ §7.5.
- `axiom` — только по прямому указанию пользователя. Сервер это **не проверяет**, правило «на совести агента» — ТЗ §7.5; install «Известные ограничения».
- Не согласен с аксиомой — запиши `hypothesis` или `theorem` со связью `contradicts` и скажи пользователю — guide стр. 92–94.
- Дедупликация при записи: косинус ≥ 0,90 или тот же нормализованный заголовок даёт 409 с кандидатами; варианты: дописать, заменить, `force` — ТЗ §7.5.
- 409 и 428 значат «перечитай и повтори» — guide «Запись»; ТЗ §11.3.
- Каждой заметке — `l0` — guide стр. 25.
- Оценка полезности: `feedback useful|useless`; шумные записи видны в WebUI — ТЗ §10.5.

**Рабочая память и долговременная.**
- Память «хранит знания, но не „где я остановился“» — поэтому появился M4.5 — gaps §2.1. Задачи, вопросы и журнал сессии держат состояние работы; insights и заметки держат знание.
- Журнал сессии — только метаданные, текста нет — ТЗ §10.7. Исключение M6 — снимок на сервере — M6 §8а [план].
- Журналы привязаны к решению, а не к сессии; сессия — атрибут записи — ТЗ §7.2.

**Идеи.**
- Идея — то, что человек хочет, но не запустил: нет плана, `next_step` и захвата — ТЗ §7.13.
- Агент предлагает **одну** идею через `propose`; сервер задаёт вопрос «начать / отложить / отказаться»; «без ответа „начать“ не начинай» — guide стр. 75–77.
- `accept` одной транзакцией создаёт `task` со связью `derived_from`; задача `done` закрывает идею — ТЗ §7.8.
- Идею человека токен не переписывает: только `append` — ТЗ §7.13.
- Раздел `### Идеи` — до 3, только первый старт, только решение; общие идеи Knowledge — при связи с задачей `in_progress` сессии или по просьбе — ТЗ §10.3; ideas §6. Одна идея — один показ за сессию, это сохраняется и при новых эпохах — M6 §7.2.

**Документы.**
- Загрузка: `zam attach <путь-заметки> <файл>` или `POST /blobs`; вложение привязано к заметке; лимит 200 МБ — ТЗ §6.5, §12, §13.2.
- Извлечение асинхронное, у вложения есть `extract_state` — ТЗ §13.2.
- Чтение: `a:` фрагмент, `b:` по sha256, `d:` вложение, `locator` (`page:12`, `slide:3`, `sheet:…`, `para:40`), без `locator` — оглавление — ТЗ §9.3.
- Ищи с `filters.kinds = ["attachment"]`, когда нужен именно документ: recall@5 0,73 в общей выдаче против 0,98 среди вложений — install «Известные ограничения».
- Нет OCR; DOC, PPT, XLSB не разбираются — install.

**Карта кода.**
- Детерминированный индекс символов; символы не входят в поиск памяти, подсказки и кэш — ТЗ §7.12.
- Привязка знания: `refs.files` на файл или `путь#Тип::метод`; символьная ссылка устаревает только при изменении тела символа — guide стр. 112.
- Устаревшее: сверил — `zam refs verify`, неверно — `supersede` — guide стр. 100.
- Тела кода на сервер не уходят; сигнатуры уходят, отключаются `code.send_signatures` — guide стр. 115.
- Одна карта на решение, «последний снимок побеждает» пофайлово — ТЗ §7.12.
- **Ранжирование слабое:** критерий ≥ 6/10 ключевых типов в центре не выполнен, факт 1/10 — README (M5.6); journal 2026-11-03. Правка запланирована — M6 §12а [план].

### Inferences
- Все правила, кроме структурных проверок (`evidence`, `reason`, `by` обязателен), держатся на дисциплине модели. Харнесс видит реальные ходы пользователя, поэтому может сам проставлять или проверять `by: human` и разрешение на `axiom`. Это прямое усиление по сравнению с блоком инструкции.
- Подсказки к запросу берутся только из insight и Rules: заметки Knowledge и решения в них не попадают (ТЗ §10.3, L1091). Знание, которое должно всплывать само, нужно оформлять как insight с триггером.

### Gaps
- В `guide.ru.md` нет раздела о вложениях; поведение агента с документами выведено из ТЗ и install.
- `pattern` есть в схеме `kind` у insight (ТЗ §7.5, L525), но не упомянут в guide. Намерение авторов по этому виду не описано.

## 3. Модель экономии токенов (M6)

### Takeaway
Принцип владельца: **качество важнее токенов**. Цель −30 % на первом обращении, скорее всего, не будет достигнута и это допустимо: оценка −9…−19 %, до −35…45 % при явном `focus`. Большая часть выгоды M6 приходит сама, но `focus`, явная сессия и соблюдение четырёх шагов — на стороне агента.

### Cited Findings

**Принцип и цель.**
- «Качество важнее токенов»; при недостижении 30 % выдача не урезается, а записывается факт — M6 §0.
- База агентного вида ≈ 3000 токенов на сценарий: `brief` ≈ 1083, `read` ≈ 1878, `cache put` ≈ 52. Историческое 3725 содержало эхо REST, которого агент не видит — R-M6 §5; M6 §3.3.
- Ожидание: R ≈ 0,81–0,91; при рекомендованном `focus` — оценка до −35…45 % (оценка, не замер) — R-M6 §5.
- Замер M4: протокол на первом обращении дороже наивного пути, 120,6 %. Дорого чтение L2 целиком, а не поиск — review §4.

**Что меняется в выдаче.**

| Механизм | Суть | Статус | Источник |

**Что должен делать агент.**
- Держать **явную сессию**: при неявной нет ни пометок, ни отметок, учёт уходит в `unattributed` — M6 §7.1.
- Звать `focus`, когда модель дорогая, запись длинная (`~T` > около 600) и нужен один факт; иначе L2 — M6 §6.
- Читать пачкой, не перечитывать, смотреть на `~N tok` — ТЗ §9.3.
- Читать изменения через `since_rev`, а не целиком — ТЗ §9.3.
- Сохранять выжимку: повтор через кэш стоит 100–400 токенов — ТЗ §9.3.
- Держать бюджет явно: `budget_tokens` есть у поиска, чтения и карты кода.

**Как измеряется.**
- **Что считается:** текст, который реально получил агент, токенизатор bge-m3; полнота — по нагетам, дословным фрагментам из источника — M6 §2, §3.2.
- **ТС-1:** ≥ 45 сценариев (набор 48) через MCP против B4. **ТС-2:** ≥ 12 сессий хуков и MCP против B5.6 — M6 §3.1; `eval/README.md`.
- **Симулированный агент:** без LLM, оракул выбора источников, дочитывание по маркерам обрезки — M6 §3.4.
- **Статистика:** `R = Σ M6 / Σ база`, парный бутстреп 10 000; неинфериорность Δ полноты ≥ −0,02, чистые потери `L ≤ 1`; dev ⅔ и holdout ⅓ по хэшу id; правило выбора записано до прогона — M6 §3.5.
- **Приёмка:** верхняя граница R < 1,00 обязательна, R ≤ 0,70 — цель. Обязательные строки дайджеста — 1,0 — M6 §17 п. 1–2.
- **Живой A/B:** `cargo xtask ab` читает поля `usage` транскриптов Claude Code; плечи memory/off, map/nomap, impact; владелец запускает ≥ 10 задач × 2 × 2 после финализации; приёмку не блокирует [план, 12] — M6 §12, §15 п. 17.
- **Контрольная группа:** `hooks.holdout` (0…0,5, по умолчанию 0): «тихие» сессии с пустым `/recall`, субагент наследует метку [план, 12] — M6 §12.
- **Подсказки:** `hint_recall`, `hint_precision`, `silence_rate` на `hints.toml` ≥ 120 случаев — M6 §9.
- Итоговые умолчания выберут сетки: `search.budget_tokens` {400, 600, 800}, `recall.digest_tokens` {800, 1000, 1500}, `recall.recovery_tokens` {1200, 1500, 2000}, `recall.brief_tokens` {500, 800}. Калибровка на реальной задаче — после M7 — M6 §3.5, §8, §0.

**Кэш провайдера.**
- Блок и описания MCP лежат в стабильном префиксе; дайджест — первое сообщение после него. Каждый выданный токен остаётся в истории до сжатия. «Главный рычаг — объём каждой выдачи, а не порядок» — R-M6 §2.5.

### Inferences
- Числовые умолчания M6 нельзя жёстко вписывать в спецификацию zero-agent: они определятся на holdout. Брать их надо из конфигурации сервера или передавать свои `budget_tokens`.
- Zero-agent сам знает цену модели и фактический `usage` на ход, поэтому может автоматизировать правило `focus` и мерить экономию честнее, чем bge-m3-оценка. Но `xtask ab` понимает только транскрипты Claude Code; для участия в том же A/B потребуется совместимый вывод или свой отчёт.
- Детерминированный дайджест стоит класть туда, где он не ломает кэшируемый префикс; авторы сами считают выигрыш небольшим (R-M6 §2.5: TTL короче интервала между сессиями).

### Gaps
- Фактических R и итоговых умолчаний M6 ещё нет: приёмка не проведена.

## 4. Многоагентная модель: личность, проекты, общая и личная память, конфликты, доверие

### Takeaway
Единица личности — **пользователь с токеном**, а не агент. Агенты различаются только атрибуцией: сессия, машина, тип агента. Конфликты решаются оптимистическими блокировками и явными связями, а не автоматикой.

### Cited Findings

**Личность.**
- Человек — это сессия WebUI; любой токен — агент (`author_kind = agent`). Токенов с правами человека нет — ТЗ §11.4.
- Токен открывает всю память пользователя, кроме Human, включая Vault, и одобренные общие решения — ТЗ §11.4.
- Токен имеет режим `rw` или `ro`; действующее право — пересечение режимов токена и участника — ТЗ §11.6.
- Атрибуция: `X-Zam-Session`, `X-Zam-Machine`, `X-Zam-Area`; ревизия хранит `user_id`, токен, сессию, машину — ТЗ §11.3, §11.6, G6.
- Сессия субагента: `<session>:<agent_id>`, `parent_id`, `agent_type` — ТЗ §6.3; M4.5 §9.4.

**Проект.**
- Решение идентифицируется GUID `agent_solution_id` в `.zeroaimemory/solution.toml`; файл коммитится; все клоны с GUID делят память — ТЗ §11.1.
- Подкаталог объявляет область `.zeroaimemory/area.toml`; поиск идёт по всему решению с бустом области; `scope.area` ограничивает строго — ТЗ §11.2.
- Первый зарегистрировавший — владелец; чужой GUID создаёт запрос доступа, ответ 202 `pending`, запись 403 — ТЗ §11.1, §11.6.

**Общее и личное.**

| Пространство | Агент | Индекс | Участнику общего решения |
|---|---|---|---|
| Rules | читает; запись — только `rules.agent_write` (выкл.) | да | не видно |
| Human | **нет доступа** | только FTS для WebUI | не видно |
| Knowledge | читает и пишет | да | не видно, подмешивается только свой |
| Solution | читает и пишет | да | видно, `rw` или `ro` |
| Vault | личный, раскрытие в аудите | не в векторах | у участника свой, привязан к GUID |

Источник: ТЗ §7.1, §11.6.

- Кэш выжимок общего решения общий; сессии и `session_seen` участника — в его базе, `usage` — в базе владельца — ТЗ §11.6.
- Отзыв доступа действует со следующего запроса, роль читается на каждый запрос — ТЗ §11.6.
- Связи между базами не делаются; общего Vault нет — ТЗ §11.6.

**Конфликты.**
- Заметки: `If-Match`, при конфликте 409 с диффом; `PATCH` по секциям проходит, если секция не менялась после `base_rev` — ТЗ §11.3.
- Журналы: `If-Match` обязателен для `PATCH`, `DELETE` (иначе 428); новые записи только дописываются и не конфликтуют — ТЗ §11.3.
- Запись идемпотентна с `Idempotency-Key` — ТЗ §11.3.
- Смысловые конфликты: `decision_near_axiom` (косинус ≥ 0,80), `contradicts`, `term-conflict`, `possible-duplicate` — ТЗ §7.5, §7.7, §7.9.
- `contradicts` влияет на порядок: запись не стоит выше действующей более надёжной — ТЗ §8.5.

**Доверие.**
- `axiom > theorem > hypothesis` даёт буст; `filters.certainty` и `decided_by` фильтруют — ТЗ §7.5.
- Аксиомы чужого архива при импорте понижаются до `theorem`, `axioms=keep` — явным указанием [план] — M6 §15.

### Inferences
- Если zero-agent нужен отдельный «паспорт» агента (роль, версия, модель), сервер его не выделит: на одного пользователя все агенты равны. Различать их придётся через сессию, `agent_type`, поле `agent` при `claim` и, возможно, отдельные токены одного пользователя.
- Рой из разных ролей на одном токене имеет доступ ко всему Vault. Токенов с областью действия в документах нет, поэтому ограничение Vault — дело харнесса (например, запрет `memory_vault` в профиле роли).

### Gaps
- В документах нет угрозной модели «вредная запись в памяти»: как относиться к тексту из памяти как к данным, а не к инструкции. Есть только совет писать подсказки фактами (events §1). Это остаётся на агенте.

## 5. Передача работы между сессиями и агентами (baton, снимок)

### Takeaway
Основной механизм — состояние, которое ведётся по ходу работы (`task`, `next_step`, `claim`). Снимок сессии из M6 — лишь страховка на случай внезапной смерти. Нативному агенту эта страховка почти не нужна в исходной форме: он может писать состояние сам до смерти.

### Cited Findings
- Вывод разбора baton: почти всё уже есть в более строгом виде, «состояние ведётся по ходу работы, а не восстанавливается задним числом»; новое — журнал сессии агента как бесплатный источник фактов — baton §2.
- Зачем снимок: при лимите или закрытии окна `next_step` мог не обновиться — M6 §8а.
- Что берётся (белый список): конспект сжатия, запросы человека, изменённые файлы, команды. Не берётся: ответы агента, вывод инструментов, файлы, правила проекта, записи субагентов `isSidechain` — M6 §8а.
- Хранение: на сервере, таблица `session_snapshots`, ≤ 16 КиБ, 14 дней, по умолчанию включён, с маскировкой секретов — M6 §8а, §15.
- Доступ: снимок видит только владелец сессии; у участника общего решения — 404 — M6 §8а. Значит передача снимка возможна только между сессиями одного пользователя.
- Показ: «Последнее известное состояние», до 400 токенов; в `recovery` без конспекта; дайджест `startup/clear` берёт снимок другой сессии за 2 суток — M6 §8а.
- Снимок не показывается, если сессия жива (`last_seen_at` моложе 10 мин, нет `ended_at`) или работа продолжилась другой сессией — M6 §8а.
- `brief` субагенту снимка не содержит — M6 §8а.
- Не взято из baton: публичные paste-сервисы, перезапись файлов, фоновая проверка обновлений, копирование правил проекта — M6 §2.
- `zam session snapshot --transcript <файл>` — для агентов без хуков [план] — M6 §8а.

### Inferences
- Нативному агенту незачем парсить свой журнал: он может сразу собирать нейтральный снимок и слать `PUT /sessions/{id}/snapshot`, а перед приближением к лимиту обновлять `next_step` по факту остатка токенов. Формат тела и требование явной сессии — M6 §8а.
- Передача между разными пользователями идёт только через общие сущности решения: `task`, `decision`, `changelog`.

### Gaps
- Формат конспекта сжатия и запросов для «чужого» агента не описан: ядро нейтрально, но поля заданы только разбором Claude и Codex.

## 6. Рой: много субагентов на одной памяти (доп. вопрос заказчика)

### Takeaway
Слова «рой», «шина», «брокер», pub/sub, webhook и подобные в документах не встречаются ни разу (проверка регулярным выражением с границами слов по `docs/specs`, `docs/research`, journal, README, install, guide, `eval/README.md`; единственное совпадение — название события `TeammateIdle` в списке событий Claude Code, events §1). Модель авторов — **один главный агент с редкими субагентами**, а не рой. Опорные примитивы есть (захват задач, ревизии, пакет `brief`), но push, адресации сообщений и заявленного предела писателей нет.

### Cited Findings

**Что есть для субагентов.**
- Причина: субагенты стартуют с пустым контекстом и не получали дайджест; всё пересказывалось вручную — gaps §5.
- `brief`: правила L0, решения `axiom`/`theorem`, термины, ловушки, файлы, `### Код`, бюджет до 800 токенов, повторы не отсекаются, «у субагента свой контекст» — ТЗ §10.7. Без `task` — мини-дайджест с задачами родителя — ТЗ §10.7.
- `brief` не содержит идей и снимка — M6 §8, §8а.

**Личность субагента: известный слабый узел.**
- «Вызовы MCP субагента приходят с сессией родителя: агент не сообщает MCP-серверу, кто зовёт». Учёт идёт в сессию родителя, «это допускаемая неточность» — M6 §7.1.
- Записи субагента через MCP идут в неявную сессию; атрибуция «не гарантируется и в этапе не требуется» — M4.5 §9.4, §14.
- «Пакет субагенту выбирается по типу субагента — при параллельном запуске субагентов одного типа он может достаться соседу той же сессии» — install «Известные ограничения»; механика — M4.5 §9.4.
- Параллельные агенты одного репозитория различаются pid файла привязки — M6 §7.1.

**Координация.**
- Захват: 409 `task-claimed` с `claimed_by`, TTL 1–1440 мин, по умолчанию 120; просроченный снимает кто угодно; чужой живой — только человек; «Захват рекомендательный, он не запрещает правку» — ТЗ §7.8; guide стр. 53.
- Цель захвата — чтобы второй агент видел, что работа уже идёт, и не дублировал — gaps §5 п. 4.
- Захват не создаёт ревизию и не требует `If-Match` — ТЗ §7.8. Гарантия атомарности при гонке двух `claim` в документах явно не описана; один актор-писатель её подразумевает (проверить в коде).
- Статус `claimed_by` содержит `{session, agent, until}` — ТЗ §7.8.
- Изоляция рабочих копий — не функция памяти: «параллельные агенты в одной рабочей копии мешают друг другу (общий git), я разводил их по очереди вручную» — gaps §5.
- Карта кода одна на решение: параллельные ветки перезаписывают друг друга пофайлово, заголовок показывает долю других снимков — ТЗ §7.12.

**Позиция о шине и очередях.**
- Сообщений между агентами нет: регулярные выражения «очередь сообщений», «между агентами», «A2A» не дают совпадений по смыслу. Всё проходит только через опрос (pull) и общие записи.
- Подсказки доходят в момент запроса, дайджеста или хука. «Фоновых заданий нет» сказано про идеи — install «Известные ограничения».
- Устарелость, возникшая внутри сессии, хук видит только со следующего `session-start` — ТЗ §10.7. Поиск и `/read` помечают сразу — install.
- Ответ человека приходит разделом дайджеста, то есть на следующем старте или восстановлении — ТЗ §7.9.
- Офлайн-очередь клиента — v2 — ТЗ §2.2, §19.

**Пределы параллельных писателей.**
- Числового предела одновременных агентов или писателей в документах **нет**.
- На каждый файл SQLite — один актор-писатель; `journal_mode=WAL`; `busy_timeout` 5 с, у писателя 30 с — ТЗ §5.2, §6.3 (L461).
- База одна на пользователя, поэтому все агенты одного пользователя упираются в одного писателя (вывод из ТЗ §6.1, §6.3).
- Для общего решения запись идёт в базу владельца — ТЗ §11.6.
- Большие тела: 2 разрешения `BIG_BODY_PERMITS` на `entries` и `/mcp`; не получено за 500 мс — 503 `busy`, `Retry-After: 2` — ТЗ §7.11.
- Масштаб: до 20 пользователей, 1 млн чанков, 50 ГБ вложений — ТЗ §17.
- Лимит частоты описан только для входа в WebUI и неверных токенов (ТЗ §11.5). Для записи или поиска по токену я лимитов не нашёл. Раскрытие Vault не ограничено намеренно (ТЗ §16.1, L1661).
- Индексация уступает эмбеддингу запросов, на CPU зарезервировано 2 потока — ТЗ §8.1 (L748). Индексация 690–770 токенов/с на CPU — ТЗ §17.
- Хуки молчат при превышении бюджета: на HDD под нагрузкой это штатно — install «Известные ограничения». Параллельная нагрузка уже роняла тесты времени и `hooks::prompt_flushes_changed_queue` — journal M4.5, M5.6, M5.7.
- Риск стоимости: «инъекция в субагентов умножает расход на их число» — review §5.

### Inferences
- Для роя zero-agent может использовать `task` + `claim` с исходом 409 как рабочую очередь: создать задачи, каждый субагент берёт свободную, продлевает `ttl_min`, пишет `next_step`, делает `release`. Это опора, а не заявленный сценарий авторов, нагрузочных гарантий нет. Шину и доставку событий харнесс делает сам и память использует как хранилище фактов.
- Нативный рой устраняет три слабых места: у каждого субагента своё HTTP-подключение и свой `X-Zam-Session` с `parent_id`; задание передаётся в `brief` напрямую, без угадывания по типу; `skip_seen` можно применять осознанно, потому что харнесс знает, что лежит в контексте субагента.
- Чтобы не упираться в одного писателя, стоит собирать записи роя в пачки и избегать частых мелких обновлений. Без нагрузочного замера это гипотеза: спецификации zero-agent стоит заложить свой тест на целевое число писателей.
- Выжимки общие на решение, значит рой экономит: первый субагент платит за чтение, следующие получают `[cache]`. Для этого каждый должен звать `memory_cache_put`.

### Gaps
- Нет данных о пропускной способности записи и поведении при десятках параллельных клиентов.
- Токены с областью действия и сущность «агент» не описаны и не обещаны.

## 7. Общий межпроектный раздел скриптов и утилит (доп. вопрос заказчика)

### Takeaway
Такого раздела **нет и он не запланирован**. Поиск «общие скрипты», «библиотека скриптов», «утилита», `shebang` по документам дал 0 совпадений, `runbook` — одно (gaps §2.6, о командах, а не о скриптах). Контракта, версии языка и понятия «переписать устаревшее» для скриптов в модели нет. Но из существующих частей можно собрать близкий механизм на стороне zero-agent.

### Cited Findings

**Ближайшие существующие части.**
- **Проверенные команды** — заметки с `verified_at`, `verified_at_commit`; заготовка папки «Команды» сознательно не создаётся. Дайджест показывает до 3 заметок **только из пространства решения**, не из Knowledge — ТЗ §7.10; решение владельца 2026-10-28.
- **Knowledge** — «глобальные знания пользователя, общие для всех проектов: инсайты с `scope=global`, приёмы, особенности окружения» — ТЗ §7.1.
- Knowledge не виден участникам общих решений — ТЗ §7.1.
- **Вложения** к заметке: файлы до 200 МБ, адрес по sha256, `_attachments/…` — ТЗ §6.5.
- **Устарелость:** ссылки `refs` следят за файлами только при известном решении; Knowledge без `X-Zam-Solution` — «ссылка справочная, устарелость не отслеживается» — ТЗ §7.10.
- **Карта кода** есть только у решений; Knowledge — 422 — ТЗ §7.12.
- **Возраст:** `age_days` считается от `max(updated_at, verified_at)` — ТЗ §7.10.
- **Замещение:** `supersede` и `retract` есть у журналов, у заметок — ревизии; `revisit` — «пересмотреть при новых идеях» — ТЗ §7.5.
- **Триггеры:** `file_glob`, `command_regex`, `error_regex`, `keyword`; только у insight — ТЗ §7.5.
- **Подсказка к запросу** берёт только insight и Rules; заметки Knowledge в неё не попадают — ТЗ §10.3 (L1091).
- **Экспорт** по префиксу путей `paths=`, импорт zip [план] — M6 §12б.5.
- Кандидат на близость: вид insight `pattern` в схеме (ТЗ §7.5), без описанного намерения.
- У аналога OpenViking есть раздел `skills`, но авторы ZeroAIMemory идею не брали — `docs/research/2026-10-17-01-analogs-agent-memory.md`.

### Inferences
Возможная схема на стороне zero-agent (только предложение, в памяти этого нет):
- Скрипт: заметка `knowledge:/scripts/<имя>.md` с телом или вложением.
- Контракт: секции заметки (вход, выход, побочные эффекты, версия языка) плюс `verified_at`, `certainty: theorem` с `evidence`.
- Проактивность: парный insight `pattern`, `scope: global`, с триггером `keyword` или `file_glob` и ссылкой на заметку, потому что сама заметка в подсказки не попадёт.
- Обнаружение: `memory_search` с фильтром пути или тегом.
- Устаревание: харнесс сам проверяет `age_days` и версию рантайма, при расхождении ставит `revisit` и создаёт `task` на переписывание; новая версия — `supersede` парного insight.
- Логичнее попросить авторов о подсказках из Knowledge и о дайджесте `verified_at` из Knowledge: оба ограничения выглядят настраиваемыми, но требуют правки памяти.

### Gaps
- Сохраняются ли произвольные поля frontmatter заметки, описано не полностью; проверить в контракте.
- Индексируются ли вложения вида `.py` или `.ps1` как текст, нужно сверить со списком форматов M5 (текст упомянут в ТЗ §19, расширения не сверялись).

## 10. Развёртывание и ресурсы, влияющие на агента

### Takeaway
Сервер — отдельный долгоживущий сервис в LAN, один на всех. Агент должен работать без него: всё fail-open, режим деградации до FTS штатный. Офлайн-записи нет.

### Cited Findings
- **Форма:** `zam-server` слушает `0.0.0.0:7700`, Qdrant — дочерний процесс на `127.0.0.1:6333/6334`; без Docker; режим службы Windows и systemd — ТЗ §4.3, §16.2; README «Требования».
- Один экземпляр на каталог данных, файл блокировки — install «Порты и данные».
- **Платформы:** Windows x64 и Linux x64 (glibc 2.35+); arm64 и macOS не поддерживаются — README.
- **Ресурсы CPU:** RSS ≈ 1,4 ГиБ с bge-m3-int8, модель ~0,6 ГБ; реранкер +0,6–0,9 ГиБ; Qdrant ~340 МиБ на 10 тыс. заметок; `ml.unload_after` не реализован, модель всегда в памяти — README; install.
- **GPU:** только NVIDIA CUDA (драйвер R580+), библиотеки ~1,9–2,2 ГБ; без CUDA работает на CPU; `ml.device = auto` — README; ТЗ §8.4.
- **Старт:** штатно ~2 с до готовности векторов, цель ≤ 5 с; после жёсткой остановки во время записи 5–14 с GPU и 14–19 с CPU; поиск в это время из FTS с `degraded: true` — ТЗ §17; install.
- **Задержки (p95, цели):** `recall` с сетью ≤ 250 мс CPU, ≤ 150 мс GPU; поиск ≤ 120/50 мс; поиск в кэше ≤ 30 мс плюс эмбеддинг; `zam` холодный ≤ 20 мс — ТЗ §17.
- **Видимость записи:** FTS синхронно ≤ 30 мс, вектор ≤ 5 с CPU, ≤ 1 с GPU при пустой очереди. Анти-цель: «только что записанное не находится, и агент не знает почему»; есть `pending_count` и `warnings: ["index rebuilding"]` — ТЗ §17, §2.3; install.
- **Без моделей** сервер стартует FTS-only — install «Модели».
- **Сервер недоступен:** хуки молчат, код 0; локальные подсказки по кэшу триггеров работают; `checkpoint` без напоминания — ТЗ §10.3.
- **Сеть:** HTTP без TLS, внешний доступ — прокси — ТЗ §11.5.
- **Токен:** не в файлах проекта; `~/.zeroaimemory/config.toml` или `ZAM_TOKEN` — ТЗ §14.1; install.
- `ZAM_MACHINE` нужен для верной атрибуции машины в MCP — install «Известные ограничения».
- Каталог данных на Windows ≤ 190 символов — install.
- Qdrant Edge отвергнут, архитектура с внешним процессом остаётся: `p95` выигрыш 1,60× при нужном ≥ 2×, RSS в 2,16 раза выше, дефекты WAL — `docs/adr/0001-qdrant-edge.md`.
- Бэкап каталога — при остановленном сервере до M6, `master.key` хранится отдельно — install.

### Inferences
- Zero-agent не должен запускать память сам как часть своей сессии: это общий сервис. Ему нужны проверка `/health`, деградация и локальная очередь записей, потому что офлайн-очереди CLI нет до v2 (исключение — снимок в M6).
- Нужно учитывать задержку между записью и векторной видимостью: сразу после записи искать только FTS-способными словами или читать по id.

### Gaps
- SLA и поведение при обновлении сервера во время работы агента описаны только как последовательность миграций и отката.

## 11. Что нативный харнесс может сделать лучше хуков

### Takeaway
Почти все оговорки документов — следствие того, что хук живёт снаружи агента. Нативный клиент снимает ограничения по времени, по месту вставки текста, по личности субагента, по сжатию и по учёту. Он не снимает только серверные пределы и необходимость держать клиентскую логику `zam`.

### Cited Findings и выводы для zero-agent

| Ограничение хука (источник) | Что может нативный клиент (вывод) |
|---|---|
| Жёсткие бюджеты 50–300 мс, при превышении тишина (ТЗ §10.3; install) | Асинхронный префетч, ожидание по важности, повтор, различение «пусто» и «не успели». Серверный `recall.timeout_ms = 200` останется |
| Текст до 9000 символов, у Codex ~2500 токенов (ТЗ §10.3) | Свои бюджеты в диапазоне API |
| Инъекция только как текст рядом с результатом; писать фактами, иначе защита от prompt injection (events §1) | Структурированный слот контекста со своим уровнем доверия |
| `PreCompact` ненадёжен и без инъекции, `PostCompact` без инъекции (events §1, §5) | Сжатие под контролем: синхронно обновить задачу, снимок, `new_epoch`, затем `recovery` в том же шаге |
| Конспект берётся из журнала, формат не документирован (M6 §8а; baton §4) | Свой конспект в нейтральном снимке, без разбора файлов |

| Субагент неотличим на общем MCP; `seen` не может скрывать (M6 §7.1) | Своё подключение и сессия на субагента, `parent_id`, учёт по каждому |
| Пакет `brief` достаётся по типу, возможна гонка (install; M4.5 §9.4) | Задание передаётся прямо в вызове |
| Смерть сессии ловится страховкой (baton §3) | Знание остатка окна и лимита, запись `next_step` заранее |
| Нет кода выхода в `tool_response` Bash у Claude (contract) | Прямой доступ к коду выхода и выводу, точные пары ошибка → исправление |
| Детектор пары смотрит только на `exe` (ТЗ §10.7) | Семантика своего шага и плана |
| `axiom`, `by: human` на совести агента (ТЗ §7.5) | Проверка по реальному ходу пользователя |
| Стабильность префикса вне контроля (R-M6 §2.5) | Осознанное размещение дайджеста в кэшируемой части |
| Учёт только выданного памятью, оценка по `ApproxCounter` (ТЗ §10.8) | Реальный `usage` провайдера на ход, цена памяти в деньгах |
| Подсказки до действия только локально и по маскам (ТЗ §10.3) | Те же кэши плюс разбор плана до выполнения |

**Что нативность не снимает.**
- Символы и `body_hash` считаются клиентом `zam` (ТЗ §7.12).
- Запись идёт через одного актора-писателя (ТЗ §6.3).
- Нет push.
- Отчёты с файлами больше 16 МиБ через MCP не пройдут; нужен `zam report` или multipart — guide стр. 44.
