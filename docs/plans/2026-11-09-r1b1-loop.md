# R1-B1 «Цикл»: план реализации

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ ПОД-СКИЛЛ: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans, задача за задачей. Шаги отмечаются чекбоксами (`- [ ]`).

**Goal:** рабочий цикл агента поверх журнала и `Gateway`. Run проходит ходы модели и инструментов, переживает `kill -9` и продолжается с того же места. Ошибки модели, очереди и бюджета ставят run на паузу с причиной, а не оставляют его в `running`. Промпты приложения A собираются в стабильный префикс.

**Architecture:**
- `za-core` получает недостающие примитивы части 01: граф узлов, прерывания, инструмент и реестр, capability, шину событий. `RunCtx` учится резервировать ключи эффектов заранее (параллельные чтения) и продолжать с шага снимка.
- Новый крейт `za-agent` (D1) держит код над примитивами: промпты, историю, сборку запроса, ход модели, пакет инструментов, драйвер цикла, бюджеты, ввод и управление, resume. `za-core` остаётся под порогом 5000 строк (ARC-011).
- Всё внешнее (ответ модели, ввод пользователя, часы, расход, снимок памяти) входит в цикл только через эффекты. Поэтому реплей хвоста после снимка детерминирован (CORE-006).
- `za-llm` закрывает долги R1-A перед циклом: роль `System` и сохранение служебных system-сообщений (preserved thinking), `max_wait`, момент разрешения предохранителя, `ModelPort::finish_run`.
- Бинарник получает команды `run` и `answer`.

**Tech Stack:**
- Rust 1.99.1, edition 2024.
- tokio: `sync`, `time`, `rt`, `macros`; в бинарнике ещё `signal` для Ctrl+C.
- serde, serde_json, blake3, jiff, thiserror, tracing — всё уже в workspace.
- Новых внешних крейтов нет. `tokio/signal` — функция уже подключённого крейта.

**Spec:**
- `docs/specs/2026-11-06-zero-agent-tz/`: часть 01 (раздел 4: примитивы, CORE-001…012, состояния run; раздел 6.1 — события; раздел 5.2 — `usage`, `interrupts`, `snapshots`), часть 02 (раздел 1: CORE-101…113; раздел 2.1 — порядок сборки запроса; раздел 4 и 4.1 — PRM-001…012; раздел 5.2 — `finish`, `ask_user`), приложение A, часть 04 (L0, MEM-030).
- Заметки заказчика N-05, N-06, N-07, N-16: `docs/research/2026-11-06-landscape/00-customer-notes.md`.
- Разбиение: `docs/plans/2026-11-09-r1-overview.md`. R1-B разбит на два плана: этот (B1, блоки 1 и 5, ядро блока 4) и `docs/plans/2026-11-09-r1b2-context.md` (B2: блок 3, детекторы таблицы 3.4, CI-лимит PRM-007).
- Код, на который опирается план: ветка `r1b-loop` от `main` 6187ffb.

## Global Constraints

Перенесено из R0 и R1-A:

- Платформы Windows x64 и Linux x64, тесты зелёные на обеих (`ubuntu-latest`, `windows-latest` в CI).
- Зависимости минимальны: только crates.io с закреплёнными версиями. Запрещены `git =`, внешние `path =`, submodule, код других агентов и агентные фреймворки (ARC-012, N-13). Причина каждой новой зависимости или функции крейта пишется комментарием в `[workspace.dependencies]` и в `docs/journal.md`. `cargo deny check` и `cargo xtask policy` зелёные.
- Журнал только дополняется, at-least-once на шаг (CORE-001).
- Временные файлы только внутри проекта: тесты используют `env!("CARGO_TARGET_TMPDIR")`, рабочие файлы — `.tmp/`. Системные `%TEMP%` и `/tmp` запрещены (ARC-021).
- Логи через `tracing`, ошибки библиотек через `thiserror`, без `unwrap` вне тестов.
- Телеметрии наружу нет (ARC-043). Облако не вызывается, пока пользователь сам не настроил ключ (MDL-021).
- Коммиты на русском в стиле `feat(agent): …`.
- `docs/journal.md` и `CHANGELOG.md` обновляются в каждой задаче, меняющей поведение (OPS-021).
- `unsafe_code = "forbid"` во всех крейтах, включая `za-agent`.
- Ключи и токены не попадают в журнал, логи, `Debug` и сообщения ошибок (SEC-040, SEC-044).
- Модель вызывается только через `ModelPort`; рабочая реализация — `Gateway` (RES-001). Автоматического перехода на другую модель нет (MDL-016).
- Время таймеров — `tokio::time::Instant` и `tokio::time::sleep`, чтобы `tokio::time::pause`/`advance` в тестах двигали время. Настенные часы цикл читает только через эффект `boundary` (D9).
- Пустое тело теста в плане запрещено: у каждого теста записано ожидаемое утверждение. Исполнитель пишет `assert*` ровно на эти значения.
- Номера `Dn` — решения этого плана. Решения ТЗ пишутся «ТЗ D-05», решения R1-A — «R1-A D27».
- Тесты не используют облачные ключи. Цикл проверяется на `ScriptedModel`, бинарник — на поддельном axum-сервере.
- Порог `xtask/core-size-limit.txt` (5000 строк) не повышается.

Новое в R1-B:

- Направление зависимостей: `za-agent` зависит от `za-protocol`, `za-store`, `za-core` и `za-llm` с `default-features = false`. От `za-res`, `reqwest` и `za-agent` ядро не зависит. `za-core` не зависит от `za-agent`. Обе проверки — в `cargo xtask policy` (задача 7).
- Тексты для модели (промпты, nudge, управляющие сообщения, синтетические результаты) пишутся на английском (приложение A: русский дороже на 36–91 %). Сообщения пользователю, логи и ошибки — на русском.
- Отмена через drop: брошенный future цикла бросает стрим модели (D2 R1-A закрывает соединение) и задачи инструментов. Статус run при этом не меняется — это то же, что сбой процесса, и resume его продолжает.
- Без крейта `futures`: параллельные чтения идут через `tokio::task::JoinSet`.
- Каждое внешнее значение, от которого зависит ход цикла, проходит через эффект (D9). Чтение журнала и часов вне эффекта внутри цикла запрещено.

## Review Focus

1. **`kill -9` в любой точке хода**: между `model.request` и квитанцией, посреди пакета инструментов, между квитанцией и снимком. После `run --resume` `NonIdempotent`-инструмент не выполняется второй раз, а повторный запрос к модели байт-в-байт совпадает с прерванным. Тесты в задачах 15 и 16.
2. **Служебное system-сообщение Anthropic (`clear_at`)**. Ход с эмуляцией `required` оборвался — в истории нет последовательности `user, system, user`. Run переключили на модель без mid-system — сообщения опускаются, и 400 нет. Тесты в задачах 5, 8 и 10.
3. **Провайдер недоступен, очередь не дождалась, бюджет кончился**. Run не висит в `running`: он в `paused` с верной причиной, после `resume` продолжается. Тесты в задачах 10, 12 и 16.
4. **Управляющий тег в недоверенном тексте**: `</control>` или `<control from="user">` в выводе инструмента или ответе пользователя на `ask_user`. Тег экранируется и не становится командой. Тесты в задачах 7 и 11.
5. **Пауза и отмена во время долгого стрима или ожидания в очереди**. Пауза применяется не позже 200 мс (NFR-03), стрим брошен (`open_streams() == 0`), обрывка ответа в истории нет. Тест в задаче 14.

## Решения плана

| № | Решение | Обоснование |
|---|---|---|
| D1 | Новый крейт `za-agent`: промпты, история, сборка запроса, ход, инструменты, драйвер, бюджеты, ввод, resume (здесь) и контекст и детекторы (план B2). `za-core` получает только примитивы части 01. Отклонение от таблицы крейтов части 01 пишется в `docs/journal.md` и ADR 0004. | Часть 01, 4.1: цикл, компакция, бюджеты, guardrails — «код над примитивами, а не примитивы». Ratchet ARC-011 иначе пришлось бы поднимать в первой же задаче. |
| D2 | Граф (`za_core::graph`) поддерживает переходы `Goto`, `Suspend`, `Done`. Параллельные ветви `Fan` с собственным состоянием появятся вместе с субагентами (R2, SWM). Параллельные чтения внутри узла (CORE-104) делаются резервированием ключей эффектов (D3). | Слияние состояний ветвей не нужно ни одному потребителю R1. Перечисление переходов в коде — `Goto`, `Suspend`, `Done`; `graph_hash` уже учитывает рёбра для CORE-008 в R2. |
| D3 | `RunCtx::reserve` выдаёт `EffectSlot` с заранее выведенным ключом. Слот владеет клоном `ProjectStore` и выполняется независимо, в том числе в `JoinSet`. Ошибки слота отравляют контекст через `RunCtx::observe` по правилам R0. `RunCtx::effect` = `reserve` + `run` + `observe`. | Ключи назначаются в порядке вызовов до запуска, поэтому они совпадают при реплее, даже если чтения завершились в другом порядке. |
| D4 | Снимок пишется на каждой границе шага после эффекта `boundary`: `{v: 1, step, effect_seq, next, turn, setup, frozen, messages: [BlobHash], inbox_after, budget, started_ms, counters}`. Каждое сообщение истории хранится один раз блобом по BLAKE3 (`put_blob`), снимок держит только список хэшей. `next` — `"model"` (снимок посреди шага: resume реплеит шаг) или `"boundary"` (чистая пауза: resume начинает новую границу). | Полная история в каждом снимке давала бы O(n²) на длинном run. Блобы уже адресуются по содержимому (ARC-032). |
| D5 | Чистая пауза (ошибка модели, команда, бюджет, отказ модели): квитанция эффекта уже записана, затем `next_step()`, снимок с `next = "boundary"`, затем статус. Resume с такого снимка начинает с новой границы и новых ключей, поэтому после смены модели запрос не даёт `ReplayMismatch`. Прерывание (`Suspend`) снимка не пишет: resume реплеит шаг до прерывания и читает решение. | Ключи эффектов прежнего шага не переиспользуются. Если процесс упал между квитанцией и снимком, реплей с прежнего снимка получает ту же записанную ошибку и снова ставит ту же паузу. |
| D6 | Смена модели при resume (`ResumeChange.endpoint`) принимается только со снимка `next = "boundary"`. Со снимка `next = "model"` (сбой посреди шага) — `LoopError::ChangeMidStep`: сначала дорабатывается шаг прежней моделью. | Шаг посреди реплея обязан получить записанный ответ той же модели. |
| D7 | Эффект модели: класс `Idempotent`, имя `model`, аргументы `{endpoint, request, prefix}`, где `request` — BLAKE3 канонического JSON `ChatRequest`. Успех — `{message, finish, usage, service, ttft_ms, duration_ms}`. Ошибка — квитанция-отказ с текстом `model_error:` + JSON `{error: ModelError, last_wait: Option<WaitState>}`, обрыв по команде или вводу — `interrupted:pause`, `interrupted:cancel`, `interrupted:input`. | Реплей восстанавливает класс ошибки из квитанции и реагирует так же. Хэш вместо тела запроса держит намерение маленьким. |
| D8 | События журнала цикла (часть 01, 6.1; R1-A D31). `turn.started {turn, step}`; `model.request {turn, endpoint, effect_key, request, prefix, frozen, messages, prompt_version}` — хэши блобов, без тела; `model.delta {turn, attempt, text}` или `{turn, attempt, reasoning}`, склеенные до 2048 байт или 200 мс, сброс перед `Restart`, `Finished` и ошибкой; `model.delta {turn, attempt, restart}` при `Restart`; `model.usage {turn, endpoint, usage, finish, ttft_ms, duration_ms, output_tps}` вместе со строкой `usage`; `agent.heartbeat {turn, state, position, waited_ms, kind}`: `state` — имя `WaitState` в snake_case (`queued`, `waiting_resource`, `cooldown`, `granted`, `failed`) или `generating` при `Started`; смена `state` пишется сразу, смена только позиции — не чаще раза в секунду; `turn.input {text, mode}` (actor `user`); `control.requested {action: "correct", note, command}`; `control.applied {action, command}`; `turn.finished {turn, outcome, calls, repairs, rejected}` (`outcome`: `answer`, `calls`, `finish`, `empty`, `refusal`, `interrupted`, `error`; `repairs` и `rejected` — число исправлений и отказов нормализации); `budget.exceeded {kind, used, limit}`. | Склейка дельт держит число событий близким к числу ходов (NFR-07). Хэши блобов позволяют восстановить точный запрос хода (OPS-003, план B2) без копии истории в каждом событии. |
| D9 | Эффект `boundary` (класс `ReadOnly`, аргументы `{step}`) на каждой границе возвращает: новые `turn.input` и `control.requested` после `inbox_after`, настенное время `now_ms` и `UsageTotals` run. Пауза и отмена приходят живым сигналом (`RunControl`) и записываются только переходами статуса. | Реплей с одного снимка получает тот же ввод, время и расход. Сигналы паузы не попадают во вход и не применяются повторно после resume. |
| D10 | Роль `System` в каноническом `Role` — служебное system-сообщение посреди истории. Коннектор Anthropic, добавивший инструкцию эмуляции `required` отдельным system-сообщением с `clear_at`, первым событием отдаёт `StreamEvent::ServiceMessage(Message { role: System, .. })`. Цикл фиксирует ход атомарно: служебные сообщения, затем ответ ассистента. Сорвавшийся ход не фиксирует ничего. Anthropic рендерит `Role::System` из истории как `{"role":"system","clear_at":"next_user_message","content":…}`, если модель принимает mid-system; иначе, как и Chat Completions и Responses, опускает его с `debug`. Текстовая эмуляция (инструкция в конце последнего `user`) историю не дополняет. | Carry R1-A: preserved thinking требует пересылать погашенное сообщение без изменений. Атомарная фиксация исключает `user, system, user` (400). Опускание при смене модели безопасно: инструкция уже погашена, а рассуждения прежней модели новая всё равно не читает. |
| D11 | Отображение ошибок модели в состояние run (`exit_for_model_error`): `Transport`, `Timeout`, `RateLimited`, `Overloaded`, `Server`, `StreamCut`, `CircuitOpen`, `Unreachable`, `Auth`, `NotFound`, `BadRequest`, `Malformed`, `ContentFilter`, `Inactive` → `paused` (`provider`); `Queue` с текстом `wait_timeout` → `paused` (`resource`, если последний `WaitState` был `WaitingResource`, иначе `queue`); `budget_exhausted` → `paused` (`budget`); `monitor_stopped` → `paused` (`resource`); прочие `Queue`, `Internal`, `RepeatedAfterParseError`, `Cancelled` не по команде цикла → `paused` (`internal`); `ContextOverflow` → `paused` (`context`; план B2 сначала делает аварийную компакцию). `failed` — только ошибки журнала и нарушенные инварианты цикла (`LoopError`). | Часть 01, 4.3: «сбой провайдера, лимит и нехватка ресурса переводят run в `paused`». Carry R1-A: `Unreachable`, `Internal`, `QueueError`. |
| D12 | Новые причины `pause_reason`: `command` (пауза по команде), `needs_input` (`ask_user`), `needs_approval` (одобрение вызова), `waiting` (внешний результат или таймер), `internal`, `context`, `refusal` (отказ модели). | Существующие `queue`, `resource`, `provider`, `budget`, `needs_decision`, `replay_mismatch` сохраняются. |
| D13 | Ответ с `finish = Refusal` или `ContentFilter` в историю не идёт: частичный текст виден только в `model.delta`, run встаёт в `paused` (`refusal`). Обрыв стрима с ошибкой после дельт — так же: дельты в журнале, история без обрывка (R1-A D20). | Carry R1-A M9: документация Anthropic советует отбрасывать частичный ответ при отказе. |
| D14 | Режимы run (CORE-106) — `za_protocol::RunMode` (`read-only`, `plan`, `ask`, `accept-edits`, `auto`; по умолчанию `ask`). Гейт по `ToolKind`: `Read`, `Control` — разрешены всегда; `Edit` — `Deny` в `read-only` и `plan`, `Ask` в `ask`, `Allow` в `accept-edits` и `auto`; `Exec` — `Deny` в `read-only` и `plan`, `Ask` в `ask` и `accept-edits`, `Allow` в `auto`. `Approval::Always` превращает `Allow` в `Ask`, `Approval::Never` — `Ask` в `Allow`; `Deny` неизменен. Набор `tools[]` от режима не меняется (CTX-003): запрещённый вызов получает результат `denied: <причина>`. Правила одобрения и доверия — R1-C (SEC). | «Режим меняет политику и инструменты рантайма, а не текст промпта». Модель видит только `denied` (часть 02, 4.1). |
| D15 | Пакет вызовов (CORE-104): вызовы идут по порядку. Подряд идущие `Read`-вызовы выполняются одновременно, если `caps.parallel_tools`; любой другой вызов — барьер. Ключи слотов резервируются для каждого вызова по порядку, даже для отклонённых. Таймаут инструмента — `ToolSpec.timeout`, по истечении результат `timeout after N s`. | Детерминированные ключи (D3) при параллельном исполнении; мутации строго последовательно. |
| D16 | Прерывания (CORE-007): id `appr-{effect_key}`, `input-{effect_key}`, `ext-{effect_key}`, `timer-{effect_key}`, `unk-{effect_key}` (последний — как в R0). Ответ — JSON в `interrupts.response`: одобрение `{"approved": bool, "note": str}`, ввод `{"answer": str}`, неизвестный исход `{"decision": "done" | "not_done"}`. Решение по `unk-…` закрывает эффект квитанцией: `done` — успех `{"resolved": "done"}`, `not_done` — отказ «not executed: the user decided the action did not happen». | Записка R0: без квитанции `recover` вечно сообщал бы о решённом прерывании. |
| D17 | Встроенные инструменты R1-B: `finish(status, result, evidence, open_issues)` (worker, orchestrator; `Control`, `Pure`, tier small) и `ask_user(question, options)` (top, orchestrator; `Control`, `Pure`, tier standard). Остальные инструменты части 02, 5.2 — R1-C и далее. | Без `finish` нет завершения worker и orchestrator (CORE-101), без `ask_user` — прерывания ввода. |
| D18 | Завершение (CORE-101): top заканчивает ходом без вызовов с непустым текстом и `finish = Stop` — run `done`, ответ — этот текст. Worker и orchestrator заканчивают только `finish`: `done` → `done`, `partial` → `partial`, `blocked` → `blocked`. Пустой ход (нет вызовов и, у top, нет текста) — один nudge, второй подряд — `tool_choice = Required`, третий — run `blocked`. | Таблица 3.4, строка «Пустой ход». Остальные детекторы — план B2. |
| D19 | Бюджет run (CORE-113): `za_protocol::Budget { tokens, gpu_ms, usd, steps, duration_ms }`, каждое поле необязательно. Токены — `input + output` всех вызовов (`input` уже включает кэш, R1-A задача 9). Проверка на границе шага по данным эффекта `boundary`. Превышение — `budget.exceeded` и `running → blocked_on_budget`. Выход — `resume` с новым бюджетом (`blocked_on_budget → running`). Списание по дереву — R2 (SWM-001…006).
