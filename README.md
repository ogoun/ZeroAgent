# ZeroAgent

Универсальный самостоятельно размещаемый агент на Rust с упором на локальные модели: веб-интерфейс, рои субагентов, периодические задания, нативная долговременная память [ZeroAIMemory](../ZeroAIMemory) и связь агентов через `zero-agent-relay`.

**Статус:** этап R1-C1 «Инструменты и граница» реализован, приёмка — финальное ревью ветки `r1c1-tools` и ручная проверка S4 на живом llama-server (`live_llama_s4_ask_mode`; сервер пока не запускался). Агент правит код и запускает команды в границах проекта (сценарий S4 без памяти): нативные инструменты `read`, `search`, `glob`, `edit`, `multi_edit`, `bash`, `request_grant`; чекпоинт рабочей копии перед каждой правкой и командой; доступ вне проекта только по гранту или с вопросом пользователю; разовое доверие к чужому проекту; движок политики с режимами и правилами; маска секретов в журнале, выгрузке и контексте модели; журнал аудита с hash-цепочкой (`za-tools`, `za-jail`, `za-secrets`, `za-agent`). Следующий — R1-C2 «Скиллы и веб». Ранее: R1-B2, контекст и отказы: счёт токенов окна, выгрузка больших выводов, удаление старых результатов, компакция истории, инспектор запроса, метрики run и детекторы отказов: повторы, циклы, застой, вырождение стрима, обещание без действия, ошибки инструмента подряд, порча JSON вызовов, падение кэша (`za-agent`). Приёмка R1-B2 — финальное ревью ветки и ручной замер доли кэша (NFR-06) на живом llama-server. Цикл агента R1-B1: ходы модели и инструментов поверх журнала, пауза, отмена, бюджеты, продолжение после сбоя. Модельный слой R1-A: коннекторы llama.cpp, vLLM, OpenRouter, Anthropic, OpenAI и совместимых серверов, общая очередь к моделям, монитор ресурсов. Бинарник `zero-agent` с командами `doctor`, `demo-run`, `replay` (R0), `models`, `ask`, `resources` (R1-A), `run`, `answer` (R1-B1), `inspect`, `stats` (R1-B2), `audit`, `journal export`, `checkpoints`, `secret list`, `trust` (R1-C1). Нативные инструменты, граница проекта, политика, доверие и чекпоинты — R1-C1; клиент памяти отложен до завершения ZeroAIMemory.

## Быстрый старт

Тулчейн Rust лежит в проекте (`.toolchain/`), в систему ничего не ставится. Окружение подключается в той же оболочке, где идут команды:

```sh
. scripts/dev-env.sh          # PowerShell: . .\scripts\dev-env.ps1
cargo build -p zero-agent
cargo test --workspace --locked
```

Бинарник — `target/debug/zero-agent` (на Windows `zero-agent.exe`). Данные лежат в `ZA_HOME`; по умолчанию это `%LOCALAPPDATA%\zero-agent` или `~/.local/share/zero-agent`. Журнал проекта создаётся в `ZA_HOME/projects/<project_id>/journal.db`, не в каталоге проекта.

```sh
zero-agent doctor                          # SQLite, llama.cpp (LLAMA_URL), версия Rust; --json для машинного вывода
zero-agent demo-run --project ./demo --steps 5
#   1-я строка stdout — id run, затем done; в ./demo/log.txt строки step 1…step 5
zero-agent demo-run --project ./demo --steps 5 --crash-at execute:3   # аварийное завершение для проверки
zero-agent demo-run --project ./demo --steps 5 --resume <id run>      # продолжение; needs_decision и id прерываний
zero-agent replay --project ./demo --run <id run>                     # хэш значимых событий run
```

Коды выхода: `0` — готово; `1` — ошибка, в том числе неверные аргументы, `Fail` в `doctor` и расхождение журнала с кодом при `--resume`; `3` — нужно решение пользователя (исход необратимого действия неизвестен, run в `paused`).

## Модели (R1-A)

Модели описываются в `ZA_HOME/config.toml`. Ключей в файле нет: эндпоинт ссылается на ключ именем `key_ref`, а сам ключ берётся из переменной окружения `ZA_SECRET_<KEY_REF>` (имя в верхнем регистре, `-` → `_`: `key_ref = "open-router"` → `ZA_SECRET_OPEN_ROUTER`). Облако не вызывается, пока ключ не задан: такой эндпоинт `inactive`. Моделью по умолчанию может быть только локальная. Раздел `[resources]` необязателен.

```toml
[models]
default = "local"

[[models.endpoints]]
id = "local"
backend = "llama_cpp"              # llama_cpp, vllm, openai_compatible, openrouter, anthropic, openai_responses, openai_chat
base_url = "http://127.0.0.1:8080" # llama.cpp — корень сервера; прочие — корень версии API (…/v1)
max_parallel = 2                   # не больше слотов сервера (-np)

[[models.endpoints]]
id = "claude"
backend = "anthropic"
model = "claude-sonnet-5-5"
key_ref = "anthropic"              # ключ — в ZA_SECRET_ANTHROPIC
daily_budget_usd = 5.0              # дневной предел расхода группы, USD
price = { input_per_mtok = 3.0, output_per_mtok = 15.0 }   # USD за миллион токенов; без price бюджет — ошибка (стоимость сообщает только openrouter)

[models.roles]
worker = "local"

[resources]                         # пороги допуска, МиБ; все поля необязательны
vram_reserve_mib = 1024             # запас VRAM для фоновых заданий
disk_margin_mib = 5120
nvidia_smi = "nvidia-smi"
```

Без раздела `[models]` и с `LLAMA_URL` используется один эндпоинт `local` по этому адресу.

```sh
zero-agent models                          # эндпоинты и состояние: ready, inactive, unreachable, probing, open, disabled; --json
zero-agent models probe local              # повторный зонд: контекст, слоты, квант, профиль в ZA_HOME/models
zero-agent ask --model local "Столица Франции?"   # ответ в stdout, usage в stderr; --priority interactive|top|worker|job
zero-agent resources                       # CPU, RAM, GPU/VRAM, тома, данные агента, очередь; --json, --watch
zero-agent doctor                          # + GPU и состояние каждой модели
```

`ask` на терминале печатает ответ по мере генерации; если стрим оборвался и запрос повторён, в stderr появляется пометка, а ответ печатается заново с новой строки. В конвейер или файл уходит только итоговый ответ. `models`, `ask` и `doctor` зондируют эндпоинты и сохраняют профили в `ZA_HOME/models`.

Коды выхода команд моделей: `0` — успех (у `models` — при любом состоянии эндпоинтов); `1` — ошибка конфигурации, неготовая модель (`ask`, `models probe`) или ошибка модели. Команды ждут первого зонда не дольше 35 с.

Живые проверки бэкендов: `LLAMA_TEST_URL=http://127.0.0.1:8080 cargo test -p za-llm --test live -- --ignored` (также `VLLM_TEST_URL`, `OPENROUTER_TEST_KEY`, `ANTHROPIC_TEST_KEY`, `OPENAI_TEST_KEY`, модель — `ZA_TEST_<PROVIDER>_MODEL`).

Тесты `Gateway` идут в реальном времени; на медленной машине длительности тестов растягивает `ZA_TEST_TIME_SCALE` (целое 1–6, по умолчанию 1, в CI — 4).

Логи пишутся в stderr, по умолчанию уровень `warn`. Фильтр задаётся `ZA_LOG` (приоритетнее) или `RUST_LOG`: например, `ZA_LOG=info` или `ZA_LOG=warn,za_store=debug`.

## Run (R1-B1)

`run` ведёт задачу через цикл агента: ходы модели, вызовы инструментов, пауза, продолжение. Журнал run — в `ZA_HOME/projects/<project_id>/journal.db`; каталог проекта должен существовать. Модель работает с проектом нативными инструментами (R1-C1): `read`, `search`, `edit`, `bash` (со всех тиров), `glob`, `multi_edit`, `request_grant` (с `standard`); спрашивает пользователя `ask_user` (тиры `standard` и `full`). Решения о вызовах принимает политика (раздел «Политика»), перед правкой и командой делается чекпоинт.

```sh
zero-agent run --project . "Ответь одним словом: столица Франции?"
#   stderr: run 019a…   stdout: Париж
zero-agent run --project DIR [--model ID] [--mode read-only|plan|ask|accept-edits|auto|bypass]
               [--work-mode coder|researcher|operator|writer] [--tier small|standard|full]
               [--max-wait СЕК] [--max-steps N] [--max-tokens N] [--max-usd USD] [--max-gpu-ms МС] [--max-duration СЕК]
               [--grant ПУТЬ[=ro|=rw]]… "<задача>"
zero-agent run --project DIR --resume RUN [--model ID] [--input "<текст>"] [--grant ПУТЬ[=ro|=rw]]…
               [--max-steps N] [--max-tokens N] [--max-usd USD] [--max-gpu-ms МС] [--max-duration СЕК]
zero-agent answer --project DIR --interrupt ID (--text "<ответ>" | --approve | --deny [--note "<текст>"] | --done | --not-done)
```

- Первая строка stderr — `run <id>`, раньше любых предупреждений и логов: по нему run продолжают. Строки нет, только если у `--resume` нет журнала проекта. Ответ модели идёт в stdout по мере генерации, в конце — перевод строки.
- Модель по умолчанию — `models.default`. Неготовый эндпоинт (`inactive`, `unreachable`, зонд не завершился) — причина в stderr и код 1, run не создаётся. Отказ модели посреди run (429, обрыв, сервер недоступен) ставит run на паузу с причиной `provider`.
- Тир промпта выбирается по размеру контекста модели: меньше 32768 — `small`, меньше 65536 — `standard`, иначе `full`; `--tier` его переопределяет. `--max-wait` — предел ожидания в очереди к модели; без него заявка ждёт сколько нужно, по истечении — пауза `queue` или `resource`. `AGENTS.md` проекта (без него — `CLAUDE.md`) входит в промпт в пределах лимита роли, только если проект доверен (раздел «Доверие к проекту»); прежний флаг `--agents-md` удалён — он печатает подсказку и выходит с кодом 2.
- `--grant ПУТЬ[=ro|=rw]` — доступ вне проекта на этот run (по умолчанию `ro`; `=` — потому что `:` входит в путь Windows); флаг можно повторять, с `--resume` грант добавляется к грантам run. Гранты глобального `[[policy.grants]]` действуют так же. Путь канонизируется при старте; сетевой путь — ошибка, код 1. Вызов, исполненный с путём вне проекта, печатается строкой `zero-agent: вне проекта: <инструмент> <доступ> <путь>`.
- `--mode bypass` — только при `[policy] allow_bypass = true` глобальной конфигурации, иначе ошибка конфигурации и код 1.
- Ctrl+C — пауза run в безопасной точке: стрим модели обрывается, идущий инструмент дорабатывает, run встаёт в `paused` (`command`). Второй Ctrl+C — выход сразу, без ожидания паузы (код 4); `--resume` такой run продолжит.
- Модель спросила пользователя или ждёт одобрения — run на паузе, в stderr вопрос (у одобрения — инструмент, аргументы до 400 символов с маской секретов, причины и пути вне проекта) и строка `zero-agent: ответьте: zero-agent answer --interrupt <id> …`. `answer` записывает ответ и выходит, цикл продолжает `run --resume`.
- `--resume` продолжает run после паузы, после `blocked_on_budget` и после аварийного завершения процесса: шаг, оборванный сбоем, повторяется по журналу, и запрос к модели совпадает с прерванным байт в байт. `--model` меняет модель только на границе шага. `--input` добавляет сообщение пользователя.

Коды выхода `run`:

| Код | Значение |
|---|---|
| 0 | run `done` или `partial` |
| 1 | ошибка или `failed` (в stderr `zero-agent: run завершился ошибкой: <причина>`); в том числе неизвестный run у `--resume`, неготовая модель |
| 2 | удалённый флаг `--agents-md` |
| 3 | нужно решение пользователя: ответ на вопрос (`needs_input`), одобрение (`needs_approval`), доверие к проекту (`needs_trust`), неизвестный исход действия (`needs_decision`) |
| 4 | прочая пауза (`provider`, `queue`, `resource`, `command`, `context`, `model_loop`, `tool_errors`, …) или `blocked_on_budget` |
| 5 | `blocked`: модель трижды подряд ответила пустым ходом, повторяет один и тот же вызов, ходит по кругу или не продвигается (раздел «Детекторы отказов») |
| 6 | `cancelled` |

На Windows аварийное завершение процесса (`abort`) тоже даёт код 3. Настоящее «нужно решение» отличает строка `zero-agent: ответьте:` в stderr.

У `answer` код 0 — ответ записан; 1 — нет журнала или прерывания, вид ответа не подходит к прерыванию (`--text` — для `input-…`, `--approve`/`--deny` — для `appr-…` и `trust-…`, `--done`/`--not-done` — для `unk-…`) или прерывание уже решено.

## Бюджеты run (R1-B1)

Пределы расхода run по умолчанию задаёт раздел `[budgets.run]` того же `ZA_HOME/config.toml`. Все поля необязательны, поле без значения — без предела. Незнакомое имя поля — ошибка конфигурации: опечатка не снимает ограничение молча.

```toml
[budgets.run]
tokens = 200000        # input + output всех вызовов модели (input включает кэш)
gpu_ms = 600000        # время GPU, мс
usd = 2.0              # стоимость, USD
steps = 50             # ходов модели: 50-й ход последний
duration_ms = 1800000  # активное время run, мс: время в паузе не считается
```

Флаги `run` задают пределы поверх `[budgets.run]`, по одному на поле: `--max-steps` — `steps`, `--max-tokens` — `tokens`, `--max-usd` — `usd` (конечное неотрицательное число), `--max-gpu-ms` — `gpu_ms`, `--max-duration СЕК` — `duration_ms` (в секундах). Каждый флаг задаёт предел на весь run, включая уже потраченное, а не прибавку: run, остановленный на 20 шагах, с `--resume --max-steps 30` сделает ещё 10. Бюджет фиксируется при старте run и хранится в его снимке. `run --resume` без флагов бюджета продолжает с тем же бюджетом; `[budgets.run]` при продолжении не перечитывается. С флагами они меняют свои поля поверх текущего бюджета run, остальные пределы сохраняются. Так run в `blocked_on_budget` продолжают с новым пределом исчерпанного вида: подсказка в stderr называет нужный флаг (`run --resume <id> --max-steps 100`, `--max-duration 3600`, `--max-usd 5`).

Бюджет проверяется на границе шага, до начала следующего хода и до чтения нового ввода. `steps` ограничивает число ходов: при `steps = 2` третий ход не начинается. Остальные пределы срабатывают, когда расход их превысил; равенство пределу — ещё не превышение. Превышение записывается событием `budget.exceeded {kind, used, limit}` и переводит run в `blocked_on_budget`. Ввод, пришедший во время последнего хода, не теряется: его прочитает граница после продолжения run с новым бюджетом. Дневной бюджет облачной группы по-прежнему задаётся `daily_budget_usd` у эндпоинта в `[models]`.

## Контекст (R1-B2)

Раздел `[context]` того же `ZA_HOME/config.toml` задаёт тир run и пороги разгрузки контекста. Все поля необязательны. Незнакомое имя поля или значение вне диапазона — ошибка конфигурации.

```toml
[context]
tier = "standard"   # small | standard | full; без поля — по размеру окна модели
compact_at = 0.75   # компакция истории при заполнении окна, 0.70–0.80
prune_at = 0.65     # удаление старых результатов инструментов, меньше compact_at
spill_share = 0.15  # предел вывода инструмента в контексте, доля окна, 0.15–0.20
```

Флаг `--tier` важнее `[context].tier`. Раздел фиксируется при старте run и хранится в его снимке: `run --resume` продолжает с теми же значениями, даже если конфигурация изменилась.

Заполнение окна считается так: оценка запроса хода плюс резерв вывода хода сравнивается с долей окна. Оценка — расход прошлого хода (`usage`) плюс новые сообщения; новые сообщения у llama.cpp считает `/tokenize`, у остальных — байты / 4. Если провайдер не сообщает расход, оценивается весь запрос. Резерв — лимит вывода хода: не меньше бюджета мышления тира плюс 1024 токена на ответ. Если размер окна модели неизвестен, run считает его равным 8192 и пишет событие `context.alert {kind: "n_ctx_unknown"}`. Если сервер принял заметно меньше токенов, чем оценка запроса (меньше половины), run пишет `context.alert {kind: "truncation_suspected"}`: сервер, вероятно, запущен с меньшим окном и срезал начало промпта.

Вывод инструмента длиннее `spill_share` окна (в байтах — доля × размер окна × 4) остаётся в контексте началом и концом, а полный текст ложится в `.zero-agent/work/spill/` проекта; строка между ними называет файл: `… omitted N lines; search .zero-agent/work/spill/<id>.txt`. Каталог `.zero-agent/work/` получает `.gitignore` и в git не попадает. При заполнении окна до `prune_at` результаты инструментов старше последних 4 ходов и длиннее 1024 байт заменяются ссылкой на файл с полным текстом (событие `context.pruned`).

При заполнении окна до `compact_at` история сжимается (событие `context.compacted`). Модель пишет сводку: решения, изменённые файлы, ошибки и следующий шаг. Цель run и сообщения пользователя добавляет в сводку сам run, дословно. Дальше run продолжает с короткой историей: `<env>`, сводка, последний запрос или последний ход модели и напоминание о текущей задаче. Если сервер отвечает, что запрос не помещается в окно, run сжимает историю по усечённому входу и повторяет ход один раз; повторный отказ или повторная обрезка ставят run на паузу `context`. Если после сжатия окно всё ещё заполнено выше порога, run пишет `context.alert {kind: "compaction_insufficient"}` и не сжимает историю на каждом шаге, пока запрос помещается в окно. `run --resume` на модель с меньшим окном пишет `context.alert {kind: "n_ctx_changed"}` и сжимает историю на первом шаге.

## Детекторы отказов (R1-B2)

Run следит, не зациклилась ли модель, и не даёт ей тратить бюджет впустую. Каждое срабатывание пишется в журнал событием `loop.detected {detector, action, turn}`; подсказки модели идут в её историю на английском.

| Что случилось | Что делает run | Что видит пользователь |
|---|---|---|
| Тот же вызов с теми же аргументами (после правки или ввода пользователя счёт начинается заново) | 2-й раз — прошлый результат с пометкой, без выполнения; 3-й — отказ; 4-й — отказ и подсказка сменить подход; 5-й — стоп | код 5, `blocked` |
| Ходы по кругу (A, B, A, B или A, B, C, A, B, C) без новых результатов | подсказка «остановись и смени подход» и напоминание задачи; повтор в ближайшие 6 ходов — стоп | код 5, `blocked` |
| 8 ходов подряд без прогресса (нет новых результатов, правок, успешных команд, ответа) | стоп | код 5, `blocked` |
| Модель повторяет один и тот же текст в стриме | стрим обрывается, ход повторяется с другими параметрами выборки; второй раз в шаге — пауза | код 4, пауза `model_loop` |
| Рассуждение без конца (сверх бюджета мышления или дольше тайм-аута без ответа) | стрим обрывается, ход повторяется без рассуждения; второй раз — пауза | код 4, пауза `model_loop` |
| «Сейчас сделаю», но без вызова инструмента | подсказка сделать вызов; второй такой ответ подряд принимается как ответ | обычный ответ |
| Инструменты одного класса ошибаются подряд | после 3-й, 4-й и 5-й ошибки — пауза 1, 2 и 4 с; 6-я — пауза run | код 4, пауза `tool_errors` |
| 3 хода подряд с испорченным JSON вызовов | аварийное сжатие истории; ещё 2 таких хода — пауза | код 4, пауза `model_loop` |
| Доля кэша промпта упала вдвое без сжатия истории | событие `context.alert {kind: "cache_drop"}` и предупреждение в лог: префикс запроса изменился или сервер вытеснил кэш | только журнал |
| Запрос не помещается в окно даже после сжатия, или сервер снова срезал промпт | пауза | код 4, пауза `context` |

Как продолжить:

- Пауза (`model_loop`, `tool_errors`, `context`) — `zero-agent run --project DIR --resume RUN`. Подсказку модели можно передать сразу: `--input "<что сделать иначе>"`; ввод пользователя сбрасывает счёт повторов. После паузы `model_loop` run начинает шаг заново, после `tool_errors` счёт ошибок класса начинается с нуля.
- Пауза `context` — окна модели не хватает: продолжите на модели с большим окном (`--resume RUN --model ID`; на первом шаге история сожмётся под новое окно) или запустите сервер с большим `n_ctx`.
- `blocked` — конечный статус, `--resume` его не продолжает. Посмотрите, на чём застряла модель (`zero-agent inspect`, события `loop.detected` в журнале), и начните новый run с уточнённой задачей.

## Инспектор и метрики (R1-B2)

`inspect` показывает, из чего состоял запрос хода к модели, `stats` — метрики run. Обе команды только читают журнал проекта и не меняют run; их можно запускать после завершения run или во время паузы (пока run идёт, журнал занят его процессом).

```sh
zero-agent inspect --project DIR --run RUN [--turn N] [--raw | --json]
zero-agent stats --project DIR --run RUN [--json]
```

- `inspect` восстанавливает запрос хода `N` (без `--turn` — последнего) по журналу и сверяет его хэш с записанным: запрос совпадает с отправленным байт в байт. Таблица — блоки запроса по порядку сборки: описания инструментов (`tools`), Core (`core`), адаптер модели (`adapter`), overlay режима (`overlay`), `AGENTS.md` (`agents_md`), первое сообщение с `<env>` и задачей (`first_message`), диалог (`dialog`) и напоминания рантайма (`control`). У каждого блока — байты, оценка токенов (байты / 4) и начало хэша. Под таблицей — оценка запроса, расход, который сообщил провайдер, и оценка следующего хода. У run, начатых до R1-B2, Core, адаптер, overlay и `AGENTS.md` показаны одной строкой `system`. Ход, повторённый после переполнения окна, показывается последней попыткой.
- `--raw` печатает точное тело запроса, которое ушло бы провайдеру, тем же кодом, что и `run`: модели из `config.toml` запускаются, ключи и заголовки в вывод не попадают. Тело строится по текущей конфигурации и профилю эндпоинта, а не по их состоянию во время хода: если модель или её настройки с тех пор менялись, тело может отличаться от ушедшего. У llama.cpp в теле нет `id_slot`: слот выбирается при отправке.
- `--json` — те же данные в JSON (`turn`, `endpoint`, `blocks`, `estimate`, `input`, `n_ctx`, `next_turn`).
- `stats`: ходы и шаги (шаг — каждый запрос хода к модели, включая повторы), токены входа, из кэша и доля кэша, выход, время до первого токена (p50 и p95), средняя скорость вывода, ошибки модели по классам, ремонт вызовов инструментов, число компакций, стоимость.

Журнал проекта, записанный более старой версией, при первом открытии командой переводится на текущую схему (один раз, только вперёд); сами события run не меняются.

Коды выхода: 0 — готово; 1 — нет журнала проекта, run или хода, запрос не восстанавливается по журналу, тело запроса не построено (модель не настроена или ещё ни разу не зондирована).

## Инструменты и граница проекта (R1-C1)

Модель работает с проектом нативными инструментами. Описания одинаковы на всех ОС; маленькой модели (тир `small`) даются только первые четыре.

| Инструмент | Что делает | Тир |
|---|---|---|
| `read(path, start, limit)` | строки файла с номерами (до 500 строк за вызов); двоичный файл — тип и размер; несуществующий путь — до трёх похожих имён | все |
| `search(pattern, path, glob)` | регулярное выражение по файлам проекта с учётом `.gitignore`, до 200 совпадений `путь:строка:текст` | все |
| `edit(path, old, new, allow_shrink)` | замена фрагмента; пустой `old` создаёт файл. Файл должен быть прочитан в этом run и не измениться после чтения. BOM, переводы строк и права сохраняются, файл не в UTF-8 не правится, удаление больше половины строк — только с `allow_shrink` | все |
| `bash(cmd, cwd, timeout)` | команда в PowerShell на Windows, в bash на Linux и macOS; результат — `exit code: N`, stdout и stderr. Тайм-аут (по умолчанию 120 с, не больше 600 с) и фоновые потомки убивают всё дерево процессов | все |
| `glob(pattern)` | пути по шаблону, до 500 | `standard` |
| `multi_edit(path, edits)` | несколько замен в одном файле: все или ни одной | `standard` |
| `request_grant(path, mode, reason)` | просьба о доступе вне проекта, решает пользователь | `standard`, только top |

Каталоги `.git` и `.zero-agent` инструменты не обходят. Рабочие файлы агента (временные каталоги команд, выгрузка длинных выводов, маркеры правок) лежат в `<проект>/.zero-agent/work/` с `.gitignore` `*`; переменные `TMP`, `TEMP`, `TMPDIR` команд указывают туда же.

**Что видит пользователь.** Первая строка stderr `run` — `run <id>`. Вызов, исполненный с путём вне проекта, печатается строкой `zero-agent: вне проекта: <инструмент> <read|write> <путь>` — на каждый путь, в том числе по гранту. Когда нужно решение, run встаёт на паузу (код 3) и печатает, о чём вопрос, затем `zero-agent: ответьте: zero-agent answer --interrupt <id> --project <P> <флаги>` и `zero-agent: продолжить: zero-agent run --project <P> --resume <run>`. Ответ записывает `answer`, работу продолжает `run --resume`.

**Какие вопросы задаёт агент:**

| Вопрос | Когда | Что в stderr | Ответ |
|---|---|---|---|
| Одобрить вызов (`appr-…`, пауза `needs_approval`) | режим требует подтверждения (`ask` — правки и команды, `accept-edits` — команды); путь вне проекта без гранта (`outside_project`, в любом режиме, и в `bypass`); необратимая или неразобранная команда (`irreversible`, всегда); правило `ask` | `вызов: <инструмент> <аргументы>`, `причины: mode, rule, outside_project, irreversible`, `необратимо: delete, git_reset…`, строки «вне проекта» | `--approve` — один этот вызов; `--deny [--note "<текст>"]` — модель получает `denied by user: <текст>` |
| Выдать грант (`appr-…`, причина `grant`) | модель вызвала `request_grant` | `модель просит грант: <ro\|rw> <путь>: <причина>` | `--approve` — грант до конца run; `--deny` |
| Доверить проект (`trust-…`, пауза `needs_trust`) | первая команда `bash` в недоверенном проекте | `нужна команда в недоверенном проекте <P>: доверить проект один раз? доверенные файлы: …` | `--approve` — один раз на проект; `--deny` — команды этого run получают `denied: untrusted project`, нового вопроса нет |
| Исход неизвестен (`unk-…`, пауза `needs_decision`) | процесс агента упал, пока шла команда: выполнена ли она, неизвестно | подсказка `answer … --done \| --not-done` | `--done` — считать выполненной, `--not-done` — нет; команда сама не повторяется |
| Вопрос модели (`input-…`, пауза `needs_input`) | модель вызвала `ask_user` | `вопрос модели: …` | `--text "<ответ>"` |

Без вопросов агент отказывает (модель получает текст отказа, run продолжается): запись в защищённое место (`denied: protected path` — `ZA_HOME`, `.zero-agent/` проекта, `.git/`), правило `deny` (`denied: policy rule`), запрет режима (`read-only`, `plan`), сетевые и device-пути Windows (`\\server\share`, `\\.\…`, `CON`, потоки `a:b`) — они отклоняются до обращения к диску. Чтение по сети (`curl`, `git pull`) и файлов вне проекта помечает результат `[untrusted content: …]` и событие `tool.finished` (`tainted`), но вопросов к следующим командам не добавляет.

**Граница проекта и гранты.** Читать и писать вне каталога проекта нативные инструменты могут только по гранту — `run --grant <путь>[=ro|=rw]` или глобальный `[[policy.grants]]` (раздел «Политика») — или с одобрением этого вызова. Грант `ro` даёт чтение, `rw` — ещё запись и команды `bash` с этим путём. Пути в командах `bash` (абсолютные, `..`, `~`, `cd`, `git -C`) распознаются по разобранной команде (best effort: `$HOME` и переменные не раскрываются). Ссылки и junction внутри проекта, ведущие наружу, считаются путями наружу, в том числе созданные командой того же ответа модели. Каждая попытка доступа наружу остаётся в журнале: исполненная — событием `boundary.outside {call_id, tool, paths: [{path, access, granted}]}`, ушедшая на вопрос — путём и причиной в прерывании (`interrupt.opened`). Гранты пишутся в аудит (`grant.added`). ОС-изоляции на этом этапе нет: граница держится на решениях агента и журнале.

**Чекпоинты.** Перед каждой правкой (`edit`, `multi_edit`) и командой (`bash`) агент сохраняет состояние рабочей копии (событие `checkpoint.created {call_id, id, kind}`), id — `<run>/<шаг>-<номер>`.

```sh
zero-agent checkpoints list --project DIR [--json]                 # id, вид (git или files), коммит
zero-agent checkpoints restore --project DIR <id> [--delete-new] [--json]
```

- В доверенном проекте с `.git` в корне чекпоинт — коммит в собственном голом репозитории агента `ZA_HOME/projects/<project_id>/checkpoints/repo.git`. Репозиторий пользователя не используется: HEAD, индекс, stash, ветки и `refs` проекта не меняются, его хуки, фильтры и конфиг не исполняются. Игнорируемые файлы (`.gitignore`) в чекпоинт не входят, правимый файл входит всегда; файлы больше 64 МиБ пропускаются. Git дольше 20 с — чекпоинт пропускается (`slow`) до конца run.
- Без git, без `.git` в корне или в недоверенном проекте правка сохраняет прежнее содержимое затронутых файлов копией в `ZA_HOME` (`files`); у команды тогда чекпоинта нет (`skipped`, причина `no_git` или `git_not_found`).
- `restore` сначала делает чекпоинт «до» (без него не восстанавливает), затем возвращает файлы. Файлы, которых не было в чекпоинте, удаляются только с `--delete-new`. Восстановление пишется в аудит (`checkpoint.restored`). Чекпоинты git видны и восстанавливаются только у доверенного проекта.

**Секреты в выводе.** Значения `ZA_SECRET_*` и ключи известных форматов в выводе инструментов (`cat .env`, `env`, `git config -l`), в ответе и аргументах модели заменяются на `[secret masked: …]` до записи в журнал, выгрузку длинного вывода и контекст модели (раздел «Секреты»). Командам `bash` переменные `ZA_SECRET*` не передаются.

## Доверие к проекту (R1-C1)

Чужой проект может подложить инструкции модели (`AGENTS.md`, `CLAUDE.md`), правила политики (`.zero-agent/config.toml`) и скиллы (`.zero-agent/skills/`, `.agents/skills/`, `.claude/skills/`). Пока проект не доверен, `run` их не читает, а команды `bash` не выполняет: первая команда ставит run на паузу `needs_trust` (код 3) с вопросом о доверии. Чтение файлов и правки идут по режиму.

```sh
zero-agent trust --project DIR [--revoke]
zero-agent answer --project DIR --interrupt trust-… (--approve | --deny)
```

- Доверие даётся один раз: `trust` заранее или ответ `--approve` на вопрос. В журнал аудита пишется `trust.granted` с хэшами доверенных файлов. После доверия команды идут по режиму: в `auto` — без вопросов, кроме необратимых и путей вне проекта. `--deny` — команды этого run получают отказ без нового вопроса.
- Каждый `run` пересчитывает хэши: если доверенный файл изменился, появился или удалён, проект снова не доверен, а stderr называет файлы (`изменены: AGENTS.md`). `trust --revoke` отзывает доверие (`trust.revoked`); отзыв действует и на продолжаемый run.
- Доверенный проект даёт `AGENTS.md` (без него — `CLAUDE.md`) в промпт и правила `ask` и `deny` своего `.zero-agent/config.toml`. Доверие посреди run промпт не меняет: инструкции проекта подхватит следующий run.
- Без доверия чекпоинты git не делаются и не читаются: правки сохраняются копиями файлов в `ZA_HOME`.
- При продолжении run сверяется журнал аудита: если запись, сохранённая в снимке run, исчезла или изменилась, `run --resume` выходит с кодом 1 и подсказкой `zero-agent audit --verify`.

## Аудит и выгрузка журнала (R1-C1)

Одобрения вызовов и доверие к проекту пишутся в журнал аудита проекта (таблица `audit` в `journal.db`). Записи связаны hash-цепочкой BLAKE3: подмена или удаление записи в середине обнаруживается проверкой.

```sh
zero-agent audit --project DIR [--verify] [--json]
zero-agent journal export --project DIR --run RUN
zero-agent answer --project DIR --interrupt trust-… (--approve | --deny)
```

- `answer` на одобрение (`appr-…`) пишет запись `approval.resolved`. Ответ на прерывание доверия к проекту (`trust-…`): `--approve` пишет ещё `trust.granted` с хэшами доверенных файлов проекта (`AGENTS.md`, `CLAUDE.md`, `.zero-agent/config.toml`, деревья скиллов) на момент ответа, `--deny [--note]` — только отказ. Если доверенные файлы изменились после вопроса, доверие не записывается: `answer` открывает новое прерывание с текущим набором, печатает его id и выходит с кодом 3. Ссылка на файл внутри проекта учитывается по содержимому цели; ссылка наружу, на сетевой путь и каталоги-ссылки (junction) не читаются и отмечаются в наборе. Решение и запись аудита сохраняются вместе или не сохраняются вовсе.
- `audit` печатает записи: номер, время UTC, кто, действие, объект, данные (`--json` — строка JSON на запись). `--verify` только проверяет цепочку. Разрыв цепочки — сообщение `разрыв цепочки аудита на записи N` и код 1.
- `journal export` печатает события run строками JSON по порядку. Секреты маскируются: значения переменных `ZA_SECRET_*` (от 8 символов) заменяются на `[secret masked: <имя>]`, а ключи и токены известных форматов (`sk-…`, `ghp_…`, `AKIA…`, `xox?-…`, `AIza…`, `glpat-…`, `hf_…`, `gsk_…`, `xai-…`, JWT, токен после `Bearer`), приватные ключи PEM и пароли в URL и строках подключения — на `[secret masked: <вид>]`, даже если переменных в окружении выгрузки нет. Так же маскируются записи `audit` и ответ, который печатают `run` и `ask`.
- Пока run идёт, его процесс держит журнал: `audit` и `journal export` печатают «журнал проекта занят запущенным run; повторите после его остановки» и выходят с кодом 1.

## Секреты (R1-C1)

Секреты агента — ключи провайдеров из переменных окружения `ZA_SECRET_<KEY_REF>`. Они читаются один раз при старте команды. Дочерним процессам (команды `bash`, git, `nvidia-smi`) переменные `ZA_SECRET*` не передаются. Хранение в разделе Vault памяти ZeroAIMemory появится вместе с клиентом памяти; конфигурация при этом не меняется.

```sh
zero-agent secret list
```

`secret list` печатает имена секретов (`key_ref` из `config.toml` и переменные `ZA_SECRET_*`), имя переменной и отметку «задан» или «не задан». Значения не печатаются. Значение короче 8 символов маска не ищет: `secret list` помечает его, а `doctor` даёт предупреждение. `doctor` показывает строку `secrets` с источником секретов, а также `git` (есть ли git в `PATH` и его версия: без git чекпоинты — копиями файлов) и `shell` (оболочка инструмента `bash`).

## Политика (R1-C1)

Решение о каждом вызове инструмента принимает политика: разрешить, спросить пользователя или отказать. Правила и гранты задаёт раздел `[policy]` глобального `ZA_HOME/config.toml`. Незнакомое поле, неверное значение или шаблон — ошибка конфигурации с путём поля, например `config.toml: policy.rules[0]: неизвестное поле`.

```toml
[policy]
allow_bypass = false          # режим bypass разрешён только при true

[[policy.rules]]
action = "deny"               # allow | ask | deny
command = "git push*"         # команда: deny и ask — имя команды или текст любой части

[[policy.rules]]
action = "allow"
command = "cargo test"        # allow — только если каждая часть команды совпала, без $(…), `…` и перенаправлений

[[policy.rules]]
action = "ask"
tool = "edit"
path = "migrations/**"        # путь внутри проекта — относительно корня через /

[[policy.grants]]             # доступ вне проекта
path = "D:/datasets"          # абсолютный путь; ~ и переменные не раскрываются
mode = "ro"                   # ro — чтение нативными инструментами (по умолчанию), rw — ещё запись и команды bash с этим путём
reason = "наборы данных"
```

- Правило срабатывает, если совпали все заданные поля `tool`, `path`, `command`; хотя бы одно обязательно. Шаблоны — glob: `*` внутри одного каталога, `**` — через каталоги. Путь сверяется после разрешения ссылок и `..`, на Windows без учёта регистра. Абсолютный шаблон действует на любой путь, относительный — только внутри проекта.
- Порядок решения: запись в защищённое место (`ZA_HOME`, `.zero-agent/` проекта кроме `.zero-agent/work/`, `.git/`) — отказ; любое правило `deny` — отказ; запрет режима (`read-only`, `plan`) — отказ; команда в недоверенном проекте — вопрос о доверии один раз, после отказа — `denied: untrusted project`. Затем собираются причины вопроса: режим, правило `ask`, путь вне проекта, необратимая команда. Прочитанное из сети или вне проекта помечается в журнале (`tainted`), но вопросов к следующим командам не добавляет.
- Чтение и запись вне проекта — только по гранту или глобальному правилу `allow` с подходящим `path`, иначе вопрос (`outside_project`). Грант `/data` не покрывает `/data2`. Путь в команде bash считается записью: его покрывает только грант `rw`. Путь с `~` в команде и чтение `ZA_HOME` спрашиваются всегда.
- Необратимые команды (`rm -rf`, `git reset --hard`, `git push --force`, публикация и другие, а также команда, которую разбор не понял) спрашиваются всегда, в любом режиме.
- Глобальное `allow` снимает только вопрос режима. Для команд bash действует лишь правило с `command`: правило только по `tool` или `path` команду не разрешает. Необратимость и неразобранную команду `allow` не снимает.
- Правило `deny` или `ask` с `command` сверяется и с нормализованной командой: без `sudo`, `env`, `timeout`, пути и `.exe`, имя без регистра, слова шаблона после имени — по порядку среди аргументов (`git push*` ловит `git -C . push`). `deny` с `path` сверяется и со всеми словами команды bash (`cat .env`).
- Режим `bypass` снимает вопрос режима, но не снимает вопросы о необратимом, о пути вне проекта, правила `ask` и инструменты, которые спрашивают всегда.
- Проектный `.zero-agent/config.toml` (только у доверенного проекта) может добавить правила `ask` и `deny`. Его `allow`, `allow_bypass` и гранты не действуют, прочие разделы — тоже (предупреждение в stderr). Смена политики (хэш глобальной и проектной) пишется в аудит записью `policy.loaded`.
