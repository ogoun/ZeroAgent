Универсальный самостоятельно размещаемый агент на Rust с упором на локальные модели: веб-интерфейс, рои субагентов, периодические задания, нативная долговременная память [ZeroAIMemory](../ZeroAIMemory) и связь агентов через `zero-agent-relay`.

**Статус:** этап R1-C2 «Скиллы и веб» реализован (задачи 1–15, проход исправлений fix-14 по ревью задач 14 и 15, финальное ревью ветки `r1c2-skills-web` тремя рецензентами и проход исправлений по нему 2026-11-17). Открыто: ручная проверка S1 на живых llama-server (окно от 32k) и своём SearXNG (`live_llama_s1`; серверы пока не запускались) и CAP-003 (`research-with-citations` вживую). Агент отвечает на вопрос с поиском и ссылками (сценарий S1): `web_search` через свой экземпляр SearXNG, `web_fetch` (HTML в Markdown и PDF в отдельном процессе) через один сетевой шлюз — без локальных адресов, cookie и прокси, с лимитами, `robots.txt`, журналом сетевых обращений и меткой `web`; `read` читает PDF; правила политики по домену и выключение веба проектом; Rule of Two пишется в журнал и аудит без вопросов (решение заказчика); скиллы из доверенных деревьев проекта, `ZA_HOME/skills` и поставки (core pack из 14 скиллов своими текстами) — `activate_skill`, `/имя`, карточки роутера на tier small, защита активных скиллов от компакции (`za-web`, `za-skills`, `za-extract`, `za-agent`). Следующий — R1-M «Память». Ранее: R1-C1 «Инструменты и граница» — выполнен и слит в `main` (7aac95f); открыта только живая проверка S4 на llama-server (`live_llama_s4_ask_mode`): агент правит код и запускает команды в границах проекта (сценарий S4 без памяти) — нативные инструменты `read`, `search`, `glob`, `edit`, `multi_edit`, `bash`, `request_grant`; чекпоинт рабочей копии перед каждой правкой и командой; доступ вне проекта только по гранту или с вопросом пользователю; разовое доверие к чужому проекту; движок политики с режимами и правилами; маска секретов в журнале, выгрузке и контексте модели; журнал аудита с hash-цепочкой (`za-tools`, `za-jail`, `za-secrets`, `za-agent`). ## Быстрый старт

Тулчейн Rust лежит в проекте (`.toolchain/`), в систему ничего не ставится. Окружение подключается в той же оболочке, где идут команды:

```sh
. scripts/dev-env.sh          # PowerShell: . .\scripts\dev-env.ps1
cargo build -p zero-agent
cargo test --workspace --locked
```

Бинарник — `target/debug/zero-agent` (на Windows `zero-agent.exe`). Данные лежат в `ZA_HOME`; по умолчанию это `%LOCALAPPDATA%\zero-agent` или `~/.local/share/zero-agent`. Журнал проекта создаётся в `ZA_HOME/projects/<project_id>/journal.db`, не в каталоге проекта.

```sh
zero-agent doctor                          # SQLite, llama.cpp (LLAMA_URL), версия Rust; --json для машинного вывода
zero-agent demo-run --project ./demo --steps 5
#   1-я строка stdout — id run, затем done; в ./demo/log.txt строки step 1…step 5
zero-agent demo-run --project ./demo --steps 5 --crash-at execute:3   # аварийное завершение для проверки
zero-agent demo-run --project ./demo --steps 5 --resume <id run>      # продолжение; needs_decision и id прерываний
zero-agent replay --project ./demo --run <id run>                     # хэш значимых событий run
```

Коды выхода: `0` — готово; `1` — ошибка, в том числе неверные аргументы, `Fail` в `doctor` и расхождение журнала с кодом при `--resume`; `3` — нужно решение пользователя (исход необратимого действия неизвестен, run в `paused`).

## Модели (R1-A)

Модели описываются в `ZA_HOME/config.toml`. Ключей в файле нет: эндпоинт ссылается на ключ именем `key_ref`, а сам ключ берётся из переменной окружения `ZA_SECRET_<KEY_REF>` (имя в верхнем регистре, `-` → `_`: `key_ref = "open-router"` → `ZA_SECRET_OPEN_ROUTER`). Облако не вызывается, пока ключ не задан: такой эндпоинт `inactive`. Моделью по умолчанию может быть только локальная. Раздел `[resources]` необязателен.

```toml
[models]
default = "local"

[[models.endpoints]]
id = "local"
backend = "llama_cpp"              # llama_cpp, vllm, openai_compatible, openrouter, anthropic, openai_responses, openai_chat
base_url = "http://127.0.0.1:8080" # llama.cpp — корень сервера; прочие — корень версии API (…/v1)
max_parallel = 2                   # не больше слотов сервера (-np)

[[models.endpoints]]
id = "claude"
backend = "anthropic"
model = "claude-sonnet-5-5"
key_ref = "anthropic"              # ключ — в ZA_SECRET_ANTHROPIC
daily_budget_usd = 5.0              # дневной предел расхода группы, USD
price = { input_per_mtok = 3.0, output_per_mtok = 15.0 }   # USD за миллион токенов; без price бюджет — ошибка (стоимость сообщает только openrouter)

[models.roles]
worker = "local"

[resources]                         # пороги допуска, МиБ; все поля необязательны
vram_reserve_mib = 1024             # запас VRAM для фоновых заданий
disk_margin_mib = 5120
nvidia_smi = "nvidia-smi"
```

Без раздела `[models]` и с `LLAMA_URL` используется один эндпоинт `local` по этому адресу.

```sh
zero-agent models                          # эндпоинты и состояние: ready, inactive, unreachable, probing, open, disabled; --json
zero-agent models probe local              # повторный зонд: контекст, слоты, квант, профиль в ZA_HOME/models
zero-agent ask --model local "Столица Франции?"   # ответ в stdout, usage в stderr; --priority interactive|top|worker|job
zero-agent resources                       # CPU, RAM, GPU/VRAM, тома, данные агента, очередь; --json, --watch
zero-agent doctor                          # + GPU и состояние каждой модели
```

`ask` на терминале печатает ответ по мере генерации; если стрим оборвался и запрос повторён, в stderr появляется пометка, а ответ печатается заново с новой строки. В конвейер или файл уходит только итоговый ответ. `models`, `ask` и `doctor` зондируют эндпоинты и сохраняют профили в `ZA_HOME/models`.

Коды выхода команд моделей: `0` — успех (у `models` — при любом состоянии эндпоинтов); `1` — ошибка конфигурации, неготовая модель (`ask`, `models probe`) или ошибка модели. Команды ждут первого зонда не дольше 35 с.

Живые проверки бэкендов: `LLAMA_TEST_URL=http://127.0.0.1:8080 cargo test -p za-llm --test live -- --ignored` (также `VLLM_TEST_URL`, `OPENROUTER_TEST_KEY`, `ANTHROPIC_TEST_KEY`, `OPENAI_TEST_KEY`, модель — `ZA_TEST_<PROVIDER>_MODEL`).

Тесты `Gateway` идут в реальном времени; на медленной машине длительности тестов растягивает `ZA_TEST_TIME_SCALE` (целое 1–6, по умолчанию 1, в CI — 4).

Логи пишутся в stderr, по умолчанию уровень `warn`. Фильтр задаётся `ZA_LOG` (приоритетнее) или `RUST_LOG`: например, `ZA_LOG=info` или `ZA_LOG=warn,za_store=debug`.

## Run (R1-B1)

`run` ведёт задачу через цикл агента: ходы модели, вызовы инструментов, пауза, продолжение. Журнал run — в `ZA_HOME/projects/<project_id>/journal.db`; каталог проекта должен существовать. Модель работает с проектом нативными инструментами (R1-C1): `read`, `search`, `edit`, `bash` (со всех тиров), `glob`, `multi_edit`, `request_grant` (с `standard`); спрашивает пользователя `ask_user` (тиры `standard` и `full`). Решения о вызовах принимает политика (раздел «Политика»), перед правкой и командой делается чекпоинт.

```sh
zero-agent run --project . "Ответь одним словом: столица Франции?"
#   stderr: run 019a…   stdout: Париж
zero-agent run --project DIR [--model ID] [--mode read-only|plan|ask|accept-edits|auto|bypass]
               [--work-mode coder|researcher|operator|writer] [--tier small|standard|full]
               [--max-wait СЕК] [--max-steps N] [--max-tokens N] [--max-usd USD] [--max-gpu-ms МС] [--max-duration СЕК]
               [--grant ПУТЬ[=ro|=rw]]… "<задача>"
zero-agent run --project DIR --resume RUN [--model ID] [--input "<текст>"] [--grant ПУТЬ[=ro|=rw]]…
               [--max-steps N] [--max-tokens N] [--max-usd USD] [--max-gpu-ms МС] [--max-duration СЕК]
zero-agent answer --project DIR --interrupt ID (--text "<ответ>" | --approve | --deny [--note "<текст>"] | --done | --not-done)
```

- Первая строка stderr — `run <id>`, раньше любых предупреждений и логов: по нему run продолжают. Строки нет, только если у `--resume` нет журнала проекта. Ответ модели идёт в stdout по мере генерации, в конце — перевод строки.
- Модель по умолчанию — `models.default`. Неготовый эндпоинт (`inactive`, `unreachable`, зонд не завершился) — причина в stderr и код 1, run не создаётся. Отказ модели посреди run (429, обрыв, сервер недоступен) ставит run на паузу с причиной `provider`.
- Тир промпта выбирается по размеру контекста модели: меньше 32768 — `small`, меньше 65536 — `standard`, иначе `full`; `--tier` его переопределяет. `--max-wait` — предел ожидания в очереди к модели; без него заявка ждёт сколько нужно, по истечении — пауза `queue` или `resource`. `AGENTS.md` проекта (без него — `CLAUDE.md`) входит в промпт в пределах лимита роли, только если проект доверен (раздел «Доверие к проекту»); прежний флаг `--agents-md` удалён — он печатает подсказку и выходит с кодом 2.
- `--grant ПУТЬ[=ro|=rw]` — доступ вне проекта на этот run (по умолчанию `ro`; `=` — потому что `:` входит в путь Windows); флаг можно повторять, с `--resume` грант добавляется к грантам run. Гранты глобального `[[policy.grants]]` действуют так же. Путь канонизируется при старте; сетевой путь — ошибка, код 1. Вызов, исполненный с путём вне проекта, печатается строкой `zero-agent: вне проекта: <инструмент> <доступ> <путь>`.
- `--mode bypass` — только при `[policy] allow_bypass = true` глобальной конфигурации, иначе ошибка конфигурации и код 1.
- Ctrl+C — пауза run в безопасной точке: стрим модели обрывается, идущий инструмент дорабатывает, run встаёт в `paused` (`command`). Второй Ctrl+C — выход сразу, без ожидания паузы (код 4); `--resume` такой run продолжит.
- Модель спросила пользователя или ждёт одобрения — run на паузе, в stderr вопрос (у одобрения — инструмент, аргументы до 400 символов с маской секретов, причины и пути вне проекта) и строка `zero-agent: ответьте: zero-agent answer --interrupt <id> …`. `answer` записывает ответ и выходит, цикл продолжает `run --resume`.
- `--resume` продолжает run после паузы, после `blocked_on_budget` и после аварийного завершения процесса: шаг, оборванный сбоем, повторяется по журналу, и запрос к модели совпадает с прерванным байт в байт. `--model` меняет модель только на границе шага. `--input` добавляет сообщение пользователя.

Коды выхода `run`:

| Код | Значение |
|---|---|
| 0 | run `done` или `partial` |
| 1 | ошибка или `failed` (в stderr `zero-agent: run завершился ошибкой: <причина>`); в том числе неизвестный run у `--resume`, неготовая модель |
| 2 | удалённый флаг `--agents-md` |
| 3 | нужно решение пользователя: ответ на вопрос (`needs_input`), одобрение (`needs_approval`), доверие к проекту (`needs_trust`), неизвестный исход действия (`needs_decision`) |
| 4 | прочая пауза (`provider`, `queue`, `resource`, `command`, `context`, `model_loop`, `tool_errors`, …) или `blocked_on_budget` |
| 5 | `blocked`: модель трижды подряд ответила пустым ходом, повторяет один и тот же вызов, ходит по кругу или не продвигается (раздел «Детекторы отказов») |
| 6 | `cancelled` |

Аварийное завершение процесса (`abort`) кода из таблицы не даёт: на Windows это `0xC0000409` (STATUS_STACK_BUFFER_OVERRUN, `__fastfail`), на Unix — сигнал SIGABRT. Настоящее «нужно решение» отличает строка `zero-agent: ответьте:` в stderr.

У `answer` код 0 — ответ записан; 1 — нет журнала или прерывания, вид ответа не подходит к прерыванию (`--text` — для `input-…`, `--approve`/`--deny` — для `appr-…` и `trust-…`, `--done`/`--not-done` — для `unk-…`) или прерывание уже решено.

## Бюджеты run (R1-B1)

Пределы расхода run по умолчанию задаёт раздел `[budgets.run]` того же `ZA_HOME/config.toml`. Все поля необязательны, поле без значения — без предела. Незнакомое имя поля — ошибка конфигурации: опечатка не снимает ограничение молча.

```toml
[budgets.run]
tokens = 200000        # input + output всех вызовов модели (input включает кэш)
gpu_ms = 600000        # время GPU, мс
usd = 2.0              # стоимость, USD
steps = 50             # ходов модели: 50-й ход последний
duration_ms = 1800000  # активное время run, мс: время в паузе не считается
```

Флаги `run` задают пределы поверх `[budgets.run]`, по одному на поле: `--max-steps` — `steps`, `--max-tokens` — `tokens`, `--max-usd` — `usd` (конечное неотрицательное число), `--max-gpu-ms` — `gpu_ms`, `--max-duration СЕК` — `duration_ms` (в секундах). Каждый флаг задаёт предел на весь run, включая уже потраченное, а не прибавку: run, остановленный на 20 шагах, с `--resume --max-steps 30` сделает ещё 10. Бюджет фиксируется при старте run и хранится в его снимке. `run --resume` без флагов бюджета продолжает с тем же бюджетом; `[budgets.run]` при продолжении не перечитывается. С флагами они меняют свои поля поверх текущего бюджета run, остальные пределы сохраняются. Так run в `blocked_on_budget` продолжают с новым пределом исчерпанного вида: подсказка в stderr называет нужный флаг (`run --resume <id> --max-steps 100`, `--max-duration 3600`, `--max-usd 5`).

Бюджет проверяется на границе шага, до начала следующего хода и до чтения нового ввода. `steps` ограничивает число ходов: при `steps = 2` третий ход не начинается. Остальные пределы срабатывают, когда расход их превысил; равенство пределу — ещё не превышение. Превышение записывается событием `budget.exceeded {kind, used, limit}` и переводит run в `blocked_on_budget`. Ввод, пришедший во время последнего хода, не теряется: его прочитает граница после продолжения run с новым бюджетом. Дневной бюджет облачной группы по-прежнему задаётся `daily_budget_usd` у эндпоинта в `[models]`.

## Контекст (R1-B2)

Раздел `[context]` того же `ZA_HOME/config.toml` задаёт тир run и пороги разгрузки контекста. Все поля необязательны. Незнакомое имя поля или значение вне диапазона — ошибка конфигурации.

```toml
[context]
tier = "standard"   # small | standard | full; без поля — по размеру окна модели
compact_at = 0.75   # компакция истории при заполнении окна, 0.70–0.80
prune_at = 0.65     # удаление старых результатов инструментов, меньше compact_at
spill_share = 0.15  # предел вывода инструмента в контексте, доля окна, 0.15–0.20
```

Флаг `--tier` важнее `[context].tier`. Раздел фиксируется при старте run и хранится в его снимке: `run --resume` продолжает с теми же значениями, даже если конфигурация изменилась.

По окну модели тир выбирается так: меньше 32k — `small`, от 32k — `standard`, от 64k — `full`. Тир `standard` или `full` на окне меньше 32k бывает только явно (`--tier`, `[context].tier`): описания его инструментов (нативные, веб, `activate_skill` с каталогом скиллов) не помещаются в слот окна, на модель остаётся мало места. На старте такого run, на `run --resume --model` с моделью меньшего окна и в `doctor` (строка `window`) печатается предупреждение; run при этом идёт. Окно модели неизвестно — run считает его 8192, и при явном `standard` или `full` предупреждение то же (с пометкой «окно модели неизвестно»).

Заполнение окна считается так: оценка запроса хода плюс резерв вывода хода сравнивается с долей окна. Оценка — расход прошлого хода (`usage`) плюс новые сообщения; новые сообщения у llama.cpp считает `/tokenize`, у остальных — байты / 4. Если провайдер не сообщает расход, оценивается весь запрос. Резерв — лимит вывода хода: не меньше бюджета мышления тира плюс 1024 токена на ответ. Если размер окна модели неизвестен, run считает его равным 8192 и пишет событие `context.alert {kind: "n_ctx_unknown"}`. Если сервер принял заметно меньше токенов, чем оценка запроса (меньше половины), run пишет `context.alert {kind: "truncation_suspected"}`: сервер, вероятно, запущен с меньшим окном и срезал начало промпта.

Вывод инструмента длиннее `spill_share` окна (в байтах — доля × размер окна × 4) остаётся в контексте началом и концом, а полный текст ложится в `.zero-agent/work/spill/` проекта; строка между ними называет файл: `… omitted N lines; search .zero-agent/work/spill/<id>.txt`. Каталог `.zero-agent/work/` получает `.gitignore` и в git не попадает. При заполнении окна до `prune_at` результаты инструментов старше последних 4 ходов и длиннее 1024 байт заменяются ссылкой на файл с полным текстом (событие `context.pruned`).

При заполнении окна до `compact_at` история сжимается (событие `context.compacted`). Модель пишет сводку: решения, изменённые файлы, ошибки и следующий шаг. Цель run и сообщения пользователя добавляет в сводку сам run, дословно. Дальше run продолжает с короткой историей: `<env>`, сводка, последний запрос или последний ход модели и напоминание о текущей задаче. Если сервер отвечает, что запрос не помещается в окно, run сжимает историю по усечённому входу и повторяет ход один раз; повторный отказ или повторная обрезка ставят run на паузу `context`. Если после сжатия окно всё ещё заполнено выше порога, run пишет `context.alert {kind: "compaction_insufficient"}` и не сжимает историю на каждом шаге, пока запрос помещается в окно. `run --resume` на модель с меньшим окном пишет `context.alert {kind: "n_ctx_changed"}` и сжимает историю на первом шаге.

## Детекторы отказов (R1-B2)

Run следит, не зациклилась ли модель, и не даёт ей тратить бюджет впустую. Каждое срабатывание пишется в журнал событием `loop.detected {detector, action, turn}`; подсказки модели идут в её историю на английском.

| Что случилось | Что делает run | Что видит пользователь |
|---|---|---|
| Тот же вызов с теми же аргументами (после правки или ввода пользователя счёт начинается заново) | 2-й раз — прошлый результат с пометкой, без выполнения; 3-й — отказ; 4-й — отказ и подсказка сменить подход; 5-й — стоп | код 5, `blocked` |
| Ходы по кругу (A, B, A, B или A, B, C, A, B, C) без новых результатов | подсказка «остановись и смени подход» и напоминание задачи; повтор в ближайшие 6 ходов — стоп | код 5, `blocked` |
| 8 ходов подряд без прогресса (нет новых результатов, правок, успешных команд, ответа) | стоп | код 5, `blocked` |
| Модель повторяет один и тот же текст в стриме | стрим обрывается, ход повторяется с другими параметрами выборки; второй раз в шаге — пауза | код 4, пауза `model_loop` |
| Рассуждение без конца (сверх бюджета мышления или дольше тайм-аута без ответа) | стрим обрывается, ход повторяется без рассуждения; второй раз — пауза | код 4, пауза `model_loop` |
| «Сейчас сделаю», но без вызова инструмента | подсказка сделать вызов; второй такой ответ подряд принимается как ответ | обычный ответ |
| Инструменты одного класса ошибаются подряд | после 3-й, 4-й и 5-й ошибки — пауза 1, 2 и 4 с; 6-я — пауза run | код 4, пауза `tool_errors` |
| 3 хода подряд с испорченным JSON вызовов | аварийное сжатие истории; ещё 2 таких хода — пауза | код 4, пауза `model_loop` |
| Доля кэша промпта упала вдвое без сжатия истории | событие `context.alert {kind: "cache_drop"}` и предупреждение в лог: префикс запроса изменился или сервер вытеснил кэш | только журнал |
| Запрос не помещается в окно даже после сжатия, или сервер снова срезал промпт | пауза | код 4, пауза `context` |

Как продолжить:

- Пауза (`model_loop`, `tool_errors`, `context`) — `zero-agent run --project DIR --resume RUN`. Подсказку модели можно передать сразу: `--input "<что сделать иначе>"`; ввод пользователя сбрасывает счёт повторов. После паузы `model_loop` run начинает шаг заново, после `tool_errors` счёт ошибок класса начинается с нуля.
- Пауза `context` — окна модели не хватает: продолжите на модели с большим окном (`--resume RUN --model ID`; на первом шаге история сожмётся под новое окно) или запустите сервер с большим `n_ctx`.
- `blocked` — конечный статус, `--resume` его не продолжает. Посмотрите, на чём застряла модель (`zero-agent inspect`, события `loop.detected` в журнале), и начните новый run с уточнённой задачей.

## Инспектор и метрики (R1-B2)

`inspect` показывает, из чего состоял запрос хода к модели, `stats` — метрики run. Обе команды только читают журнал проекта и не меняют run; их можно запускать после завершения run или во время паузы (пока run идёт, журнал занят его процессом).

```sh
zero-agent inspect --project DIR --run RUN [--turn N] [--raw | --json]
zero-agent stats --project DIR --run RUN [--json]
```

- `inspect` восстанавливает запрос хода `N` (без `--turn` — последнего) по журналу и сверяет его хэш с записанным: запрос совпадает с отправленным байт в байт. Таблица — блоки запроса по порядку сборки: описания инструментов (`tools`), Core (`core`), адаптер модели (`adapter`), overlay режима (`overlay`), `AGENTS.md` (`agents_md`), первое сообщение с `<env>` и задачей (`first_message`), диалог (`dialog`) и напоминания рантайма (`control`). У каждого блока — байты, оценка токенов (байты / 4) и начало хэша. Под таблицей — оценка запроса, расход, который сообщил провайдер, и оценка следующего хода. У run, начатых до R1-B2, Core, адаптер, overlay и `AGENTS.md` показаны одной строкой `system`. Ход, повторённый после переполнения окна, показывается последней попыткой.
- `--raw` печатает точное тело запроса, которое ушло бы провайдеру, тем же кодом, что и `run`: модели из `config.toml` запускаются, ключи и заголовки в вывод не попадают. Тело строится по текущей конфигурации и профилю эндпоинта, а не по их состоянию во время хода: если модель или её настройки с тех пор менялись, тело может отличаться от ушедшего. У llama.cpp в теле нет `id_slot`: слот выбирается при отправке.
- `--json` — те же данные в JSON (`turn`, `endpoint`, `blocks`, `estimate`, `input`, `n_ctx`, `next_turn`).
- `stats`: ходы и шаги (шаг — каждый запрос хода к модели, включая повторы), токены входа, из кэша и доля кэша, выход, время до первого токена (p50 и p95), средняя скорость вывода, ошибки модели по классам, ремонт вызовов инструментов, число компакций, стоимость.

Журнал проекта, записанный более старой версией, при первом открытии командой переводится на текущую схему (один раз, только вперёд); сами события run не меняются.

Коды выхода: 0 — готово; 1 — нет журнала проекта, run или хода, запрос не восстанавливается по журналу, тело запроса не построено (модель не настроена или ещё ни разу не зондирована).

## Инструменты и граница проекта (R1-C1)

Модель работает с проектом нативными инструментами. Описания одинаковы на всех ОС; маленькой модели (тир `small`) даются только первые четыре.

| Инструмент | Что делает | Тир |
|---|---|---|
| `read(path, start, limit)` | строки файла с номерами (до 500 строк за вызов); двоичный файл — тип и размер; несуществующий путь — до трёх похожих имён | все |
| `search(pattern, path, glob)` | регулярное выражение по файлам проекта с учётом `.gitignore`, до 200 совпадений `путь:строка:текст` | все |
| `edit(path, old, new, allow_shrink)` | замена фрагмента; пустой `old` создаёт файл. Файл должен быть прочитан в этом run и не измениться после чтения. BOM, переводы строк и права сохраняются, файл не в UTF-8 не правится, удаление больше половины строк — только с `allow_shrink` | все |
| `bash(cmd, cwd, timeout)` | команда в PowerShell на Windows, в bash на Linux и macOS; результат — `exit code: N`, stdout и stderr. Тайм-аут (по умолчанию 120 с, не больше 600 с) и фоновые потомки убивают всё дерево процессов | все |
| `glob(pattern)` | пути по шаблону, до 500 | `standard` |
| `multi_edit(path, edits)` | несколько замен в одном файле: все или ни одной | `standard` |
| `request_grant(path, mode, reason)` | просьба о доступе вне проекта, решает пользователь | `standard`, только top |

Каталоги `.git` и `.zero-agent` инструменты не обходят. Рабочие файлы агента (временные каталоги команд, выгрузка длинных выводов, маркеры правок) лежат в `<проект>/.zero-agent/work/` с `.gitignore` `*`; переменные `TMP`, `TEMP`, `TMPDIR` команд указывают туда же.

**Что видит пользователь.** Первая строка stderr `run` — `run <id>`. Вызов, исполненный с путём вне проекта, печатается строкой `zero-agent: вне проекта: <инструмент> <read|write> <путь>` — на каждый путь, в том числе по гранту. Когда нужно решение, run встаёт на паузу (код 3) и печатает, о чём вопрос, затем `zero-agent: ответьте: zero-agent answer --interrupt <id> --project <P> <флаги>` и `zero-agent: продолжить: zero-agent run --project <P> --resume <run>`. Ответ записывает `answer`, работу продолжает `run --resume`.

**Какие вопросы задаёт агент:**

| Вопрос | Когда | Что в stderr | Ответ |
|---|---|---|---|
| Одобрить вызов (`appr-…`, пауза `needs_approval`) | режим требует подтверждения (`ask` — правки и команды, `accept-edits` — команды); путь вне проекта без гранта (`outside_project`, в любом режиме, и в `bypass`); необратимая или неразобранная команда (`irreversible`, всегда); правило `ask` | `вызов: <инструмент> <аргументы>`, `причины: mode, rule, outside_project, irreversible`, `необратимо: delete, git_reset…`, строки «вне проекта» | `--approve` — один этот вызов; `--deny [--note "<текст>"]` — модель получает `denied by user: <текст>` |
| Выдать грант (`appr-…`, причина `grant`) | модель вызвала `request_grant` | `модель просит грант: <ro\|rw> <путь>: <причина>` | `--approve` — грант до конца run; `--deny` |
| Доверить проект (`trust-…`, пауза `needs_trust`) | первая команда `bash` в недоверенном проекте | `нужна команда в недоверенном проекте <P>: доверить проект один раз? доверенные файлы: …` | `--approve` — один раз на проект; `--deny` — команды этого run получают `denied: untrusted project`, нового вопроса нет |
| Исход неизвестен (`unk-…`, пауза `needs_decision`) | процесс агента упал, пока шла команда: выполнена ли она, неизвестно | подсказка `answer … --done \| --not-done` | `--done` — считать выполненной, `--not-done` — нет; команда сама не повторяется |
| Вопрос модели (`input-…`, пауза `needs_input`) | модель вызвала `ask_user` | `вопрос модели: …` | `--text "<ответ>"` |

Без вопросов агент отказывает (модель получает текст отказа, run продолжается): любой доступ к защищённым местам памяти `ZA_HOME` и `~/.zeroaimemory/` и запись в `.zero-agent/` проекта, `.git/`, `.zeroaimemory/` проекта (`denied: protected path`), вызов клиента памяти `zam` в `bash` (`denied: memory client`, раздел «Безопасность памяти»), правило `deny` (`denied: policy rule`), запрет режима (`read-only`, `plan`), сетевые и device-пути Windows (`\\server\share`, `\\.\…`, `CON`, потоки `a:b`) — они отклоняются до обращения к диску. Чтение по сети (`curl`, `git pull`) и файлов вне проекта помечает результат `[untrusted content: …]` и событие `tool.finished` (`tainted`), но вопросов к следующим командам не добавляет.

**Граница проекта и гранты.** Читать и писать вне каталога проекта нативные инструменты могут только по гранту — `run --grant <путь>[=ro|=rw]` или глобальный `[[policy.grants]]` (раздел «Политика») — или с одобрением этого вызова. Грант `ro` даёт только чтение нативными инструментами (`read`, `search`, `glob`). Команда `bash` с внешним путём, даже `cat <путь>`, может туда писать, поэтому её покрывает только грант `rw`; с `ro` она спрашивается (`outside_project`). Грант `rw` даёт ещё запись нативными инструментами и команды с этим путём. Пути в командах `bash` (абсолютные, `..`, `~`, `$HOME`, `${HOME}`, `%USERPROFILE%`, `$env:USERPROFILE`, `cd`, `git -C`) распознаются по разобранной команде (best effort: прочие переменные не раскрываются). Путь с началом домашнего каталога (`~`, `$HOME` и др.) раскрывается по вашему домашнему каталогу и всегда считается путём вне проекта — грант его не покрывает, в режиме `auto` команда спрашивает (R1-M). Ссылки и junction внутри проекта, ведущие наружу, считаются путями наружу, в том числе созданные командой того же ответа модели. Каждая попытка доступа наружу остаётся в журнале: исполненная — событием `boundary.outside {call_id, tool, paths: [{path, access, granted}]}`, ушедшая на вопрос — путём и причиной в прерывании (`interrupt.opened`). Гранты пишутся в аудит (`grant.added`). ОС-изоляции на этом этапе нет: граница держится на решениях агента и журнале.

**Чекпоинты.** Перед каждой правкой (`edit`, `multi_edit`) и командой (`bash`) агент сохраняет состояние рабочей копии (событие `checkpoint.created {call_id, id, kind}`), id — `<run>/<шаг>-<номер>`.

```sh
zero-agent checkpoints list --project DIR [--json]                 # id, вид (git или files), коммит
zero-agent checkpoints restore --project DIR <id> [--delete-new] [--json]
```

- В доверенном проекте с `.git` в корне чекпоинт — коммит в собственном голом репозитории агента `ZA_HOME/projects/<project_id>/checkpoints/repo.git`. Репозиторий пользователя не используется: HEAD, индекс, stash, ветки и `refs` проекта не меняются, его хуки, фильтры и конфиг не исполняются. Игнорируемые файлы (`.gitignore`) в чекпоинт не входят, правимый файл входит всегда (кроме секретного, см. ниже); файлы больше 64 МиБ пропускаются. Прочие файлы рабочей копии, в том числе неотслеживаемые, копируются в репозиторий чекпоинтов агента как есть. Git дольше 20 с — чекпоинт пропускается (`slow`) до конца run.
- Без git, без `.git` в корне или в недоверенном проекте правка сохраняет прежнее содержимое затронутых файлов копией в `ZA_HOME` (`files`); у команды тогда чекпоинта нет (`skipped`, причина `no_git` или `git_not_found`).
- `restore` сначала делает чекпоинт «до» (без него не восстанавливает), затем возвращает файлы. Файлы, которых не было в чекпоинте, удаляются только с `--delete-new`. Восстановление пишется в аудит (`checkpoint.restored`). Чекпоинты git видны и восстанавливаются только у доверенного проекта.

**Секреты в чекпоинтах (R1-C2).** Секретные файлы в чекпоинт не входят — ни в git, ни в копию файлов:

- по имени (без учёта регистра): `.env` и `.env.*`, кроме `.env.example`, `.env.sample`, `.env.template`, `.env.dist`; `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.kdbx`, `*.ppk`; `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519` (`.pub` — не секрет); `.netrc`, `_netrc`, `.npmrc`, `.pypirc`, `.git-credentials`;
- по содержимому — файл до 1 МиБ, в котором есть значение одного из секретов `ZA_SECRET_*` (от 8 символов), блок закрытого ключа PEM (`-----BEGIN … PRIVATE KEY-----`), закрытый ключ PGP (`-----BEGIN PGP PRIVATE KEY BLOCK-----`) или ключ PuTTY (файл начинается с `PuTTY-User-Key-File-`). Шаблоны вроде `api_key = …` файл чекпоинта не лишают.

Такой файл правится без чекпоинта: модель получает строку `[no checkpoint for this file: it looks like a secret]` (при любом исходе вызова, в том числе при ошибке), событие `checkpoint.created` — поле `secret_skipped`. Восстановление не перезаписывает и не удаляет (и с `--delete-new`) файл, который секрет по имени или сейчас по содержимому, в том числе из чекпоинтов, сделанных до R1-C2; такие файлы `checkpoints restore` перечисляет в stderr («не тронуты как секреты»), в `--json` и в записи аудита — поле `secret_untouched`. Diff правки в маркере повтора (`ZA_HOME/projects/<project_id>/edits/`) хранится с маской секретов. Это дополнительный слой: остальные файлы с секретами по-прежнему копируются, исключайте их в `.gitignore`.

**Старые чекпоинты.** Секреты, попавшие в репозиторий чекпоинтов до R1-C2, в нём остаются. Чтобы убрать их, удалите каталог `ZA_HOME/projects/<project_id>/checkpoints/` вручную, когда run этого проекта не идёт (все прежние чекпоинты проекта пропадут). Команда очистки (`checkpoints prune`) — в R1-D. Каталог доступен только владельцу (на Unix права 0700).

**Секреты в выводе.** Значения `ZA_SECRET_*` и ключи известных форматов в выводе инструментов (`cat .env`, `env`, `git config -l`), в ответе и аргументах модели заменяются на `[secret masked: …]` до записи в журнал, выгрузку длинного вывода и контекст модели (раздел «Секреты»). Командам `bash` переменные `ZA_SECRET*`, `ZA_MEMORY_*` и `ZAM_*` не передаются.

## Доверие к проекту (R1-C1)

Чужой проект может подложить инструкции модели (`AGENTS.md`, `CLAUDE.md`), правила политики (`.zero-agent/config.toml`) и скиллы (`.zero-agent/skills/`, `.agents/skills/`, `.claude/skills/`). Пока проект не доверен, `run` их не читает, а команды `bash` не выполняет: первая команда ставит run на паузу `needs_trust` (код 3) с вопросом о доверии. Чтение файлов и правки идут по режиму.

```sh
zero-agent trust --project DIR [--revoke]
zero-agent answer --project DIR --interrupt trust-… (--approve | --deny)
```

- Доверие даётся один раз: `trust` заранее или ответ `--approve` на вопрос. В журнал аудита пишется `trust.granted` с хэшами доверенных файлов. После доверия команды идут по режиму: в `auto` — без вопросов, кроме необратимых и путей вне проекта. `--deny` — команды этого run получают отказ без нового вопроса.
- Каждый `run` пересчитывает хэши: если доверенный файл изменился, появился или удалён, проект снова не доверен, а stderr называет файлы (`изменены: AGENTS.md`). `trust --revoke` отзывает доверие (`trust.revoked`); отзыв действует и на продолжаемый run.
- Доверенный проект даёт `AGENTS.md` (без него — `CLAUDE.md`) в промпт и правила `ask` и `deny` своего `.zero-agent/config.toml`. Доверие посреди run промпт не меняет: инструкции проекта подхватит следующий run.
- Без доверия чекпоинты git не делаются и не читаются: правки сохраняются копиями файлов в `ZA_HOME`.
- При продолжении run сверяется журнал аудита: если запись, сохранённая в снимке run, исчезла или изменилась, `run --resume` выходит с кодом 1 и подсказкой `zero-agent audit --verify`.

## Аудит и выгрузка журнала (R1-C1)

Одобрения вызовов и доверие к проекту пишутся в журнал аудита проекта (таблица `audit` в `journal.db`). Записи связаны hash-цепочкой BLAKE3: подмена или удаление записи в середине обнаруживается проверкой.

```sh
zero-agent audit --project DIR [--verify] [--json]
zero-agent journal export --project DIR --run RUN
zero-agent answer --project DIR --interrupt trust-… (--approve | --deny)
```

- `answer` на одобрение (`appr-…`) пишет запись `approval.resolved`. Ответ на прерывание доверия к проекту (`trust-…`): `--approve` пишет ещё `trust.granted` с хэшами доверенных файлов проекта (`AGENTS.md`, `CLAUDE.md`, `.zero-agent/config.toml`, деревья скиллов) на момент ответа, `--deny [--note]` — только отказ. Если доверенные файлы изменились после вопроса, доверие не записывается: `answer` открывает новое прерывание с текущим набором, печатает его id и выходит с кодом 3. Ссылка на файл внутри проекта учитывается по содержимому цели; ссылка наружу, на сетевой путь и каталоги-ссылки (junction) не читаются и отмечаются в наборе. Решение и запись аудита сохраняются вместе или не сохраняются вовсе.
- `audit` печатает записи: номер, время UTC, кто, действие, объект, данные (`--json` — строка JSON на запись). `--verify` только проверяет цепочку. Разрыв цепочки — сообщение `разрыв цепочки аудита на записи N` и код 1.
- `journal export` печатает события run строками JSON по порядку. Секреты маскируются: значения переменных `ZA_SECRET_*` (от 8 символов) заменяются на `[secret masked: <имя>]`, а ключи и токены известных форматов (`sk-…`, `ghp_…`, `AKIA…`, `xox?-…`, `AIza…`, `glpat-…`, `hf_…`, `gsk_…`, `xai-…`, JWT, токен после `Bearer`), приватные ключи PEM и пароли в URL и строках подключения — на `[secret masked: <вид>]`, даже если переменных в окружении выгрузки нет. Так же маскируются записи `audit` и ответ, который печатают `run` и `ask`.
- Пока run идёт, его процесс держит журнал: `audit` и `journal export` печатают «журнал проекта занят запущенным run; повторите после его остановки» и выходят с кодом 1.

## Rule of Two: экспозиция run (R1-C2)

Агент следит за тремя свойствами run: в контексте есть недоверенное содержимое (прочитанное из сети, вывод инструментов с меткой, недоверенный проект), исполнен нативный вызов с путём вне проекта (ваши файлы, в том числе по гранту), исполнен нативный сетевой вызов (`web_search`, `web_fetch`). Команды `bash` и правки внутри проекта в эти свойства не входят.

- **Вопросов это не добавляет.** По решению заказчика 2026-11-11 сочетание всех трёх свойств вызов не останавливает: он идёт по режиму, как без правила. Требование SEC-052 «третье свойство — только через человека» и требование SEC-053 о подтверждении в tainted-контексте этим решением отменены (ADR 0006). Защита — режимы, гранты, доверие к проекту и правила по домену; эксфильтрация командой или нативными вызовами не предотвращается. Запись аудита получает только вызов с внешней связью (ниже); у команды, которую разбор считает локальной, её нет.
- **Что записывается.** Изменение свойств после пакета вызовов — событие журнала `exposure.changed {untrusted, private, external, calls, rule_of_two}`; свойства хранятся в снимке run (v4) и сбрасываются только новым run.
- **Запись аудита.** Каждый вызов с внешней связью, который исполняется при всех трёх свойствах, получает запись аудита `rule_of_two` (`call_id`, инструмент, свойства, ключ эффекта). Внешняя связь — у сетевых инструментов (`web_fetch`, `web_search`) и у команды `bash`, которая обращается к сети или не разобрана. Чтение и правка в проекте, команда `bash`, которую разбор считает локальной, и `finish` записи не получают. Это не значит, что через них данные наружу не уходят: «локальная» команда вроде `python x.py` может сама передать данные в сеть, а записи у неё нет. Run, где наружу выходит только `bash`, без нативного сетевого вызова, трёх свойств не набирает: `bash` в свойства не входит. Это принятый риск — граница shell соблюдается по мере возможности (best effort, SEC-002; ADR 0006). Свойства вызова — это свойства на начало пакета вызовов плюс то, что даёт сам вызов: чтение по гранту, затем `web_fetch`, затем ещё `web_fetch` — две записи. Запись делается до вызова, поэтому отмена посреди вызова её не теряет. Записи видно в `zero-agent audit`. Если запись не удалась, вызов не исполняется, а run встаёт на паузу `store`, как при сбое записи гранта.
- **Что видно в stderr.** Один раз за run, в том числе после `--resume`: `zero-agent: в этом запуске сошлись недоверенное содержимое, ваши файлы вне проекта и обращение в сеть (SEC-052); вызов выполнен, запись в аудите`.

## Секреты (R1-C1)

Секреты агента — ключи провайдеров из переменных окружения `ZA_SECRET_<KEY_REF>`. Они читаются один раз при старте команды. Дочерним процессам (команды `bash`, git, `nvidia-smi`) переменные `ZA_SECRET*` не передаются, как и переменные памяти `ZA_MEMORY_*` и клиента `zam` `ZAM_*` (R1-M). Хранение в разделе Vault памяти ZeroAIMemory появится вместе с клиентом памяти; конфигурация при этом не меняется.

```sh
zero-agent secret list
```

Известный секрет в аргументах вызова модели маскируется до вызова: инструмент получает `[secret masked: <имя>]`, а не значение, и у `web_fetch` сайт получает адрес с маской. Это защита от утечки: передать значение `ZA_SECRET_*` наружу через аргументы модель не может. Файл инструкций проекта (`AGENTS.md` или `CLAUDE.md`) до системного промпта проходит ту же маску (R1-M, раздел «Безопасность памяти»).

`secret list` печатает имена секретов (`key_ref` из `config.toml` и переменные `ZA_SECRET_*`), имя переменной и отметку «задан» или «не задан». Значения не печатаются. Значение короче 8 символов маска не ищет: `secret list` помечает его, а `doctor` даёт предупреждение. `doctor` показывает строку `secrets` с источником секретов, а также `git` (есть ли git в `PATH` и его версия: без git чекпоинты — копиями файлов) и `shell` (оболочка инструмента `bash`).

## Политика (R1-C1)

Решение о каждом вызове инструмента принимает политика: разрешить, спросить пользователя или отказать. Правила и гранты задаёт раздел `[policy]` глобального `ZA_HOME/config.toml`. Незнакомое поле, неверное значение или шаблон — ошибка конфигурации с путём поля, например `config.toml: policy.rules[0]: неизвестное поле`.

```toml
[policy]
allow_bypass = false          # режим bypass разрешён только при true

[[policy.rules]]
action = "deny"               # allow | ask | deny
command = "git push*"         # команда: deny и ask — имя команды или текст любой части

[[policy.rules]]
action = "allow"
command = "cargo test"        # allow — только если каждая часть команды совпала, без $(…), `…` и перенаправлений

[[policy.rules]]
action = "ask"
tool = "edit"
path = "migrations/**"        # путь внутри проекта — относительно корня через /

[[policy.rules]]
action = "deny"
domain = "*.example.com"      # хост: поддомены, но не сам example.com; только deny и ask

[[policy.grants]]             # доступ вне проекта
path = "D:/datasets"          # абсолютный путь; ~ и переменные не раскрываются
mode = "ro"                   # ro — чтение нативными инструментами (по умолчанию), rw — ещё запись и команды bash с этим путём
reason = "наборы данных"
```

- Правило срабатывает, если совпали все заданные поля `tool`, `path`, `command`, `domain`; хотя бы одно обязательно. Шаблоны — glob: `*` внутри одного каталога, `**` — через каталоги. Путь сверяется после разрешения ссылок и `..`, на Windows без учёта регистра. Абсолютный шаблон действует на любой путь, относительный — только внутри проекта.
- Порядок решения: встроенные запреты — любой доступ к `ZA_HOME` и `~/.zeroaimemory/`, запись в защищённое место (`.zero-agent/` проекта кроме `.zero-agent/work/`, `.git/`, `.zeroaimemory/` проекта), вызов `zam` в `bash` — отказ; их нет в снимке и хэше политики, правила, гранты и `bypass` их не снимают; любое правило `deny` — отказ; запрет режима (`read-only`, `plan`) — отказ; команда в недоверенном проекте — вопрос о доверии один раз, после отказа — `denied: untrusted project`. Затем собираются причины вопроса: режим, правило `ask`, путь вне проекта, необратимая команда. Прочитанное из сети или вне проекта помечается в журнале (`tainted`), но вопросов к следующим командам не добавляет.
- Чтение и запись вне проекта — только по гранту или глобальному правилу `allow` с подходящим `path`, иначе вопрос (`outside_project`). Грант `/data` не покрывает `/data2`. Путь в команде bash считается записью: его покрывает только грант `rw`. Путь с `~` в команде спрашивается всегда; `ZA_HOME` и `~/.zeroaimemory/` — отказ при любом доступе (R1-M).
- Необратимые команды (`rm -rf`, `git reset --hard`, `git push --force`, публикация и другие, а также команда, которую разбор не понял) спрашиваются всегда, в любом режиме.
- Глобальное `allow` снимает только вопрос режима. Для команд bash действует лишь правило с `command`: правило только по `tool` или `path` команду не разрешает. Необратимость и неразобранную команду `allow` не снимает.
- Правило `deny` или `ask` с `command` сверяется и с нормализованной командой: без `sudo`, `env`, `timeout`, пути и `.exe`, имя без регистра, слова шаблона после имени — по порядку среди аргументов (`git push*` ловит `git -C . push`). `deny` с `path` сверяется и со всеми словами команды bash (`cat .env`): с целями перенаправлений, со значениями опций (`--file=…`, `-Path:…`, `of=…`) и со словами, начало которых `~`, `$HOME`, `${HOME}`, `%USERPROFILE%`, `$env:USERPROFILE` раскрыто по вашему домашнему каталогу (`deny path="/home/u/.ssh/**"` ловит и `cat ~/.ssh/id_rsa`, и `rg --file=$HOME/.ssh/x`).
- Правило по домену (`domain`, R1-C2) сверяется с хостом вызова: у команды bash — с хостами её сетевых частей (URL у `curl`, `wget` и подобных, `ssh`, `scp`, `sftp`, `rsync`, адрес репозитория у `git clone|fetch|pull|push|ls-remote|remote add`), у `web_fetch` — с хостом страницы. Шаблон и хост сравниваются после нормализации: без учёта регистра, без последней точки, имена не из ASCII — в punycode (`пример.рф` и `xn--e1afmkfd.xn--p1ai` — один хост). `deny` с совпавшим хостом — отказ, `ask` — вопрос. `allow` с `domain` ничего не разрешает. Если хост команды определить нельзя (`curl $URL`, `ssh -J`, `curl --resolve`, `--proxy`, адрес git `<транспорт>::…`, сокет `/dev/tcp`, неразобранная команда), при подходящем правиле `deny` или `ask` по домену команда спрашивается (причина `rule`); без правил по домену такой команде вопрос не задаётся. Опции сетевых утилит разбираются строго по их известному набору: незнакомая или сокращённая опция (`wget --exec=…`, `iwr -Prox:…`) тоже делает хост неизвестным. Так же — глобальная опция git вне известного набора (тогда и подкоманда неизвестна: команда считается сетевой и спрашивается как неразобранная), ключ `git -c` вне короткого списка безопасных (`user.*`, `core.autocrlf`, `color.*`, `advice.*` и подобные; `http.*`, `url.*`, `remote.*`, `core.sshCommand` — неизвестный хост), ключ `-o` у `ssh`, `scp`, `sftp` вне списка безопасных (`Port`, `User`, `IdentityFile`, `StrictHostKeyChecking`, `BatchMode`, `ConnectTimeout` и подобные; `ProxyJump`, `ProxyCommand`, `HostName`, `ControlPath`, `ControlMaster`, `LocalCommand` — неизвестный хост), мастер-соединение `ssh -S`, туннели и SOCKS `ssh -L`, `-R`, `-D`, `-W`, транспорт git `<имя>::…` и схема вне встроенных в git (`9x://…`). Любое присваивание переменной в той же команде — `export`, `VAR=…` перед командой или отдельно, `env`, `set`, `unset`, `read`, `source`, в PowerShell `$env:X = …`, `$x = …`, `Set-Variable`, `Set-Item env:…`, `Import-Module`, в том числе во вложенном коде другого языка (`pwsh -c "…"` из bash и наоборот) — делает хост её сетевых частей неизвестным: переменная окружения может сменить адрес (`https_proxy`, `GIT_SSH_COMMAND`). `web_search` правилам по домену не подчиняется: веб целиком выключает только `[web] enabled = false`.
- Шаблон `domain` — имя хоста с шаблонами `*` и `?` или IP-адрес. `*` пересекает точки: `*evil.test` совпадёт и с `notevil.test`, `a*.test` — с `a.b.test` (у `deny` и `ask` лишнее совпадение безопасно); поддомены без самого домена — `*.evil.test`. После перевода в нижний регистр и punycode метка имени состоит только из `a-z`, `0-9`, `-`, `_`, `*`, `?`; классов `[…]` и альтернатив `{…}` нет. IP-адрес (`10.0.0.1`, `127.1`, IPv6 `::1` или `[::1]`) — только литералом, без `*` и `?` (`192.168.*.*`, `10.*`, `*.1` и `[fe80::*]` — ошибки). Прочее — схема, порт, путь, пробел (`https://*.evil.test`, `*.evil.test:443`, `evil.test/*`) — ошибка конфигурации: такое правило не совпало бы ни с одним хостом. Глобальное `allow` с `domain` принимается, но ничего не разрешает — предупреждение при загрузке.
- Хост берётся из текста команды, поэтому правило по домену — дополнительный слой, а не граница: псевдоним из `~/.ssh/config` (`Host x` с `HostName`) и подмена адреса `url.<base>.insteadOf` из конфигурации git пользователя команде не видны, как и переменная окружения, заданная прежней командой (отдельным вызовом `bash`) или окружением самого агента, и настоящий хост может отличаться от записанного. Полное решение — исходящий трафик команд через шлюз (R2).
- У `web_fetch` правило по домену сверяется с именем хоста в URL, а не с сервером: тот же сервер по IP-адресу или под другим именем — другой хост. Чтобы закрыть сервер, добавьте правило и на его IP-литерал (`domain = "203.0.113.7"`).
- Режим `bypass` снимает вопрос режима, но не снимает вопросы о необратимом, о пути вне проекта, правила `ask`, вопрос о неизвестном хосте при правилах по домену и инструменты, которые спрашивают всегда.
- Проектный `.zero-agent/config.toml` (только у доверенного проекта) может добавить правила `ask` и `deny`, в том числе по домену, и выключить веб: `[web] enabled = false` (`true` в проекте ничего не включает, прочие ключи `[web]` и `[web.search]` не действуют — предупреждение в stderr; `enabled` не true/false — ошибка). Его `allow`, `allow_bypass` и гранты не действуют, прочие разделы — тоже (предупреждение в stderr). Смена политики (хэш глобальной и проектной) пишется в аудит записью `policy.loaded`.

## Веб (R1-C2)

Модель читает веб двумя инструментами (тир `standard` и выше, в любом режиме, включая `read-only` и `plan`: это только чтение):

| Инструмент | Что делает |
|---|---|
| `web_search(query, count)` | поиск через ваш экземпляр SearXNG: до 20 результатов `N. заголовок` / адрес / описание. Есть в наборе, только если задан `[web.search] url` |
| `web_fetch(url, prompt)` | страница: HTML переводится в Markdown, у PDF — текст первых 20 страниц; длинная страница выгружается, а с `prompt` в контекст идут подходящие к нему абзацы |

```toml
[web]
enabled = true                # false — web_fetch и web_search не регистрируются
robots = true                 # соблюдать robots.txt
max_bytes = 5242880           # предел тела ответа, байт, до 33554432 (у PDF — свой, 32 МиБ)
requests_per_minute = 60      # на процесс; к одному хосту — не чаще раза в 500 мс
ports = [80, 443, 8080, 8443] # порты web_fetch

[web.search]
provider = "searxng"          # единственный поставщик (по умолчанию)
url = "http://127.0.0.1:8888" # свой экземпляр SearXNG
```

- **Свой экземпляр SearXNG.** Поиск бесплатный: поставщик — экземпляр SearXNG, который вы запускаете сами; ключа нет. В его `settings.yml` должен быть включён формат `json` (`search.formats`), иначе он отвечает 403. С `server.limiter: true` SearXNG пропускает к API `format=json` не больше 4 запросов в час с одного адреса, и заголовки этого не меняют; путей два — выключить `server.limiter` в `settings.yml` (у частного экземпляра он обычно выключен) или внести адрес, с которого ходит агент (обычно `127.0.0.1`), в `botdetection.ip_lists.pass_ip` файла `limiter.toml`. `zero-agent doctor` делает пробный запрос к экземпляру (строка `search`) и подсказывает на 403 и 429. Без `url` `doctor` пишет «поиск не настроен».
- **Адрес поставщика — только глобальная конфигурация.** Проектный `.zero-agent/config.toml` его задать не может (предупреждение): иначе чужой репозиторий указал бы свой адрес. Экземпляр обычно стоит на `127.0.0.1` или в локальной сети, поэтому для него сделано единственное исключение фильтра адресов — только для запросов `web_search` и только к этому адресу. `web_fetch` на тот же адрес получает отказ `blocked: local or private address`.
- **`web_fetch`** ходит только по `http` и `https`, без учётных данных в адресе, без cookie, без сжатия и без прокси (переменные `HTTP_PROXY`, `HTTPS_PROXY` не действуют). Локальные и частные адреса (`127.0.0.1`, `localhost`, `10.0.0.0/8`, `169.254.169.254`, IPv6 ULA и link-local и т. п.) отклоняются до соединения: `blocked: local or private address`; порт вне `[web] ports` — `blocked: port N is not allowed`. Редирект исполняется только на тот же хост (до 5 переходов); на другой хост модель получает адрес и решает сама — следующий вызов снова проходит политику и `robots.txt`.
- **Правила по домену к `web_search` не применяются**: у поиска нет хоста страницы, и `deny domain="*"` его не останавливает. Выключить веб целиком можно только `[web] enabled = false` — глобально или в доверенном проекте. Хост поставщика виден в событиях `web.request` и в записи аудита `policy.loaded` (`search_host`); выключение веба — там же (`web_disabled`: `config` или `project`). Запись пишется у нового run и у каждого resume, если хэш политики, `web_disabled` или `search_host` изменились (смена `[web.search] url` или выключение веба во время паузы).
- **Журнал и stderr.** Каждое обращение, в том числе к `robots.txt` и отказ фильтра, — событие `web.request` (метод, адрес, код, размер, время, исход; секреты в адресе маскируются). `run` печатает `zero-agent: веб: GET <адрес> → 200, 12.3 КиБ`, отказ — `zero-agent: веб: отказ <адрес>: <причина>`. Результаты веба помечены строкой `[untrusted content: web]` и в журнале — меткой `web`.
- **Набор веб-инструментов run заморожен.** Resume берёт `web_fetch` и `web_search` только из набора, с которым run начался: новых посреди run нет. Если веб выключили (или убрали `[web.search] url`) во время паузы, модель по-прежнему видит описание (префикс не меняется ради кэша), но вызов не исполняется: она получает `web_fetch: web tools are disabled by configuration since this run started` (у поиска — `web_search: web search is not configured since this run started`), а stderr resume — строку «веб выключен после старта run …».
- **Таблицы и заголовок страницы.** Таблица выравнивается пробелами, только если это увеличивает её вывод не больше чем на 25 % (и в пределах 2 МиБ на страницу); иначе — та же таблица Markdown без выравнивания: пробелы стоят токенов модели. Заголовок страницы — не длиннее 1 КиБ.
- **Разбор HTML и PDF** идёт в отдельном процессе (`zero-agent extract`): падение, переполнение стека или зависание разборщика убивают только его, инструмент получает ошибку. Тот же извлекатель читает PDF в `read` (страницами: `start` — первая, `limit` — сколько, до 50). Память этого процесса не ограничена — принятый риск до R2. Если бинарник не знает своего пути (процесс извлекателя не запустить), `web_fetch` и `web_search` остаются: текст, JSON и XML читаются, на HTML и PDF — отказ `html: extraction is unavailable in this session`, а `read` отвечает на PDF `binary file`.

## Скиллы (R1-C2)

Скилл — каталог с `SKILL.md` (frontmatter `name`, `description`, затем текст шагов). Источники по старшинству:

| Источник | Где | Когда читается |
|---|---|---|
| `user` | `ZA_HOME/skills/<имя>/SKILL.md` | всегда; так редактируется и скилл поставки — свой с тем же именем его затеняет |
| `bundled` | core pack из 14 скиллов в бинарнике (`grill`, `spec`, `tickets`, `orient`, `tdd`, `diagnose`, `review`, `evidence`, `source-driven`, `research-with-citations`, `domain-model`, `retro`, `handoff`, `router`) | всегда |
| `extra` | каталоги `[skills] dirs` по порядку | всегда |
| `project` | `.zero-agent/skills`, `.agents/skills`, `.claude/skills` проекта | только у доверенного проекта |

```toml
[skills]
enabled = true          # false — ни каталога, ни activate_skill, ни /имя
dirs = ["D:/skills"]    # каталоги extra, абсолютные пути (~ и переменные не раскрываются)
max_entries = 1000      # предел записей обхода на каждый корень user и extra
```

- **Как скилл попадает к модели.** На тире `standard` и выше каталог (имена и описания) — в описании инструмента `activate_skill`, и модель загружает нужный скилл сама. Пользователь загружает скилл командой `/<имя>` в начале задачи или ввода (любой тир). На тире `small` к сообщению пользователя добавляется короткая карточка подходящего скилла; полный текст — по `/<имя>`. В stderr `run` — `zero-agent: скилл <имя> (<источник>)`. Каталог run пишется событием `skill.catalog` (число по источникам, пропущенные с причинами, предупреждения).
- **Скиллы, выключенные во время паузы** (`[skills] enabled = false` перед resume): модель по-прежнему видит описание `activate_skill` (префикс заморожен ради кэша), но новый вызов не исполняется — ответ `activate_skill: skills are disabled by configuration since this run started`, а stderr resume — строка «скиллы выключены после старта run ([skills] enabled = false): вызовы activate_skill этого run не исполняются». Скилл, загруженный до паузы, на resume берётся из журнала тем же текстом.
- **`zero-agent skills list [--project DIR]`** печатает скиллы (`имя  источник  путь` и предупреждения), затем пропущенные с причинами. Скиллы проекта — только у доверенного проекта; иначе строка «проект не доверен» и какие доверенные файлы изменились.
- **Ссылки не разворачиваются.** Каталог скилла, подключённый ссылкой или junction (частая практика у `~/.claude/skills`), не читается: он среди пропущенных с причиной `linked skill directory`, а `skills list` и `doctor` подсказывают, что делать — скопировать каталог скилла или перечислить каталог, где он лежит, в `[skills] dirs`. Ресурс скилла с невидимыми или управляющими символами в имени в список ресурсов не входит (предупреждение скилла).
- **Предел обхода.** Корень `user` или `extra`, в котором больше `max_entries` записей (файлов, каталогов, ссылок), не читается целиком: обход идёт на каждом старте run. Следующие корни читаются; `skills list` и `doctor` называют пропущенный корень и предел. Выход — поднять `max_entries` (около 1,25 мс на файл на старте run), разнести скиллы по нескольким `dirs` или убрать из каталога лишнее.
- **Доверие.** Деревья скиллов проекта входят в набор доверенных файлов. Правка `.claude/skills/*` (и других деревьев) — в том числе самим агентом внутри проекта — меняет набор доверия: следующий run спросит доверие заново с отличием «изменены: .claude/skills». Это полезное свойство: скилл, переписанный моделью или чужим коммитом, не становится доверенным молча.
- **Скилл ничего не исполняет.** Поля `hooks`, `commands`, `scripts` frontmatter игнорируются с предупреждением, `allowed-tools` прав не даёт. Текст скилла приходит модели как данные: невидимые символы удаляются, разметка экранируется. Файл, изменённый после старта run, не загружается (`changed since the run started`).

## Безопасность (R1-C2)

- **ОС-изоляции нет** (решение заказчика на старте): граница проекта держится на решениях агента, политике, режимах, грантах, доверии и журнале. Отдельный процесс извлекателя защищает от падения и зависания разборщика, а не изолирует его.
- **SEC-052 и SEC-053 отменены решениями заказчика 2026-11-11.** Чтение из сети на запуск команд не влияет (вопросов к командам после `web_fetch` нет), и сочетание недоверенного содержимого, ваших файлов вне проекта и обращения в сеть вызов не останавливает. Вместо вопросов экспозиция run пишется в журнал (`exposure.changed`) и в аудит (`rule_of_two`), а stderr сообщает о ней один раз за run — раздел «Rule of Two».
- **Веб — только через один шлюз**: разрешающий список адресов в резолвере (каждое соединение идёт по проверенному адресу), порты, редиректы на тот же хост, лимиты размера и частоты, `robots.txt`, журнал каждого обращения. Исключение — только адрес SearXNG из глобальной конфигурации и только для `web_search`.
- **Принятые риски** (ADR 0006): публичный адрес, ведущий обратно в вашу сеть (внешний IP роутера с hairpin NAT), фильтр не отличает; экземпляр SearXNG агент считает доверенным ровно как адрес, который вы вписали сами; память подпроцесса извлечения не ограничена (предел — R2); команда `bash` может передать данные наружу без записи экспозиции (граница shell — best effort).

## Память (R1-M)

Клиент памяти ZeroAIMemory подключается разделом `[memory]` глобальной `ZA_HOME/config.toml` и токеном агента в переменной `ZA_MEMORY_TOKEN` (свой токен агента, выпускается в WebUI памяти; не токен клиента `zam`):

```toml
[memory]
url = "http://127.0.0.1:7700"   # адрес сервера: http или https, без логина и пароля
# machine = "workstation"       # имя для X-Zam-Machine; по умолчанию — имя хоста
enabled = true                  # false — работа без памяти
```

- **Адрес задаёт только глобальная конфигурация.** В `.zero-agent/config.toml` проекта действует только `[memory] enabled = false` (выключить память в этом проекте); `url` и `machine` там не действуют — предупреждение в stderr: чужой репозиторий не направит запросы с вашим токеном на свой адрес.
- **Клиент** ходит без прокси (переменные `HTTP_PROXY` не действуют), редиректы не исполняет (ответ 3xx — ошибка «memory server redirected; not followed»), токен шлёт только своему серверу и не печатает.
- **Уровень** определяется по `GET /api/v1/health` (корневой `/health` у ZeroAIMemory — веб-интерфейс): L0 — сервер не отвечает или это не API ZeroAIMemory, L1 — сервер без списка возможностей (`0.0.10-m5.7`), L2 — в списке есть `m6` (`0.0.11-m6`, `0.0.12-m6.5` и новее). Версия только печатается. Без памяти агент работает (L0).
- **`zero-agent doctor`** показывает строку `memory`: версию и коммит сервера, уровень, число флагов, принят ли токен, открыт ли Vault, выключенные у вас типы подсказок памяти. Предупреждение — если память не настроена, сервер недоступен, токен не задан или отклонён, Vault заблокирован, а также если адрес `http` ведёт на хост вне локальной сети (`127.0.0.1`, `localhost`, `10.*`, `172.16–31.*`, `192.168.*`, IPv6 ULA и link-local): токен шёл бы открытым текстом, нужен `https`.

## Безопасность памяти (R1-M)

У агента свой токен памяти ZeroAIMemory — переменная `ZA_MEMORY_TOKEN`. Токен вашего клиента `zam` лежит в `~/.zeroaimemory/config.toml` (`%USERPROFILE%` на Windows, `$HOME` иначе), и модели он недоступен. Меры встроенные: их не снимают ни правила проекта и глобальной конфигурации, ни гранты, ни режим `bypass`.

- **Защищённые места.** `ZA_HOME` и `~/.zeroaimemory/` инструменты модели не читают, не ищут, не перечисляют и не пишут, команда не запускается с `cwd` там: `denied: protected path` без вопроса. Сверяется настоящий путь — через ссылку, junction, короткое имя и в другом регистре тоже. Слова команды `bash`, начинающиеся с `~`, `$HOME`, `${HOME}`, `%USERPROFILE%`, `$env:USERPROFILE`, и абсолютные пути туда дают тот же отказ. Свои файлы агент читает сам: конфигурацию, журнал, чекпоинты и скиллы `ZA_HOME/skills` (`activate_skill` работает).
- **Обход их пропускает.** `search` и `glob` по каталогу выше защищённого места (проект — сам домашний каталог, грант на домашний каталог, шаблон вида `C:/Users/u/**`) в `ZA_HOME` и `~/.zeroaimemory/` не заходят. Чекпоинт проекта, равного домашнему каталогу, не берёт `~/.zeroaimemory/config.toml`, а `checkpoints restore` его не трогает.
- **Одобрение и грант их не открывают.** Одобренный, но ещё не исполненный вызов (`answer --approve`, в том числе одобрение, открытое старой версией) с `zam` или защищённым местом после resume получает отказ. `request_grant` на защищённое место — отказ без вопроса.
- **Домашний каталог в командах — граница проекта.** Путь в команде `bash`, начинающийся с `~`, `$HOME`, `${HOME}`, `%USERPROFILE%`, `$env:USERPROFILE`, — всегда «вне проекта»: в режиме `auto` такая команда спрашивает (`outside_project`), даже если проект — сам домашний каталог или есть грант на него. В вопросе показан настоящий путь.
- **`.zeroaimemory/` проекта** (привязка к решению памяти) модель читает, но не пишет.
- **Проект внутри `ZA_HOME` или `~/.zeroaimemory/`** — run не запускается: инструменты туда не обращаются. Домашний каталог, который не разрешается (сетевой путь, висячая ссылка), — run тоже не запускается, сообщение называет домашний каталог.
- **Секреты в `AGENTS.md` и `CLAUDE.md`.** Старый клиент `zam` писал токен строкой `ZeroAIMemoryToken=…` в `CLAUDE.md`. Файл инструкций проекта (агент читает `AGENTS.md`, без него — `CLAUDE.md`; `CLAUDE.local.md` не читает) до модели проходит ту же маску, что вывод инструментов: формат токена `zam_` и прочие шаблоны, значения `ZA_SECRET_*`. Модель видит `[secret masked: zam_token]`, в stderr run — `zero-agent: в файле инструкций проекта замаскировано секретов: N`, в журнале — событие `input.masked` без значений. Уберите токен из файла сами.
- **Клиент `zam` агенту недоступен.** Команда `bash`, в которой вызывается `zam` (`zam.exe`, полный путь, `env zam`, `sh -c "zam …"`, `pwsh -Command`, `cmd /c`, конвейер), получает `denied: memory client` без вопроса. Причина: `zam` берёт адрес сервера из `CLAUDE.md` и `AGENTS.md` проекта, а токен — из вашего домашнего каталога; чужой репозиторий со строкой `ZeroAIMemoryUrl=http://…` получил бы ваш токен. Запускайте `zam` из своего терминала; агент работает с памятью через свой клиент.
- **Окружение команд.** Переменные `ZA_MEMORY_*` и `ZAM_*` (`ZAM_URL`, `ZAM_TOKEN`, сессия) командам `bash` и прочим дочерним процессам не передаются.
- **Маска.** Строка формата токена ZeroAIMemory (`zam_` и 40 букв и цифр) в выводе инструментов, ответе и аргументах модели заменяется на `[secret masked: zam_token]`.
- **Остаточные риски** (ADR 0007, граница shell — best effort): путь из переменной, подстановки или относительный после `cd`, имя `zam` из переменной, переименованная копия клиента и сборка его из исходников не ловятся; токен, разорванный переводом строки, маска формата `zam_` не узнаёт.
